상태·감사 모듈은 원본·canonical·캐시를 읽지 않으며 실제 전처리 실행도 하지 않는다. 현재 통과한 테스트는 독립 합성 입력만 사용한다.

승인 대상·기록·검사 함수는 `src/agents/approvals.py`, 영속 저장소는 `src/agents/approval_store.py`에 둔다. `record_confirmed_approval()`은 상위 실행기가 사용자 확인을 마친 뒤 호출하는 내부 기록 API이며 자체적으로 사용자 인증을 수행하지 않는다. `pending`은 발급 후 미사용 상태다. `consume_and_reserve()`는 쓰기 잠금 획득 후 최신 시각·기록으로 검사하고 승인 소비와 예약을 함께 커밋한다. 예약이 실패하면 소비도 롤백하며, 이미 커밋한 예약은 자동 재실행하지 않는다. 동일 승인 동시 소비·새 승인으로 동일 작업 중복 예약·만료·취소·대상 변경·예약 저장 장애를 합성 DB로 검증했다. 실제 worker 연결은 후속 구현 범위다.

### 산출물 완료·재사용 검사 구현

`src/agents/artifacts.py`는 도구별 내용 검증이 끝난 attempt 폴더에 `AGENT_COMPLETE.json`을 기록한다. 기존 전처리 코어의 `SUCCESS.json`은 보존하며 이 파일도 정합성 검사 대상에 포함한다. `ArtifactContext`의 `source_id`, `config_id`, `plan_id`, `policy_version`, `tool_id`가 모두 같고 실제 파일 목록·크기·SHA-256이 일치할 때만 `ARTIFACT_REUSABLE`을 반환한다. 식별값은 상위 실행기가 실제 원본·설정·계획에 연결해야 하며 임의의 문자열 입력만으로 그 연결이 입증되지는 않는다.

`complete_artifacts()`는 파일을 청크 단위로 해싱하고 완성된 임시 표식을 하드 링크로 게시하여 기존 표식을 덮어쓰지 않는다. `check_artifacts()`는 파일을 다시 읽어 검사하므로 대형 캐시는 검사 시간이 필요하다. 등록된 파일의 누락·추가·동일 크기 내용 변경·계약 변경·잘못된 표식·상위 경로 이동·JSON 중복 키를 거부한다. 빈 폴더와 파일만 남은 부분 결과는 완료로 인정하지 않는다. 상세 내용·파일 목록·해시는 로컬용이며 LLM 입력으로 전달하지 않는다.

표식 작성 전 내용 검증은 등록 도구의 검증 함수로 호출하고, 동일 실행의 동시 쓰기는 OS 실행 잠금으로 차단한다. 임의 프로세스의 파일 쓰기·허용 루트와 OS 접근 권한·파일 검사와 사용 사이의 경로 바꿔치기 방어는 후속 격리 구현 범위다. SHA-256은 손상 검사이며 악의적인 표식 재작성이나 과거 정상 결과 교체를 인증하지 않는다. 승인 DB 변조 방어 후속 검토와 함께 인증 무결성을 재검토한다.

테스트 실행 결과는 [범용 설계](design/GENERIC_PREPROCESSING_DESIGN.md)의 검증 범위와 최신 실행 기록을 따른다. 실제 심볼릭 링크 생성 검사는 Windows 권한 부족으로 건너뛸 수 있으며 실제 junction·경로 바꿔치기 OS 검증 완료를 뜻하지 않는다.

### 규칙 기반 실행기 구현

`src/agents/executor.py`의 `RulesExecutor`는 등록된 `RegisteredTool`의 실행·검증 함수만 호출한다. `ExecutionPlan`에 고정한 단계와 로컬 인자를 사용하며 동적 import·셸 명령·LLM 호출을 수행하지 않는다. 한 번의 `run_next()`는 현재 단계 하나만 처리한다. 현재 도구 함수는 실행기와 같은 프로세스에서 실행하므로 OS 격리 worker는 별도 구현해야 한다.

- `ExecutionStep`: 단계·도구 ID·로컬 JSON 인자. 인자는 정규화하고 계획 ID에 포함한다.
- `ExecutionPlan`: 원본·설정·정책 식별값과 단계 목록. 최초 계획·실행 주체를 `execution_plan.json`에 고정한다.
- `RegisteredTool`: 신뢰하는 코드에서 주입하는 `execute(output_dir, arguments)` 및 `validate(output_dir, arguments)` 함수와 추가 승인 필요 여부.
- `scope_for(stage)`: 사용자 승인 연결에 필요한 정확한 작업 범위를 반환한다. 승인 발급 기능은 아니다.
- `run_next(approval_id=...)`: 정책·선행 작업·승인을 검사하고 한 단계를 수행한다. 승인 없이 민감 단계에 도달하면 `awaiting_approval`로 저장한다.

`run_ingest`, `review_eda`, `commit_split`, `prepare_data` 및 호환용 `prepare_cache`는 등록 옵션과 무관하게 승인을 요구한다. 단계·작업·템플릿은 `src/preprocessing/workflows.py`에서 한 번 정의한다. 분할 계획에는 `run_eda → review_eda → propose_split`을 포함하고 프로파일 계획은 템플릿 단계 전체와 일치해야 한다. 합성 데모의 OS 계정 확인·대화형 승인을 연결했으며 실데이터용 제한 세션·승인은 후속 범위다.

DB의 `task_runs`는 `reserved → running → verified → committed`를 기록하며 실행·내용 검증 실패는 `failed`로 남긴다. 기존 `reservations` 테이블을 덮어쓰지 않는다. `reserved/running/failed` 또는 이전 버전의 예약만 남은 작업은 `TASK_REQUIRES_REVIEW`로 차단한다. `verified/committed` 결과는 파일 정합성과 내용 검증을 다시 통과하면 실행 없이 재사용한다. 검증 후 DB 커밋 전 중단, DB 커밋 후 상태 저장 전 중단을 각각 합성 테스트로 확인했다. 부분 산출물은 삭제하지 않는다.

실행 폴더의 `executor.lock`은 Windows 파일 잠금 또는 POSIX flock을 사용한다. DB 잠금은 승인·예약을 보호하고 OS 잠금은 같은 실행의 파일·상태 진행을 보호한다. 취소·revision·blocker를 도구 실행 전과 실행 후에 확인한다. 같은 프로세스에서 동작하는 장시간 도구는 중간 강제 취소하지 않으며 반환 후 완료 등록·후속 실행을 막는다. 감사 기록 실패·계획 불일치·잘못된 승인·산출물 손상은 후속 실행을 차단한다.

실행기 회귀 검증 명령:


### 공통 품질 검사 연결

`src/preprocessing/quality.py`는 구조·수치형·결측/상수 후보·target·복합 ID·group·timestamp를 검사한다. `QualityRules`는 프로파일의 선택 설정이며 기본값과 다른 기준을 프로파일/계획 서명에 포함한다. 판단은 `passed/review_required/blocked_input`이고 데이터 삭제·대치·라벨 변경을 수행하지 않는다. 각 검사 근거는 로컬 quality.json·quality.md에 남긴다.

입력 어댑터의 `audit_tool()`은 같은 원본 식별·로더·프로파일을 `run_audit`에 연결한다. 구조 오류를 보고서로 남기기 위해 audit에서만 로더의 strict validate를 유예하고 품질 코어가 구조부터 검사한다. EDA 입력 검증은 기존 strict 방식을 유지한다. 데이터 읽기 계약 오류는 고정 코드로 보고서를 만들며 원문 오류를 반환하지 않는다.

실행기는 `review_required`도 후속 EDA로 진행하지 않고 `TOOL_REVIEW_REQUIRED`로 중단한다. 차단 입력은 `TOOL_INPUT_BLOCKED`, 실행 오류는 `TOOL_RUNTIME_FAILED`로 구분한다. 부분 품질 보고서는 보존하고 통과하지 않은 단계에는 완료 표식을 만들지 않는다. 검토 결과를 자동 승인·해제하는 기능은 아직 없다. 상세 기준·설정·검증 범위는 [품질 검사](history/QUALITY_CHECK.md)를 따른다.

### 공통 EDA와 WM 적용 사례

`src/agents/adapters/tabular.py`는 CSV 로더 또는 다른 등록 로더의 `TabularInput`을 공통 `src/preprocessing/eda.py`로 전달한다. `wm811k_metadata.py`는 WM metadata 읽기·accepted 행 선택만 담당하고 동일한 공통 EDA를 사용한다. `wm_eda.py`는 이전 import 호환 wrapper다. 맵 예시·Lot 충돌·다이 공간 통계는 기존 `wafer_dl` 도메인 코어에 유지한다. 반환값은 일반 `ToolResult`이며 상세 집계·그림·경로는 로컬 보고서에만 저장한다.

WM의 `source_id`는 관리 파일·manifest 해시를 결합하며 CSV는 로컬 파일 해시를 사용한다. WM metadata 식별값은 원본 pickle·NPZ 인증이 아니다. 공통 프로파일에 역할·분석 옵션·adapter/workflow ID를 정의하고 프로파일 서명을 `config_id`·도구 인자·계획 ID에 연결한다. 출력 검증은 공통 완료 계약·필수 파일·입력에서 계산한 요약을 검사하고 파일 해시는 실행기가 검사한다. timestamp·target·group·ID는 수치 상관분석에서 제외한다.

공통 EDA도 `requires_approval=True`로 등록한다. 독립 CSV의 다중 클래스·미라벨·범주형 입력과 WM metadata를 검증했다. 실제 데이터 실행 CLI는 연결하지 않았고 합성 데모는 유지한다. `plan --profile`은 원본을 읽지 않는 계획 조회만 제공한다. 실데이터 활성화 전에는 승인 DB 변조 방어·원본 검증·OS 격리·사용자 승인 대상 표시를 검토한다. 범용 품질 규칙과 Random·Group·Time 분할 제안·승인 후 확정은 구현했다. 분할 확정 승인은 선행 제안의 완료 표식 해시까지 결합하며 [분할 검사](history/SPLIT_CHECK.md)의 제약을 따른다. Train-only fit·Train/Validation 변환·JSON 저장/복원과 승인 필수 prepare_data 연결도 합성 검증했다. 설정·Test 처리 경계·기존 코드 유지 범위는 [학습 입력 준비](history/TRAIN_ONLY_PREPARATION.md)를 따른다.

## 1. 확정 범위와 보안 불변식

- LLM은 최소 검사 상태를 받아 안전한 다음 작업만 선택한다. 전처리 정책·라벨·분할·해상도·임계값을 수정하지 않는다.
- 원본·개별 샘플·맵·텐서·정확한 통계·집계·식별자·실제 설정·원문 오류는 어떤 LLM에도 제공하지 않는다.
- 승인된 일반 검사 상태와 현재 허용 동작 ID만 예외로 제공한다. 이는 데이터와 무관한 정보가 아니며 상태·호출 순서·시점에서 제한적인 추측 위험이 남는다.
- 원본을 검사하는 코어, 실행 권한을 가진 관리자, LLM 선택기를 분리한다. 선택기는 파일·도구 직접 실행 권한을 갖지 않는다.
- 필수 검사 실패·유효 승인 없음·권한 판단 불가·보안 기록 실패 시 후속 작업을 차단한다.
- 실제 실행의 LangSmith·외부 trace·crash upload·일반 telemetry는 금지한다. 승인된 provider 요청은 별도 검토한 최소 계약만 허용한다.
- API 없이도 `rules_only`로 전처리를 완료할 수 있다. `bounded_llm` 활성화는 13절의 검증을 통과해야 한다.

## 2. 위협 모델

보호 자산은 원본·캐시·라벨·Lot, 설정·분할 계약, 승인 기록, 체크포인트, 산출물, provider 비밀 키다. 비신뢰 입력에는 원본 metadata·pickle·파일 경로, 사용자 설정, LLM 응답, 과거 저장 상태, 패키지·SDK 출력이 포함된다.

| 위협 | 공격·실패 예 | 설계 대응 |
| --- | --- | --- |
| 프롬프트 주입 | 라벨·오류에 업로드 지시 포함 | 원문을 문맥에서 제외, 열거값 매핑만 허용 |
| 도구 악용 | LLM이 삭제·셸·재분할 요청 | 고정 동작 ID, 인자 없음, 실행기 독립 검증 |
| 데이터 유출 | 로그·헤더·SDK trace에 경로 포함 | DTO 새 생성, egress 제한, 네트워크 캡처 검사 |
| 승인 우회·재전송 | 과거 승인·응답을 다른 작업에 적용 | actor·정확한 대상·버전에 결합, 원자적 소비·응답 폐기 |
| 저장 상태 오염 | checkpoint의 blocker·경로 조작 | 로컬 접근 통제·무결성·재개 시 재검증 |
| 자원·비용 고갈 | 진단 루프·무한 재시도 | 실행/지점/도구별 상한·취소·회로 차단 |
| 공급망·역직렬화 | SDK telemetry·악성 pickle 실행 | 의존성 검토·격리된 ingestion·기본 네트워크 차단 |

초기 대상은 한 명의 로컬 운영자다. 악성 관리자가 OS 권한·코드·정책·키를 모두 통제하는 상황까지 방어한다고 주장하지 않는다. 코어가 침해되면 상태 선택·호출 시점도 은닉 유출 통로가 될 수 있다. 최소 DTO는 코어 신뢰를 대체하지 않는다. 다중 사용자·원격 서비스·다중 에이전트는 범위 밖이며 추가 인증·격리 검토 전 활성화하지 않는다.

## 3. 컴포넌트와 신뢰 경계

```text
로컬 운영자 → 실행 관리자·승인 UI → 도구 실행기 → 전처리 코어
                  │                    │             │
                  └──── 로컬 상태·감사 기록·산출물 ──┘
                  │
              정보 축소 게이트
                  │ 최소 DTO만, 제한된 IPC
                  ▼
             LLM 선택기 프로세스 → 승인 provider / 격리 로컬 LLM
                  │ 동작 ID·사유 코드만
                  ▼
              응답 검증기 → 현재 정책 재검사 → 실행 관리자
```

| 구성 | 읽기 | 쓰기·실행 | 네트워크 |
| --- | --- | --- | --- |
| 실행 관리자 | 설정·로컬 상태·승인 | 그래프·승인·감사 기록, 등록 도구 호출 | 외부 차단 |
| 전처리 코어 | 승인 원본·실행 산출물 | 승인된 실행 하위 산출물 | 외부 차단 |
| 축소 게이트 | 검증된 로컬 결과 | 새 최소 DTO·로컬 전송 검사 기록 | provider 직접 접속 없음 |
| LLM 선택기 | 정적 정책·도구 설명·DTO·전용 키 | 엄격한 선택 응답 | 검토한 단일 provider 연결만 |
| 로컬 보고서 | 검증된 결과 | Markdown·그림 | 외부 차단 |

단순한 별도 Python 프로세스나 가상환경은 보안 격리가 아니다. Windows에서는 별도 제한 계정·NTFS ACL·방화벽 또는 검증한 VM/컨테이너 구성으로 권한을 강제한다. 실제 수단은 환경 확인 후 선정하고 선택기의 `data/`, `logs/`, `models/`, `reports/` 직접 접근 거부를 실측한다. 같은 사용자 계정으로 실행해 파일을 읽을 수 있는 구성은 실데이터 LLM 모드의 통과 조건이 아니다.

IPC는 로컬 제한 named pipe 등 인증·접근 통제가 가능한 전송을 사용한다. 초기에는 한 요청씩 직렬 처리한다. IPC 봉투의 상관 ID는 무작위 일회성으로 로컬에서만 사용하고 provider 본문·헤더·요청명에 넣지 않는다. 선택기가 실행기 RPC를 호출하거나 파일을 열게 하지 않는다. 공유 폴더에 전체 상태를 적어 전달하는 방식은 금지한다.

TLS 검증을 끄지 않으며 endpoint의 scheme·host·port·경로를 허용목록으로 검증한다. 임의 redirect·proxy·사용자 endpoint·자동 fallback provider는 거부한다. 네트워크 허용은 URL 검사만으로 구현하지 않고 실제 egress 경계로 강제한다. DNS·SDK·프록시의 우회 여부도 시험한다.

## 4. 로컬 데이터 계약과 최소 상태 매핑

### 4.1 내부 계약

내부 `ToolResult`는 `status`, `artifact_refs`, `metrics`, `warnings`, `errors`를 가진다. 배열은 파일 참조로 보관한다. 상세 오류·수치는 로컬 보고서로만 전달한다. 모든 내부 결과는 등록된 도구와 현재 실행에 결합해 검증하며 임의 객체의 `status` 문자열을 신뢰하지 않는다.

로컬 상태에는 기초 설계의 필드 외에 `policy_version`, `state_revision`, `decision_checkpoint`, `pending_request`, `decision_counts`, `request_budget`, `cancel_requested`, `artifact_status`를 둔다. 이 필드와 이력은 LLM 입력이 아니다.

### 4.2 상태 매핑표

| 로컬 판단 | 외부 최소 상태 | 가능한 동작 |
| --- | --- | --- |
| 구조·라벨 필수 검사 통과 | structure_check_passed | continue_workflow, request_user_review |
| canonical 구조 검사 실패, 안전한 추가 진단 가능 | structure_review_required | inspect_structure, request_user_review |
| 분할안의 비중첩·클래스 지원·그룹 조건 실패 | split_constraints_unmet | inspect_split_constraints, request_user_review |
| 캐시 필수 계약 검사 통과 | cache_check_passed | continue_workflow, request_user_review |
| 캐시 계약 검사 실패, 읽기 진단 가능 | cache_review_required | verify_cached_contract, request_user_review |
| 매핑 불가·권한/감사 오류·의심스러운 입력·ingest 실패 | 전송하지 않음 | 로컬 안전 중단·사용자 확인 |

분할안의 필수 검사 통과 시에는 고정 승인 노드로 이동하며 LLM을 불필요하게 호출하지 않는다. 위 목록은 최대 후보이며 실행기가 안전 조건·기실행 동작·예산으로 더 줄인다. 자유문에서 상태를 추출하지 않고 타입화한 내부 검사 결과를 고정 표로 매핑한다. 여러 실패가 있으면 로컬 우선순위로 하나의 일반 상태를 고르고 실패 건수·유형 목록을 보내지 않는다.

동일 상태의 추가 진단은 한 번만 허용한다. blocker가 그대로면 다음 LLM 요청 없이 사용자 확인으로 종료한다. LLM에 별도 성공 이력·도구 로그·상세 진단 결과를 덧붙이지 않는다.

### 4.3 provider 입력

```json
{
  "contract_version": "minimal_state_v1",
  "check_state": "split_constraints_unmet",
  "allowed_actions": ["inspect_split_constraints", "request_user_review"]
}
```

키는 위 세 개로 고정하고 추가 키·중복 JSON 키·null·타입 강제 변환·빈 동작 목록·중복 동작·미등록 열거값을 거부한다. 동작은 정해진 정렬 순서로 직렬화한다. `contract_version`은 공개 메시지 규격이며 실제 데이터 버전이 아니다. 정적 프롬프트·도구 설명에는 공장·프로젝트 경로·실제 환경·설정값을 넣지 않는다.

provider 요청은 정적 system 지시와 위 DTO뿐이다. 대화 이력·RAG·파일 첨부·원본 기반 예시·자동 메모리·직접 function calling 실행 루프는 없다. HTTP 인증은 선택기의 전용 비밀 키만 사용하며 실행 식별자가 아니라는 이유로 비밀 키를 본문·로그에 남기지 않는다.

### 4.4 provider 출력

```json
{
  "action_id": "inspect_split_constraints",
  "reason_code": "CHECK_CONSTRAINTS"
}
```

| action_id | 유일한 허용 reason_code |
| --- | --- |
| inspect_structure | CHECK_STRUCTURE |
| inspect_split_constraints | CHECK_CONSTRAINTS |
| verify_cached_contract | VERIFY_CONTRACT |
| request_user_review | NEEDS_USER_REVIEW |
| continue_workflow | READY_TO_CONTINUE |

JSON 객체 하나만 받는다. 추가 키·인자·자유문·Markdown 코드블록·도구 호출 배열·잘못된 조합은 거부한다. 응답이 잘렸거나 구조화 출력 지원이 불충분해도 문자열에서 일부를 찾아 실행하지 않는다. SDK가 반환한 본문은 검사 후 폐기하며 로컬에는 파싱한 열거값과 거부 코드만 기록한다. 거부된 응답 원문은 기본 저장하지 않는다.

## 5. 선택·실행 프로토콜

1. 실행 잠금을 얻고 현재 계획·actor·state_revision·취소 상태·정책 버전을 확인한다.
2. 로컬 도구 결과를 검증하고 필수 blocker를 먼저 적용한다. LLM은 blocker를 해제할 수 없다.
3. 매핑 가능한 상태와 안전한 동작 후보를 만든다. 승인·예산·네트워크 전제 미충족이면 전송하지 않는다.
4. 로컬 pending 기록에 상태 버전·후보·일회성 요청 ID·만료를 결합하고 요청 예산을 먼저 예약한다.
5. 새 DTO를 생성·검사하고 제한된 IPC로 선택기에 전달한다. 선택기는 같은 계약을 다시 검증한다.
6. 응답을 파싱하고 현재 후보·사유 코드·응답 만료·취소·계획 변경을 검사한다.
7. 잠금 안에서 pending을 한 번만 소비하고 동작을 예약한다. 중복 응답은 실행하지 않는다.
8. 실행 직전에 도구 정책·선행 조건·승인·대상 경로·budget을 다시 검사한다. 동작 인자는 로컬 계획에서만 구성한다.
9. 로컬 감사 기록을 남긴 뒤 도구를 실행하고 결과·산출물·상태를 등록한다. 기록 실패 시 새 작업을 시작하지 않는다.
10. 완료·사용자 확인·다음 고정 단계 중 하나로 이동한다. 반복이면 중단하고 실제 근거는 로컬 UI에 표시한다.

상태 변경·취소가 요청 중 발생하면 응답을 버린다. 재시작 시 pending 응답은 모두 무효화하고 provider 요청을 자동 재전송하지 않는다. 기존 호출 비용은 예산에서 되돌리지 않는다. 거부 응답·시간 초과를 새로운 질문으로 무한 보정하지 않는다.

`rules_only`는 같은 안전 실행기를 사용한다. 검사 통과 시 고정 단계로 복귀하고, 진단 가능 실패면 해당 진단을 최대 한 번 실행한 뒤 사용자 확인으로 이동한다. 모드별 데이터 정책·승인·필수 검사는 동일하다.

## 6. 도구 권한과 승인 계약

### 6.1 실행 레지스트리

| 분류 | 작업 | 호출 주체 | 권한 |
| --- | --- | --- | --- |
| 제한적 읽기 | inspect_structure, inspect_split_constraints, verify_cached_contract | LLM 제안 또는 규칙 | 현재 실행의 검증된 산출물만 읽음 |
| 제어 | request_user_review, continue_workflow | LLM 제안 또는 규칙 | 승인 생성·단계 생략 없음 |
| 민감 로컬 처리 | ingest, commit_split, prepare_cache | 고정 그래프만 | 정확한 원본·분할·변환 계획 승인 필요 |
| 로컬 기록 | publish, render_report | 고정 그래프만 | 필수 검사·완료 계약 확인 후 새 산출물 등록 |
| 금지 | 임의 셸·코드·설치·웹·삭제·학습·Test 성능 평가 | 누구도 자동 호출 불가 | 레지스트리에 등록하지 않음 |

도구는 임의 함수명 import가 아니라 코드에 등록한 ID로 찾는다. LLM이 인자를 전달하지 못하게 하며 대상 참조는 실행기가 계획에서 해석한다. `request_user_review`는 로컬 알림·미리보기 생성이지 승인 행위가 아니다. `continue_workflow`도 다음 고정 노드로 복귀할 뿐 직접 쓰기 도구를 실행하지 않는다.

경로는 허용 루트 내 정규화·최종 대상·junction/symlink·UNC·장치 경로·대체 데이터 스트림을 검사한다. 승인 후 경로 바꿔치기 위험을 줄이도록 원본은 읽기 전용 승인 사본/스냅샷으로 고정하고 핸들 기반 최종 대상 확인·ACL을 적용한다. 사전 resolve 검사만으로 TOCTOU 공격을 해결했다고 주장하지 않는다.

### 6.2 승인 기록과 재개

승인 기록은 로컬에 `approval_id`, `actor_id`, `run_id`, `stage`, `tool_id`, 정규화 대상 참조·인자 식별값, `source_id`, `config_id`, `plan_id`, `policy_version`, 생성·만료 시점, `pending/consumed/revoked/expired` 상태를 둔다. 식별값은 자동 생성하며 소스에 해시를 수작업으로 적지 않는다. 이 기록은 LLM에 보내지 않는다.

초기 승인 유효기간은 30분, 요청·응답 유효기간은 60초로 제안한다. 운영자가 로컬 승인 화면에서 정확한 작업·대상·영향을 확인한다. 단순 메시지나 `approved=true` 설정은 승인으로 인정하지 않는다. 정책·대상·인자·원본·설정 변경 또는 취소 시 관련 승인은 폐기한다.

승인 검증·소비·작업 예약은 하나의 로컬 DB 트랜잭션으로 처리한다. 같은 승인을 동시에 두 번 사용할 수 없게 한다. 소비 직후 장애가 나면 승인 상태를 자동으로 되돌리지 않는다. 작업 완료 여부를 조사해 완료 결과를 재사용하거나, 미완료 작업에 새 승인을 요청한다. 작업이 실행됐는지 불명확하면 새로 실행하지 않고 사용자 확인을 요청한다.

로컬 actor는 OS 계정과 제한된 실행 세션으로 식별하고 CLI의 임의 문자열을 신뢰하지 않는다. 관리자·동일 계정의 임의 코드에 대한 강한 부인 방지를 보장하지 않는다. 향후 원격 UI 도입 시 인증·세션·CSRF·권한 검증과 중요 작업의 재인증을 별도 설계한다.

## 7. 저장·중단·재개·데이터 보호

체크포인트·승인·결정 예산은 로컬 영속 저장소에 둔다. DB 트랜잭션과 캐시 파일 생성은 서로 원자적이지 않다. `planned → reserved → running → verified → committed` 작업 기록과 완료 표식으로 복구한다. 임시 산출물은 현재 실행의 새 attempt 경로에 생성하고 검증 뒤 같은 파일시스템 내 등록을 수행한다. 완료 표식만 있거나 파일만 있다고 완료로 판단하지 않는다.

재개 전 원본·설정·정책·산출물 계약·잠금을 확인한다. 완료 결과는 재사용하고 부분 결과는 격리 보존한다. 잠금은 프로세스 생존 확인 없이 삭제하지 않는다. 취소는 새 도구·LLM 요청을 즉시 금지하고 실행 중 도구는 안전 지점에서 정지한다. 강제 종료가 필요하면 하위 프로세스까지 종료됐는지 확인하고 부분 결과를 등록하지 않는다. ‘롤백’은 원본 복원·자동 삭제가 아니라 미완료 결과 미등록과 이전 완료 버전 유지다.

원본과 checkpoint가 백업·동기화 폴더로 자동 전송되지 않게 한다. 실데이터 모드에서는 암호화된 로컬 저장 장치와 제한 ACL을 확인하고, 키는 데이터와 다른 승인 저장소로 관리한다. 로컬 checkpoint는 스키마·정책·무결성을 검증하며 신뢰하지 않는 pickle로 복원하지 않는다. 인증 무결성이 필요한 상태에는 관리된 키를 쓰는 표준 HMAC/서명 방식을 검토한다. 단순 해시는 관리자 변조 방지 증명이 아니다.

보존 초기 제안은 임시 IPC/응답은 처리 직후 폐기, 로컬 결정·보안 이벤트는 실행 종료 후 30일, 승인·산출물 출처 기록은 프로젝트 보존 정책에 따른 별도 기간이다. 실데이터 활성화 전 기간·암호화·백업·수동 정리 절차를 확정한다. 이 에이전트에 자동 삭제 도구를 추가하지 않는다. 완료 결과에 필요한 출처 기록을 임의로 정리하지 않는다.

신뢰한 pickle도 역직렬화는 코드 실행 위험이 있다. 원본 승인만으로 안전이 입증되지 않는다. ingestion은 네트워크·비밀 키·다른 프로젝트 파일 접근이 없는 제한 worker에서 수행한다. OS 격리가 준비되지 않으면 신뢰 출처의 합성 fixture 단계에 머물고 실데이터 실행을 보안 완료로 표현하지 않는다.

## 8. 호출·자원·비용 한도

| 항목 | 초기 설계 상한 | 초과 처리 |
| --- | --- | --- |
| 동시 실행 / 동시 provider 요청 | 각각 1 | 대기 또는 거부 |
| 선택 지점당 유효 선택 | 3 | 사용자 확인 |
| 동일 지점·상태·동작 | 1 | 반복 거부 |
| provider 재시도 | 요청당 1회, 일시 통신 오류만 | 규칙 모드 또는 중단 |
| 실행당 provider 시도 | 재시도 포함 18회 | 새 전송 금지 |
| provider timeout | 시도당 30초 | 늦은 응답 폐기 |
| 요청 / 응답 크기 | 정적 프롬프트 포함 8 KiB / 1 KiB | 송신 전·수신 중 차단 |
| 요청 입력 / 응답 토큰 | 2,048 / 128 | 입력 초과·응답 잘림 거부 |
| 진단 도구 실행 시간 | 호출당 120초 | worker 정지 확인 후 실패 |

크기·토큰 상한 모두 검사하고 실제 provider가 지원하는 제한을 검증한다. SDK 숨은 재시도는 비활성화한다. 응답 본문뿐 아니라 다운로드·스트리밍 수신량에도 제한을 적용한다. 제한을 맞추기 위해 보안 지시나 DTO를 잘라 보내지 않는다.

금액 한도는 provider와 통화·최대 요율을 선정한 뒤 반드시 지정한다. 각 호출 전에 입력·최대 출력 기준 비용을 예약하고 불명확한 과금은 최대치로 유지한다. 비용 산정 불가·provider 자동 전환·요율 검증 실패 시 호출하지 않는다. 기록된 사용량만으로 엄격한 청구 상한을 보장하지 않는다. 실행기 예약 한도와 provider 계정 한도를 함께 사용한다.

도구 I/O 재시도는 최초 포함 최대 3회이며 멱등성이 확인된 일시 실패에만 적용한다. 대용량 ingest·cache timeout·RAM·디스크는 소규모 측정 후 별도 유한 상한을 설정한다. 미설정 상태에서 실데이터 모드를 켜지 않는다. 지점 한도와 실행 전체 예산은 재개해도 초기화하지 않는다.

## 9. 비밀·프롬프트·의존성 관리

전용 API 키는 선택기에서만 읽고 최소 provider 권한·비용 제한·회전·폐기 절차를 적용한다. `.env`·환경 변수·키 저장소를 LLM 도구로 노출하지 않는다. SDK가 환경 변수로 trace·proxy·자동 upload를 켜는지 preflight와 격리 환경에서 검사한다. 무해한 마스킹 문자열도 민감 원문 전송의 대체 정책으로 사용하지 않는다.

프롬프트·도구 설명·최소 상태 매핑·동작 레지스트리·모델 버전은 코드 검토 대상으로 버전 관리한다. 사용자가 임의 JSON으로 프롬프트를 덮어쓰거나 도구 registry·import 경로·URL을 주입할 수 없게 한다. 외부 문서·원문 오류는 프롬프트에 추가하지 않는다. 자연어 system 지시는 보조 계층이며 권한 통제는 코드·OS에서 수행한다.

LangGraph·LangChain·provider SDK는 에이전트용 의존성으로 분리하고 버전 고정·취약점·라이선스·전이 의존성·telemetry를 검토한다. 설치·업데이트는 데이터 로드 전에 별도 사용자 작업으로 수행한다. 에이전트가 패키지를 자동 설치하지 않는다. provider·프롬프트·도구·보안 정책 변경 시 보안 회귀 검사를 다시 수행한다.

## 10. 로컬 관측·사고 대응

로컬 보안 이벤트는 고정 스키마로 `event_type`, actor·run·정책 버전, 결정 지점, 상태 버전, 후보·선택 ID, 승인 식별자, 허용/거부 코드, 비용·예산, 작업 결과·시각을 기록한다. 원본·배열·비밀 키·원문 provider 응답은 포함하지 않는다. 상세 품질 보고서는 별도 제한 파일이며 이벤트에 내용 복사 대신 참조만 둔다. 실제 이벤트도 외부 전송 금지다.

거부된 동작·승인 우회·의심스러운 egress·접근 권한 실패는 한 번이라도 실행을 잠근다. 단순 provider timeout은 제한 재시도 후 규칙 모드로 복귀할 수 있다. 감사 기록 저장 실패 시 새 작업을 시작하지 않고 로컬 실패 상태와 운영자 알림을 가능한 안전 경로로 남긴다.

사고 시 신규 요청·도구 예약 차단 → worker 정지 확인 → 선택기 네트워크 차단·키 폐기 → 로컬 증거 접근 제한 → 원인·영향 확인 → 새 승인·회귀 검사 후 재개 순서로 대응한다. 증거를 자동 삭제하거나 실제 데이터를 외부 지원 채널에 업로드하지 않는다. 원본을 변경하지 않으므로 이전 완료 버전을 보존한다.

## 13. 보안 검증과 활성화 조건

모든 fixture는 실제 데이터로부터 만들지 않은 독립 합성 입력이다. 원본 개인정보·공장 정보·비밀 키를 테스트 저장소에 넣지 않는다. 기본 테스트는 mock provider로 수행하고 실제 API 검증은 별도 승인 후 최소 계약만 사용한다.

| ID | 검증 사례 | 통과 기준 |
| --- | --- | --- |
| SEC-01 | metadata·오류·설정의 업로드/규칙 무시 지시 | DTO에 원문 0건, 금지 동작 0회 |
| SEC-02 | 금지 필드·중복 키·타입 혼합·원문 삽입 | 송신 전 거부, 외부 요청 0회 |
| SEC-03 | 서로 다른 원본이 같은 상태·후보로 매핑 | 정적 프롬프트·DTO·동적 헤더에 원본 차이 없음 |
| SEC-04 | 합성 canary를 원본·경로·예외에 삽입 | 본문·헤더·trace·proxy/crash 전송에서 canary 0건 |
| SEC-05 | LLM의 셸·삭제·경로·추가 인자·잘못된 사유 | 실행 0회, 거부 기록 |
| SEC-06 | blocker가 있는데 continue 선택 | 후속 처리·publish 0회 |
| SEC-07 | 만료·취소·다른 actor·대상/인자 변경 승인 | 작업 실행 전 거부 |
| SEC-08 | 동일 승인·응답 동시 제출·재개 재전송 | 작업 예약 최대 1회, 불확실 상태 자동 재실행 없음 |
| SEC-09 | 요청 중 상태·정책 변경·취소 | 늦은 응답 폐기, 취소 후 신규 실행 0회 |
| SEC-10 | 선택 반복·timeout·재시작으로 예산 초기화 시도 | 지점/전체 상한 유지, 규칙 복귀 또는 중단 |
| SEC-11 | 선택기의 실제 파일·checkpoint·다른 계정 접근 | OS 수준 거부, 단순 앱 예외만으로 통과 불가 |
| SEC-12 | 코어·SDK·하위 프로세스의 외부 접속 | 허용되지 않은 egress 0건, 실제 캡처 증거 |
| SEC-13 | checkpoint·승인·완료 표식 변조·기록 실패 | 재개/신규 작업 차단, 부분 결과 미등록 |
| SEC-14 | junction·UNC·경로 바꿔치기·미승인 pickle | 접근·역직렬화 거부 또는 안전 중단 |
| SEC-15 | 모드별 정상 완료·승인·재개 | 필수 계약·결정적 결과 일치, 진단 순서만 차이 |
| SEC-16 | trace 환경 변수·SDK 재시도·자동 provider 전환 | 자동 전송·숨은 재시도 차단 |

canary 검사·샘플 캡처만으로 모든 유출 부재를 증명하지 않는다. 계약 검사·OS 권한·네트워크 통제·적대적 테스트를 함께 통과해야 한다. 변조 방지 검증은 일반 해시와 인증 무결성의 차이를 구분한다.

### 구현 순서와 출시 게이트

분할 제안 전 `run_eda → review_eda`를 필수 로컬 단계로 둔다. `run_eda`는 `src.wafer_dl.eda.run_eda()`를 호출하고 실제 집계·예시 그림은 로컬 보고서에만 보존한다. `review_eda`는 사용자의 구조·품질 확인 게이트이며 EDA 실행 성공을 라벨·제외·분할 정책 승인으로 간주하지 않는다. EDA 완료 여부와 승인 기록은 로컬에서 관리한다. 현재 metadata EDA 어댑터의 등록·승인·실행기 연결을 합성 입력으로 검증했다. 예시 맵을 포함한 실데이터 연결과 LangGraph 노드는 후속 범위다.

`eda_complete` 반환은 로컬 상태일 뿐 provider DTO가 아니다. 현재 외부 상태·동작 열거값을 추가하지 않는다. EDA는 LLM 선택 없이 고정 순서로 실행하며, 집계·그림·경로를 LLM이나 LangSmith에 전송하지 않는다. 실패는 기존 로컬 중단·진단 정책을 따르고, 추후 외부 상태 매핑이 필요하면 별도 승인·전송 검증을 거친다.

1. 코어 ingest/audit와 내부 ToolResult 계약을 합성 입력으로 완성한다.
2. rules_only executor·승인·로컬 감사·멱등성·중단/재개를 구현한다.
3. 최소 매핑·DTO·응답 검증을 mock selector로 검증한다.
4. 프로세스/OS 격리·egress·비밀 키·provider 정책·예산을 확정한다.
5. SEC-01~16과 정상 회귀 검사를 수행하고 담당자가 결과·잔여 위험을 검토한다.
6. 정확한 계획에 LLM 모드를 승인한 뒤 bounded_llm을 활성화한다.

보안 증거에는 코드·정책·프롬프트·계약·provider/model 버전, OS 격리 구성, 실행한 사례·예상/실제 결과, 거부·예산·승인·네트워크 결과, 허용한 잔여 위험을 로컬에 보존한다. 실제 데이터 유래 증거는 자동 Git 업로드하지 않는다. CI에는 합성 fixture·기대 거부·정책 회귀 검사를 넣고 provider·프롬프트·도구·승인·메모리 정책 변경에 맞는 검증이 없으면 활성화 승인을 보류한다.

### 범용 구조 정비 결과와 남은 검토

기록일: 2026-10-15. 상태: **공통 입력·EDA·프로파일 계획 정비 및 합성 검증, 전체 범용 전처리는 진행 중**. 최초 목표와 기존 WM 중심 구현의 차이는 [설계 정렬 비교표](design/GENERIC_PREPROCESSING_DESIGN.md#1-최초-목표와-구현의-차이)에 기록했다. WM label·클래스·Lot·맵 저장 형식은 어댑터/도메인 코어에 두고, CSV와 WM metadata가 같은 공통 분석·실행기를 사용한다.

검토 방향은 공통 실행기 → 코드에 등록된 데이터 어댑터 → 도메인 EDA·전처리 코어다. 프로파일에는 컬럼 역할·라벨·그룹 기준·분석 옵션을 정의하고, 읽기 방식과 도메인 계산은 어댑터가 담당한다. JSON으로 임의의 함수명·모듈 경로·셸 명령을 실행하게 하지 않는다. WM 전용 기능을 공통 코어에 강제로 편입하거나 모든 데이터 유형을 한 분석에 맞추지 않는다.

- [ ] 전체 실데이터 실행·승인 화면·게시·보안 격리 연결.
- [ ] 표형 이외 원본 배열 계약·도메인 확장 등록 기준 검증.
- [ ] 어떤 어댑터에서도 원본·집계·그림·경로를 LLM/외부 추적으로 전달하지 않는지 검증.

실데이터 CLI·권한 격리·LLM 정보 축소 게이트는 아직 활성화하지 않는다. 새로운 프로파일 지원이 기존 외부 정보 전달 정책의 완화를 뜻하지 않는다.

### 후속 검토: 승인 DB 변조 방어

기록일: 2026-10-15. 상태: **검토 보류·미구현**. 현재 SQLite 구현은 동시성·트랜잭션·이력 저장을 제공하며, 악의적인 DB 변조에 대한 인증 무결성을 제공하지 않는다. 이번에는 검토 사항만 기록하고 코드에는 적용하지 않는다.

| 위험 | 가능한 영향 | 검토할 대처 |
| --- | --- | --- |
| 소비 상태 변경과 예약 삭제 | 동일 승인·작업 재사용 | 파일 ACL, 승인·예약 기록의 인증 무결성 |
| 만료 시각·사용자·대상·설정 변경 | 승인 범위를 벗어난 작업 허용 | 관련 필드를 함께 인증하는 HMAC 또는 서명 |
| 과거의 정상 DB로 교체 | 최근 소비·취소 이력이 사라져 재사용 가능 | DB 외부의 보호된 최신 버전 기록과 복구 정책 |
| DB 삭제·손상 | 승인 조회·예약 실패, 실행 중단 | 접근 제한, 검증된 백업과 수동 복구 절차 |

검토 우선순위는 Windows 계정·폴더 ACL 제한 → 인증 무결성 및 키 보관 방식 → 과거 버전 교체 탐지·복구 정책 순서다. HMAC 키는 DB와 분리하여 보호하고, 단순 SHA-256은 공격자가 재계산할 수 있으므로 변조 인증 수단으로 사용하지 않는다. 과거의 정상 DB는 HMAC 검사를 통과할 수 있어 HMAC만으로 되돌리기 공격을 탐지할 수 없다. 같은 실행 계정이나 관리자 권한이 장악된 경우의 한계도 함께 평가한다.

- [ ] DB 폴더의 수정 가능 계정과 Windows ACL 적용·검증 방식 결정.
- [ ] HMAC/서명 적용 범위, 키 생성·보관·교체·복구 방식 결정.
- [ ] 승인 상태와 작업 예약의 인증 정보를 동일 트랜잭션에서 갱신하는 방식 검토.
- [ ] 과거 DB 교체를 탐지할 외부 기준과 정상 백업 복구 절차 결정.
- [ ] 상태·대상·만료 시각 변경, 예약 삭제, 과거 DB 교체를 합성 입력으로 검증.
- [ ] 검증 실패 시 신규 예약 차단·보안 잠금·로컬 기록·사용자 확인 경로 연결.

실제 전처리 실행을 연결하기 전에 이 항목을 다시 검토한다. 완료 판단은 SEC-13의 변조·기록 실패 검증과 연계한다.

### 구현 전 확정해야 할 사항

- [ ] Windows 격리 수단·계정·파일 ACL·방화벽·IPC 구현 방식.
- [ ] provider/model·endpoint·요청 보관/학습 이용·로그 정책·비밀 관리.
- [ ] 실행당 금액 한도·유한 자원 한도·보존 기간·암호화/백업 정책.
- [ ] 실제 코어 검사 결과와 최소 상태 매핑의 정확성·지원하지 않는 오류 목록.
- [ ] 승인·audit 저장소 트랜잭션·무결성·장애 복구 방식.
- [ ] SEC-01~16 검증 증거와 제한적 추측 위험의 수용 여부.

최종 상태는 ‘상세 설계 완료, 구현·보안 준수 검증 미완료’다. 실제 처리의 자율성은 도구 선택에 한정하며 데이터에 대한 자율 분석·원본 접근·출하 판정으로 확대하지 않는다.
