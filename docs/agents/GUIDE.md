# 에이전트 문서 안내

갱신일: 2026-10-20. 문서를 처음 읽을 때와 현재 구현 상태를 확인할 때의 진입점입니다. 상세 계약·명령·과거 검증 이력을 분리하며, 소스나 실행 동작은 이 문서 정리로 변경하지 않습니다.

**현재 마감 기준:** CSV 등록 모듈·LLM 실행안의 사용자 승인 완료, WM 정상 개발 6단계 공통 UI, 로컬 결과 해설, B의 저장 EDA 제안 목록 복원·모델 목록 조회를 구현·기록했습니다. 최종 전체 합성 회귀는 **958개 실행·945개 통과·13개 생략·실패/오류 0**입니다. 아래의 940개·845개 회귀와 당시 “다음 단계”는 과거 이력이며 새 실행을 요구하지 않습니다. A·C의 추가 확장은 보류합니다.

## 먼저 읽을 문서

### 전처리 옵션 설명·처리 영향 미리보기·결과 보고서 개선 — 2026-10-22

- 계획 확인 화면에서 전처리 옵션마다 쉬운 이름·처리 내용·적용 대상·주의·사용하지 않을 때의 동작을 보여 줍니다. 진단 집계로 확인한 사실과 모델 의견을 나눠 표시합니다. 모든 전처리 방법은 질문과 관계없이 양식에서 고치거나 끌 수 있습니다(구간화 none 포함).
- 확정은 2단계입니다. "최종 계획 미리보기"로 질문 답변을 반영한 최종 계획·출처·사전 경고를 본 뒤 동의하고 "확인하고 진행"을 누릅니다. 양식 값과 답변이 충돌하면 자동으로 고르지 않고 사용자가 고릅니다. 서버는 미리 본 계획·시도·기록 revision과 같을 때만 확정합니다.
- Train 후보 계산에서 clipping 변경 값 수, 변환 후 상수 특징(정보 손실), 제거 사유, 구간화·원핫 출력 폭을 집계해 적용 확인(결정 D) 전에 보여 줍니다. 설정은 자동으로 바꾸지 않고, "적용하지 않고 계획 수정"으로 새 시도(새 동의 C)를 진행할 수 있습니다.
- 결과 보고서는 핵심 결과·주요 문제 / 컬럼별 처리·제외 사유 / 실제 전후 비교(실측과 예상 구분) / 정보 손실·미처리·미검증 경고 / 적용 구간과 결과 파일 활용 / 접힌 기술 상세로 구성합니다.
- 검증(합성 입력·모의 transport·모의 모델 응답): 대상 8개 모듈 134건 중 133건 통과·실패 1건(설계 변경 반영 누락 테스트, 수정 후 해당 4개 모듈 87건 모두 통과)·오류 0·생략 0. 독립 보안 검토 1차 CHANGES_REQUIRED(확정 5건) → 반영 후 재검토 PASS. 실제 AppContainer·실제 모델·실제 사용자 화면과 기존 실제 작업에서는 확인하지 않았습니다. 전체 회귀는 실행하지 않았습니다.
- 이 변경 전에 후보를 계산해 적용 확인에서 멈춘 작업은 처리 코드 지문이 달라 적용 단계에서 동의 D 발급 전에 차단됩니다(상태 변경 없음). "적용하지 않고 계획 수정"으로 새 시도를 진행하세요. 이전 형식 완료 보고서의 "보고서 다시 조립"도 같은 이유로 실패할 수 있습니다. 지금 완료한 검사를 다시 실행하라는 안내가 아니며, 기존 완료 작업을 재실행하지 않았습니다.

### 큰 작업 기록 분리 저장과 완료 기록 복구 — 2026-10-22

- 컬럼이 많은 작업의 진단·보고서 등 큰 내용은 별도 파일로 저장하고, 작업 기록에는 해시 참조를 남깁니다. 보고서를 포함해 기록이 커져도 완료 저장이 실패하지 않습니다.
- 모든 처리가 끝났는데 완료 저장만 실패한 작업은 화면의 "검증 후 완료 기록 복구"로 완료 처리할 수 있습니다. worker 재실행·새 승인은 없습니다.
- 실행 뒤 코드가 바뀐 로컬 전달 단계는 실행 당시 코드 지문이 동의·승인 기록과 같을 때만 읽기 전용으로 검증합니다. 실행 승인 검사는 그대로입니다.
- 실제 작업 `9b600512`: 검증 후 완료로 복구했습니다(작업 기록 revision 41). worker 실행 0, 새 승인 0이고, 로컬 전달 단계는 읽기 전용으로 검증했습니다. 보고서는 기존 report_2_1.md를 참조하며 해시 7249cb24…는 파일 바이트와 같습니다. 변경은 작업 기록과 새 분리 저장 파일 3개(진단·적용 대상·보고서)뿐이고, 전달 실행 폴더·보고서·그 밖의 작업 폴더 파일 해시는 복구 전과 같습니다.

### 답변 조합 충돌 안내 — 2026-10-21

- 구간화(binning)와 스케일링(scaling)처럼 함께 쓸 수 없는 답변을 고르면, 계획 확인 화면이 충돌한 질문 번호와 값을 보여 줍니다. 한쪽을 골라 다시 확인하면 됩니다.

### 범주 수 상한·시간 컬럼 확인과 후보 실패 후 계획 수정 — 2026-10-21

- **실행 전 질문:** 고유값이 원핫 범주 상한을 넘는 범주형 특징은 결정 화면에서 질문합니다. 반드시 실패하면 필수 질문입니다. 시각·날짜로 보이는 컬럼도 역할 확인 질문을 둡니다.
- **timestamp 역할:** 통합 작업은 시간 형식을 지정할 수 없어 timestamp 역할을 쓸 수 없습니다. 지정하면 실행 전에 필수 질문으로 알립니다.
- **후보 실패 후 진행:** 전처리 후보가 입력 문제로 실패하면 원인을 표시하고(worker 세부 코드로 확인됨 / 이전 기록은 추정), 계획 확인 화면에서 역할을 고쳐 새 시도로 이어 갈 수 있습니다. 이전 시도 기록과 사용한 승인은 보존됩니다.
- **검증:** 관련 테스트 통과, 독립 보안 검토 PASS.
- **코드 지문:** CSV·모듈 파이프라인·WM pickle import·사용자 검토 모듈 지문이 바뀌었습니다. 아직 실행하지 않은 해당 승인은 다시 준비해야 합니다.

### 넓은 표 지원·작업 기록 재조회·숫자형 식별자 — 2026-10-21

- **작업 기록:** 컬럼이 많은 작업(예: 592컬럼)의 기록을 다시 열 수 있습니다. 열지 못할 때는 원인별로 안내합니다.
- **넓은 표 권장안:** 모델 문맥 예산 안에서 컬럼을 상세·이름만·요약만으로 나눠 보내고, 결정 화면에 **모델 검토 범위**를 표시합니다. 요약만 보낸 컬럼은 모델이 역할을 권하지 않으며, 사용자는 역할 표에서 직접 바꿀 수 있습니다.
- **숫자형 식별자:** 행마다 다른 정수 ID(이름 단서나 연속 정수)도 식별자 안내 질문으로 표시합니다.
- **실패 진단:** 처리 실패 화면에 예외 종류와 단계를 표시합니다(원문 없음).

검증: 관련 211개 테스트 통과, 독립 보안 검토 PASS. 합성 SECOM형 592컬럼으로 기록 재조회부터 권장안·계획 확인까지 종단 테스트가 통과했습니다. 실제 로컬 모델로는 합성 넓은 표 요청이 예산 안에서 처리됐습니다. 실제 데이터는 다시 보내지 않았습니다. 품질 검토 간헐 실패는 원인을 아직 확인하지 못했습니다. 코드 지문이 바뀌어 진행 중인 작업은 새로 시작해야 합니다.

**실제 UI 확인 절차(UI 재시작 후)**
1. **일반 CSV:** 예전 Titanic 파일로 새 작업을 진행합니다.
   - 결정 화면에 `로컬 LLM 권장안`과 "모델 검토 범위: 상세 N개"(요약 0)가 나오는지 봅니다.
   - target이 정해졌는지, 없으면 [필수] target 질문이 나오는지 봅니다.
   - `PassengerId`에 숫자형 식별자 질문이 나오는지 봅니다.
   - 완료한 뒤 최종 결과의 처리 내용에서 target을 확인합니다.
2. **넓은 표(기록 재조회):** 이전 작업 `e6ac6cca…`를 화면에서 다시 열 수 있는지 봅니다. 이전 형식이라 계획 화면에 검토 범위 표시는 없습니다.
3. **넓은 표(권장안 경로):** SECOM CSV로 **새 작업**을 진행합니다(이때 로컬 모델에 새로 보내는 것은 사용자가 직접 진행합니다).
   - 결정 화면에 "모델 검토 범위: 상세 a · 이름만 b · 요약만 c"가 나오는지 봅니다.
   - 권장안 출처(로컬 LLM 권장안 / 기본 계획(사유))와 target 질문 처리를 확인합니다.
   - 계획 확인 → 적용 화면의 후보 수치가 "미집계"가 아닌지 봅니다.

### 로컬 LLM 권장안 거부 줄이기: 허용 값 전달·응답 형식 고정 — 2026-10-21

모델이 허용 값 밖의 값을 권해 권장안 전체가 버려지던 문제를 줄였습니다. 예: 실제 작업에서 `outlier="iqr"`. 모델에 경로별 허용 값을 함께 보내고, 응답 형식에서 경로별 값 형태를 고정했습니다. 검증과 전체 거부 규칙은 그대로이고, 모델에 보내는 자료 범위도 같습니다(코드 상수만 추가). 요청이 너무 크면 보내지 않고 별도 사유 코드를 남깁니다.

검증: 영향 46개 테스트 통과, 독립 보안 검토 PASS. 실제 로컬 모델로 다시 확인한 결과, 이번 작업 데이터와 합성 4사례 중 3건이 권장안을 받았습니다. 그룹 사례는 내용 오류로 거부됩니다. 컬럼이 약 160개를 넘으면 권장안 없이 기본 계획으로 진행합니다. 코드 지문이 바뀌어 진행 중인 작업은 새로 시작해야 합니다. [세부 기록](design/CSV_TASK_AGENT.md#716-권장안-허용-값-전달응답-형식-고정--2026-10-21)을 참고하세요.

### 예측 목적에서 target 없이 확정되지 않도록 보완 — 2026-10-21

계획 확인 화면에서 target이 정해지지 않았으면 target 질문이 **필수**로 표시됩니다. 후보 컬럼을 고르거나, 예측 목적이 아니면 "예측 대상 없음"을 골라야 확정할 수 있습니다. 후보를 고르면 그 컬럼의 역할 하나만 target으로 바뀝니다. "예측 대상 없음"을 고르면 최종 보고서 주의사항에 표시됩니다.

검증: 목표 "생존여부 확인 위한 데이터 전처리 수행"과 `2urvived` 컬럼으로 만든 합성 재현 테스트가 통과했고, 관련 테스트와 독립 보안 검토(PASS)도 마쳤습니다. 품질 검토 테스트 1건이 간헐적으로 실패하며 원인은 확인하지 못했습니다. 실제 관리자 UI 확인은 남아 있습니다. 코드 지문이 바뀌어 진행 중인 작업은 새로 시작해야 합니다. [세부 기록](design/CSV_TASK_AGENT.md#715-예측-목적의-target-미지정-확정-방지--2026-10-21)을 참고하세요.

### 중복 컬럼명 정비 보완: 작업 복사본 기준·이력·사전 검사 — 2026-10-21

정비는 작업을 시작할 때 만든 검증된 복사본으로만 합니다. 그 뒤 원본 파일을 옮기거나 지우거나 바꿔도 이어서 진행할 수 있습니다. 복사본이 변조되면 계속 막습니다. 해결할 수 없는 요청은 새 동의를 만들기 전에 거부합니다. 정비 전후 실행·동의·복사본 해시의 연결은 작업 기록 이력에 남습니다.

검증: 관련 18개 모듈 199개 통과(실패 0·오류 0), 독립 보안 검토 PASS. 실제 사용자 CSV(같은 이름 19개 컬럼, 1309행)로 정비 → 로컬 LLM 권장안 → 적용 → 최종 결과까지 완료했습니다(작업 `2cd002c9…`). 다만 그 작업은 수정 전에 시작한 UI 서버로 실행된 것으로 보여 정비 이력이 남지 않았고, 이력 기능의 실제 환경 확인은 남아 있습니다. 코드가 바뀐 뒤에는 UI를 다시 시작하세요. [세부 기록](design/CSV_TASK_AGENT.md#714-중복-컬럼명-정비-보완작업-복사본-기준이력사전-검사--2026-10-21)을 참고하세요.

### 통합 작업: 중복 컬럼명 파일 이어서 진행 — 2026-10-21

통합 작업에서 같은 컬럼명이 여러 번 쓰인 CSV로 진단이 막히면, 화면에 중복 이름 수와 영향 컬럼 수가 표시됩니다. 여기서 `번호 붙인 복사본으로 진행`을 동의와 함께 누르면, 원본은 그대로 두고 중복 이름에만 번호를 붙인 작업용 복사본을 격리 실행으로 만들어 진단·권장안부터 이어 갑니다. 빈 컬럼명이나 읽을 수 없는 헤더는 자동으로 고치지 않습니다.

검증: 관련 18개 모듈 193개 통과(실패 0·오류 0), 독립 보안 검토 PASS. 합성 입력과 모의 실행 결과이며, 실제 사용자 파일로는 아직 다시 확인하지 않았습니다. 코드 지문이 바뀌었으므로 막혔던 작업은 새 작업으로 다시 시작해야 합니다. [세부 기록](design/CSV_TASK_AGENT.md#713-통합-작업의-중복-컬럼명-정비-연결--2026-10-21)을 참고하세요.

### 범용 작업 구조 G1: 공통 핵심 + 표형 어댑터 — 2026-10-21

사이드바 메뉴 이름이 `통합 작업`으로 바뀌었습니다. 조정기·동의·작업 기록·질문·보고서·화면은 공통 코드가 맡고, CSV 처리는 표형 어댑터가 맡습니다.
- 모델 권장안은 기본 계획에서 바꿀 항목만 받습니다. 하나라도 계약을 어기면 권장 변경 전체를 버리고 기본 계획을 씁니다.
- 결정 화면은 질문을 보여 줍니다(필수/안내). 예: 분할 방식 미정, 식별자로 보이는 범주형 컬럼, target 모호성. 답변 하나는 해당 항목 하나만 바꿉니다.
- 적용 전 후보는 구조화된 표로 보여 주고, 실패하면 확인된 worker 분류와 추정 원인을 나눠 안내합니다.
- 위임 범위는 확정 계획에서 계산합니다.

검증: 관련 18개 모듈 189개가 통과했습니다(실패 0·오류 0). 보안 지적 반영 후 영향 테스트를 다시 실행했고, 도메인 없는 합성 배열 어댑터가 같은 공통 경로로 끝까지 진행되는 것을 확인했습니다. 독립 보안 검토는 지적 반영 후 재검토 PASS입니다. 실제 로컬 모델은 합성 4사례에 4회 호출해 2건이 권장안 계약을 통과했습니다. 실패했던 일반 CSV 사례도 통과했습니다. 실제 관리자 UI·로컬 모델·격리 실행으로 합성 일반 CSV 한 건이 권장안 사용부터 내용 있는 최종 결과까지 완료됐습니다(작업 `542b5538…`, 권장 변경 5건 채택). 실데이터·다른 CSV 형태와 전체 회귀는 확인하지 않았습니다. CSV·모듈 파이프라인 코드 지문이 바뀌어, 아직 실행하지 않은 승인과 진행 중인 통합 작업은 새로 준비해야 합니다. 기존 완료 작업을 재실행하라는 안내가 아닙니다. [G1 구현 기록](design/CSV_TASK_AGENT.md#712-g1-구현-기록--2026-10-21)을 참고하세요.

### 범용 전처리 에이전트 구조 재설계(설계안, 미구현) — 2026-10-21

목표를 CSV 전용 작업에서 범용 전처리 에이전트로 정정하고 설계를 갱신했습니다. 코드는 바꾸지 않았습니다.
- 현재 통합 작업은 보안 기반은 적합합니다. 다만 조정기·동의 표·권장안 계약·보고서·화면이 CSV에 고정돼 있어 목표에 맞지 않는다고 판정했습니다.
- 계획 계약(`validate_workflow_proposal`·`bind_workflow_step`)도 실제로는 CSV 전용입니다. 명세 형식만 일반화해 씁니다.
- 새 구조의 공통 핵심이 맡는 것: 계획 확정·전체 검증, 질문·답변, 위임 범위 계산, 문제 처리, 보고서, 화면.
- 입력 유형 어댑터가 맡는 것: 로딩·진단·결정 항목·결과 요약. CSV 전용 규칙은 표형 어댑터 안의 CSV 로더에 둡니다.
- 권장안 계약: 모델은 기본값과 다른 항목만 이유와 함께 권하고, 합친 계획 전체를 검증합니다. 하나라도 실패하면 권장 변경 전체를 버립니다.
- 질문 답변: 답변 하나는 해당 항목 하나만 바꾸고, 답변을 반영한 계획을 다시 검증합니다.
- 공통 계층은 표형과 배열·이미지 두 데이터 형태를 기준으로 둡니다. WM은 데이터 유형이 아닙니다. 웨이퍼 처리는 배열 형태 위의 도메인 프로파일과 기존 전용 모듈(`wm_*`, `src/wafer_dl`, 계산 코드 보존)로 두고, WM-811K는 `waferMap`·`failureType`·`lotName`을 표본·라벨·그룹으로 바꾸는 입력 매핑으로 둡니다. 공통 조정기·화면은 WM 이름·필드·단계를 쓰지 않습니다.
- 공통성 검증: 테스트 전용 합성 배열 어댑터(도메인 프로파일 없음)로 확인합니다.

다음 단계는 G1(공통 핵심 + 표형 어댑터 구현, 흐름 결함 3건 포함)입니다. G2(배열 형태 + 웨이퍼 프로파일 연결)에서 웨이퍼 모듈의 위임 발급 위치를 결정합니다. 이 절은 설계안이며 구현이나 검증 완료를 뜻하지 않습니다. [재설계 7절](design/CSV_TASK_AGENT.md#7-범용-전처리-에이전트-구조-재설계--2026-10-21-설계안-미구현)을 참고하세요.

### 초안·확인 검사 코드의 지문 포함 — 2026-10-21

`llm_task_assist.py`는 동의 C 발급 전 검사를 맡습니다. 이 파일을 CSV `code_id`와 모듈 파이프라인 코드 지문에 넣었습니다. 아래 "역할×분할 교차 검사" 절에 남긴 지문 결정 항목은 이 절로 해소합니다. 지문이 다시 바뀌었으므로, 아직 실행하지 않은 CSV·모듈 파이프라인 승인과 진행 중인 통합 작업은 새로 준비해야 합니다. WM 작업은 그대로이고, 기존 완료 작업은 재실행하지 않습니다.

### 역할×분할 교차 검사·time 미지원 처리·모호한 target 표시 — 2026-10-21

`통합 작업 (CSV)`에서 역할과 분할 방식의 조합을 공통 함수 하나로 검사합니다. 초안 검증, 결정 화면, 서버의 사용자 확인이 모두 같은 함수를 씁니다. time 분할은 미지원으로 명시합니다. 화면에서는 선택지가 없고, 모델이 제안하면 초안 전체를 거부합니다. random으로 자동 대체하지 않고, 분할 방식을 비워 두어 사용자가 직접 고르게 합니다. 목표 문장과 target 지정이 맞물리지 않으면 결정 화면에 확인 사항으로 표시합니다. 검증 완화나 부분 채택은 없습니다.

WM 작업 지문은 그대로입니다. 기존 완료 작업을 재실행하라는 안내가 아닙니다. [세부 기록](design/CSV_TASK_AGENT.md#54-역할분할-교차-검사time-미지원-처리모호한-target-표시--2026-10-21)을 참고하세요.

### 로컬 LLM 권장안 지시문 보강·거부 사유 코드 — 2026-10-21

`통합 작업 (CSV)`의 로컬 LLM 초안 지시문에 역할 의미, 분할 제약, 실제 기본값을 넣었습니다. 모두 기존 계약 코드에서 생성합니다. 초안 거부 사유는 오류 원문 없이 고정 코드 7종으로 기록하고 화면에 표시합니다. 검증 조건과 모델에 보내는 자료는 바뀌지 않았습니다. 실제 모델로 합성 4사례를 비교한 결과, 계약 통과는 이전 지시문 0/4에서 개선 지시문 3/4로 늘었습니다. 일반 사례는 여전히 거부되어 기본 초안을 씁니다. 역할이 기대값과 일치한 것은 통과 3건 중 1건이고, 기대값이 없는 사례가 1건입니다.

### CSV 통합 작업 결과 보고서 개편 — 2026-10-21

`통합 작업 (CSV)`의 최종 결과는 이제 문제점, 처리 내용, 전후 비교, 분할 EDA 그래프, 주의사항, 결과 파일을 보여 줍니다. 값은 각 단계의 검증된 결과 파일에서 재계산 없이 가져오고, 없는 수치는 "미집계"로 표시합니다. 경로·해시·내부 작업명은 접힌 기술 상세로 옮겼고, LLM은 쓰지 않습니다. 결정 D의 적용 구간 안내를 실제 계약(Train·Validation 적용, Test 미적용)에 맞게 고쳤고, 승인 전 전체 설정 표와 LLM 초안 사용 여부 표시를 추가했습니다. 이전 형식 보고서가 있는 완료 작업은 결과 화면의 `보고서 다시 조립`으로 새 보고서를 만들 수 있습니다. 실행·승인·모델 호출·덮어쓰기는 없습니다.

검증: 대상 테스트 16개 통과(실패 0·오류 0). 독립 보안 검토는 불확실 위험 3건 반영 후 재검토 PASS이고, 낮은 위험 1건이 남아 있습니다. 합성 CSV와 모의 실행 결과이며, 관리자 UI 실제 화면과 전체 회귀는 확인하지 않았습니다. 지금 완료한 작업을 재실행하라는 안내가 아닙니다. [보고서 개편 기록](design/CSV_TASK_AGENT.md#52-통합-결과-보고서-개편--2026-10-21)을 참고하세요.

### CSV 지속 작업 P1: 통합 작업 화면 — 2026-10-20

사이드바 `작업 시작 방식` → `통합 작업 (CSV)`에서 CSV 파일과 목표를 입력하고 작업 동의(A)를 체크하면 다음 순서로 진행합니다.
- 격리 진단 → 로컬 LLM 권장안
- 역할·처리안 확인(B·C, 한 화면) → 분할 → 내보내기 → Train 기준 전처리 후보
- 적용 확인(D) → 적용 → 로컬 전달 묶음 → 통합 결과 보고서

내부 작업 이름·경로·선행 결과는 조정기가 연결합니다. 각 단계의 1회 승인은 동의 범위와 정확히 맞을 때만 위임 발급하며, 이 발급은 직접 확인 기록과 구분됩니다. 모델에는 목표 문장과 컬럼명·집계만 보내고 원본 행·개별 값은 보내지 않습니다. 기존 5단계 화면은 그대로 둡니다.

### 관리자 UI의 모듈 파이프라인 출력 폴더 권한 보완 — 2026-10-20

관리자 UI에서 입력 진단을 실행하면 `ACL_OUTPUT`·`OWNER_MISMATCH`로 worker 시작 전에 실패했습니다(`input-profile-fcd81425306948c5`). 승격된 관리자 토큰이 만든 새 작업 폴더의 소유자가 사용자 대신 `BUILTIN\Administrators`였고, 기존 검사는 사용자 소유만 허용했기 때문입니다. 실패 기록은 보존하며, 소비된 승인과 실패 작업은 재사용하지 않습니다. 같은 원인으로 관리자 UI의 3·4번 EDA 실행도 실패했을 것으로 보지만 재현하지는 않았습니다.

`writable_directory_acl.py`에 예외를 하나 추가했습니다. 다음을 모두 만족할 때만 Administrators 소유 폴더를 허용합니다.
- 실제 토큰이 승격됨(TokenElevation)
- 토큰의 기본 소유자가 Administrators(TokenOwner)
- 폴더 소유자도 Administrators
- 사용자가 일반 계정 SID(`S-1-5-21-`)

변하지 않은 것:
- WO는 Administrators 그룹이 아니라 현재 사용자 SID에만 부여합니다.
- 대상은 해당 작업의 빈 `output/result`·`scratch/task`뿐입니다.
- 링크·junction, 기존 폴더, 다른 소유자, SYSTEM·서비스 계정은 계속 거부합니다.
- worker 권한은 기존 `M`·Low 그대로입니다.

검증: 관련 43개 모듈 **442개 실행: 442개 통과·0개 생략, 실패 0·오류 0**입니다. 이 회귀는 마지막 보완(TokenOwner·계정 조건) 전에 시작했으므로, 보완 후 ACL·운송·진단 관련 65개를 다시 실행해 모두 통과했습니다. 독립 보안 검토 PASS(보완 2건 반영 후 재검토 PASS)입니다. 경로 문자열 기반 검사의 시점 차이(TOCTOU)는 이전부터 있던 한계로 후순위에 기록했습니다. 승격 토큰 경로는 모의 값으로만 검사했습니다. 실제 관리자 UI 재실행, Low 레이블 설정 성공, AppContainer 쓰기 동작은 아직 확인하지 않았습니다. 이 파일은 모듈 파이프라인 코드 지문에 포함되므로 아직 실행하지 않은 모듈 파이프라인·진단 승인은 새 작업으로 다시 받아야 합니다. 다른 18종 실행 체계의 코드 식별값은 바뀌지 않았습니다. 기존 완료 작업을 재실행하라는 안내가 아닙니다.

### 최신 UI 연결 범위 — 2026-10-19

현재 **CSV 품질·EDA** 경로는 요청 대화부터 제안 검토·저장, 입력 선택, 실행 후보 준비, 사전 검사, 별도 승인, 격리 실행, 로컬 결과 확인까지 연결했습니다. 아래 날짜별 초기 구현의 ‘승인·worker 미연결’ 설명은 당시 기록입니다. WM canonical 이후 작업과 CSV 분할·변환·전달은 등록 모듈 경로로 연결했습니다. CSV 후속 작업의 3.12 실행은 위 지원 제한을 확인하세요. 일반 이미지 입력·pickle 격리 변환의 생성 UI는 아직 미연결입니다. 정보 전달 정책·결과 해설은 결과 해설 목적에 한해 연결했습니다(위 후속 범위 표 참고). 기존 도메인 CLI의 지원 여부와 구분합니다.

UI 실행 단계는 다음과 같습니다.

1. 3번에서 입력 결합 미리보기와 작업 준비에 동의하고 새 이름으로 **실행 후보 생성**을 누릅니다.
2. 4번에서 **작업 시작·승인 지점까지 진행**을 누릅니다. 사전 검사와 승인 범위 준비는 자동 진행하며 승인 없이 worker를 시작하지 않습니다.
3. 화면에 표시된 현재 입력·모듈·품질 기준·코드·자원을 확인합니다.
4. 확인 체크 후 **승인하고 실행**을 누릅니다. 현재 단계의 일회 승인 저장·실행까지 이어지고 다음 승인 지점에서 멈춥니다. 기존 AppContainer·Job 실행기에 연결하고 범위 변경·승인 만료·중복 소비는 거부합니다.
5. 5번에서 상태를 조회하고 **로컬 결과 검사·열기**를 누릅니다. 품질 검토 중단이면 후속 EDA를 실행하지 않고 품질 보고서만 표시합니다. 실패·부분 결과를 완료로 표시하지 않습니다.

`ui/execution_service.py`는 작업 범위를 고정하고 동일 revision의 명령 중복과 예외 후 재시도를 차단합니다. `pipeline_approval_cli.preview_approval`·`record_approval`은 CLI와 UI가 공유하는 승인 경계입니다. 터미널은 확인 문자열, UI는 해당 범위의 명시적 확인 폼을 사용하지만 입력·코드 재검사, revision, 실행 잠금, 승인 DB·범위 검증은 유지합니다. UI가 승인 DB에 직접 SQL을 쓰지 않습니다.

화면 갱신·단계 이동은 작은 상태 JSON만 읽으며 모델 호출·승인 저장·worker 실행을 반복하지 않습니다. 실제 명령과 결과 열기에서 전체 계약을 재검사합니다. 작업 실행은 현재 동기 호출이며 처리 중에는 기다려야 합니다. **백그라운드 진행·실행 중 취소·재접속 복원은 미구현**입니다. 창 닫기나 새로고침을 안전한 취소 명령으로 해석하지 않습니다. 실패·중단 시 디스크 기록을 확인하고 새 작업을 준비하며 자동 재시도하지 않습니다.

이미 시작한 작업 연결은 입력·모델 설정 변경과 독립적으로 세션에 보존하므로 5번에서 이전 상태를 볼 수 있습니다. 이는 새 범위에 이전 승인을 재사용한다는 뜻이 아닙니다. 서버 재시작 시 메모리 연결은 사라지지만 기존 작업·소비 승인은 삭제하지 않습니다.

`ui/result_service.py`는 성공 작업의 DB 커밋·완료 표식·파일 해시·결과 계약을 검사합니다. 검토 중단은 별도 품질 결과 계약으로 확인하고 완료 커밋으로 취급하지 않습니다. 링크를 거부하고 파일 128개·개별 8 MiB·표시 자료 합계 32 MiB로 제한합니다. 자동 검증은 `tests/agents/test_ui_execution.py`의 승인·실행·결과 연결과 기존 UI·snapshot·제안 저장·후보 준비 회귀를 사용합니다. 실제 Streamlit AppTest, 모의 모델·worker, 합성 데이터만 사용하며 실제 Ollama 호출·AppContainer 실행은 포함하지 않습니다. 신규 검증은 승인 전 미실행, 승인/실행 확인 분리, 중복 실행·중복 발급·범위 변경·만료·중단 재시도·결과 변조 거부, 품질 검토 중단·결과 열람·새로고침 미재실행을 다룹니다.

### 로컬 Qwen 연결 — 합성 제안 호출과 질문 지침 보완

2026-10-18 사용자 환경에서 Ollama `qwen3.5:9b` 설치와 Python `ollama.chat`의 합성 한국어 응답을 확인했습니다. 이후 LangChain 계열·LangGraph·LangSmith 설치와 import를 확인했습니다. LangChain 모델 어댑터의 실제 합성 제안 성공을 확인했고, LangGraph 질문·답변 흐름은 모의 응답으로 검증했습니다. 실제 데이터 해설은 연결하지 않았습니다.

`src/agents/llm_proposal_contract.py`는 모델 응답을 `llm_proposal_v1` JSON으로 검사합니다. 필드는 `schema_version`, `status`, `pipeline`, `questions`만 허용합니다. `proposed`는 기존 표형 또는 WM 계획 형식을 사용하며, `needs_clarification`은 `pipeline: null`과 확인 질문만 반환합니다.

- 로컬 호출자가 정한 논리 입력 계약과 해당 요청의 모듈 ID·정확한 버전 허용 목록을 따릅니다. 모델이 입력·권한 범위를 정하지 않습니다.
- 기존 등록·설정·포트·순서 검증을 재사용하며, 표형 분석·변환·보고는 선행 품질 검사에 의존해야 합니다.
- 중복 JSON 키·비표준 숫자·64 KiB 초과 응답·추가 승인/명령 필드를 거부합니다. 설명문에서 JSON을 임의 추출하지 않습니다.
- 정적 계약 통과는 실제 입력의 품질·사용자 의도 충족·실행 안전성·사용자 승인을 보증하지 않습니다. 질문과 설명도 신뢰할 수 없는 모델 출력입니다.
- 계약 검사 함수 자체는 모델 호출·원본 읽기·승인 발급·worker 실행을 하지 않습니다. 별도 합성 제안 호출부를 연결했으며 실제 모델 제안 품질은 사용자 터미널에서 확인합니다.

`llm_config.py`는 `configs/agents/llm/local_ollama.json`을 읽습니다. `local_ollama.py`는 검증된 loopback 주소의 Ollama HTTP API에 한 번만 요청하고, `llm_proposal.py`는 공개 명세와 요청 문장을 구성한 뒤 응답을 기존 계약으로 검증합니다. `llm_proposal_cli.py`는 미리보기·제안과 별도 확인을 받는 로컬 보관·복원을 제공합니다. 데이터 파일 입력·분석 결과 저장·실행 기능은 없습니다. 표형 품질·결측·상관 모듈 3개에 대해 합성 요청 3종 또는 사용자가 직접 작성한 문장을 지원합니다. WM 제안·기능별 데이터 공개는 후속 범위입니다.

#### LangChain 모델 연결 — 기존 운송 보호 재사용

`src/agents/langchain_local.py`의 `LocalProposalChatModel`은 [LangChain BaseChatModel](https://reference.langchain.com/python/langchain-core/language_models/chat_models/BaseChatModel)의 `_generate`·`_llm_type`을 구현한 프로젝트용 모델 어댑터입니다. `ChatOllama` SDK의 별도 HTTP 운송으로 교체하지 않고 기존 `request_local_proposal`을 호출하므로 목적지 고정·프록시 무시·리다이렉트 거부·응답 크기·중복 JSON 키·모델 일치·완료 응답 검사를 재사용합니다. 메시지 변환이나 LangChain 도입을 이유로 보호 규칙을 생략하지 않습니다.

흐름은 `기존 문장·공개 명세 구성 → LangChain invoke → 프로젝트 _generate → 기존 로컬 HTTP → AIMessage → 기존 제안 검증`입니다. 모델명·생성 옵션은 기존 JSON 설정을 그대로 사용합니다. 첫 단계는 단일 요청의 모델 인터페이스 연결이며 LangGraph 다중 턴·도구 실행·새 승인 기능이 아닙니다.

기존 기본값은 `--backend http`이며 새 경로는 `--backend langchain`으로 명시합니다. 실패하면 기본 경로로 자동 전환하지 않습니다. 미리보기는 LangChain을 import하거나 모델을 호출하지 않습니다. 추가 의존성이 없으면 고정 오류로 중단합니다. 현재 의존성은 루트 `requirements.txt`로 통합했으며 전체 전이 의존성의 완전한 잠금 파일은 아닙니다. 과거의 별도 에이전트 requirements 설치 안내 대신 통합 파일을 사용합니다.

```powershell
python -m src.agents.llm_proposal_cli --example missing --backend langchain --preview

python -m src.agents.llm_proposal_cli `
  --example missing --backend langchain --confirm-local-model-call
```

직접 문장·별도 저장 확인도 기존 옵션과 조합할 수 있습니다. 저장된 제안 복원에는 모델 연결이 필요 없으므로 `--load-name`과 새 backend 옵션을 함께 사용하지 않습니다. 저장·실행 후보·승인·worker·결과 검증 코드는 이번 단계에서 변경하지 않았습니다.

호출은 새 `Context()`에서 수행하여 외부 Runnable 콜백 문맥을 상속하지 않고, `tracing_context(enabled=False, parent=False)`로 추적을 끕니다([LangSmith 추적 제어](https://kb.langchain.com/articles/2491399069-how-do-i-disable-or-toggle-langsmith-tracing-during-execution)). 캐시는 사용하지 않습니다. 전역 디버그·상세 출력 또는 추가 콜백이 감지되면 호출 전 거부하며 환경 변수나 전역 설정을 바꾸지 않습니다. 이는 신뢰된 프로젝트 호출부의 제어이지 같은 프로세스의 임의 악성 Python이나 Ollama 서버의 외부 통신을 차단하는 OS 경계는 아닙니다. 모델 호출 자체는 AppContainer 밖의 제안 계층에서 수행합니다.

검증: `python -m unittest tests.agents.test_langchain_local tests.agents.test_llm_proposal tests.agents.test_llm_proposal_contract -q` — 42개 통과. 실제 LangChain 모델 인터페이스를 사용하고 HTTP 운송은 모킹하여 한 번 호출·설정 보존·부모 콜백 비상속·추적 비활성화·디버그 차단·허용 메시지·추가 도구 거부·오류 원문 비공개·계약 재검증·CLI 선택을 확인했습니다. 실제 Qwen 응답은 위 합성 명령으로 사용자가 별도 확인합니다. 기존 HTTP의 합성 실행 성공과 새 LangChain의 실제 모델 호출 성공을 혼동하지 않습니다.

기존 제안 저장·복원·실행 후보·승인 테스트까지 확장한 관련 회귀는 총 66개 통과했습니다. 임시 폴더·SQLite 사용을 허용받아 실행했으며 실제 모델·네트워크·AppContainer worker는 호출하지 않았습니다. 전체 에이전트 테스트 전체집합의 재실행은 아닙니다.

사용자 실행에서는 `--example missing --backend langchain`이 품질 `q1` → 결측 `m2` 의존성을 갖는 실행안을 반환하여 `proposal_validated`를 확인했습니다. `execution_approved: false`, `worker_started: false`로 전처리 실행은 하지 않았습니다.

#### LangGraph 확인 질문·답변 연결

`src/agents/llm_dialogue.py`는 `StateGraph`의 `propose → clarify → propose` 순환을 관리합니다. `propose`는 기존 LangChain 경로와 제안 계약을 호출하고, 유효한 제안이면 종료합니다. 질문이 필요하면 `clarify`의 `interrupt()`에서 멈추며 다음 답변을 `Command(resume=...)`로 전달합니다([LangGraph interrupt](https://reference.langchain.com/python/langgraph/types/interrupt)). 중단된 노드는 재개 시 처음부터 실행되므로, 그 노드 안에서는 모델 호출·파일 저장을 하지 않습니다.

- `InMemorySaver`는 한 프로세스 안에서 생성한 기본 자료형 상태만 보관합니다. 외부 checkpoint를 읽지 않고 DB·파일에 대화를 자동 저장하지 않습니다. 프로세스를 닫으면 대화를 복원하지 못하며 메모리의 보안 소거까지 보증하지 않습니다. 현재 API는 단일 터미널의 순차 사용 범위이며 다중 사용자 서비스가 아닙니다.
- 최초 사용자 요청·검증된 질문·사용자 답변을 하나의 사용자 메시지 안에 대화 자료로 묶습니다. 데이터·통계·그림·로컬 작업 기록을 자동 첨부하지 않습니다. 매번 전체 누적 문장이 기존 4000자·UTF-8 8 KiB 제한을 만족해야 합니다.
- 최초 호출 포함 최대 4회(답변 재개 최대 3회)입니다. 계속 모호하면 `clarification_limit_reached`로 종료하고 자동으로 다시 질문하거나 호출하지 않습니다. 회수 제한은 정확한 제안이나 의미적 일치를 보장하지 않습니다.
- 그래프와 모델 모두 `run_unobserved`를 사용하여 추적·부모 콜백 비상속 규칙을 적용합니다. 전역 디버그·추가 콜백은 거부합니다. 원문·오류를 외부 추적 시스템으로 보내지 않습니다.
- 모델·계약 실패나 통신 중단 후에는 세션을 닫고 재시도하지 않습니다. 사용자 입력이 길이 제한을 넘으면 다음 호출 전에 거부합니다. 질문 답변·`SEND`·메모리 checkpoint는 실행 승인이 아닙니다. SQLite 승인·AppContainer worker는 그래프의 노드로 넣지 않았습니다.

`src/agents/llm_dialogue_cli.py`는 같은 터미널에서 문장 입력·누적 전송 미리보기·매 호출 `SEND` 확인·질문 답변을 제공합니다. 다음 명령에서 첫 질문을 확인한 뒤 예를 들어 “품질 검사 후 결측률을 확인해 주세요. 데이터는 변경하지 마세요.”라고 답하고 다시 전송 내용을 확인합니다.

```powershell
python -m src.agents.llm_dialogue_cli --example clarify
```

직접 요청은 `--interactive-request`, 완성 제안의 선택적 저장은 `--save-name dialogue_eda01`처럼 새 영문 ID를 사용합니다. 저장에는 별도 `SAVE` 확인이 필요하며 기존 저장 계약을 재사용합니다. 질문만 있거나 호출 상한에 도달하면 저장하지 않습니다. 저장 후의 입력 선택·실행 후보·사용자 승인은 기존 CLI의 별도 절차입니다. 모델 질문은 신뢰된 안내가 아니므로 원본·통계·비밀정보를 요구하면 응답하지 말고 취소합니다.

자동 검증: `python -m unittest tests.agents.test_llm_dialogue tests.agents.test_langchain_local tests.agents.test_llm_proposal tests.agents.test_llm_proposal_contract -q` — 55개 통과. 실제 LangGraph 중단·재개와 메모리 checkpointer를 사용하고 모델 운송은 모킹했습니다. 문맥 유지·이전 모델 호출 비반복·회수/누적 크기 제한·세션 분리·반환 객체 변조 비전파·취소·전송 확인·추적 비활성화·오류 후 재개 금지를 검사했습니다. 실제 Qwen 다중 턴 응답은 사용자 실행으로 별도 확인합니다.

#### 로컬 UI 형태 확정 — 단계 안내형

2026-10-18 사용자는 화면 시안의 **단계 안내형(첫 번째 안)**을 선택했습니다. 대화 중심형은 첫 구현 대상으로 채택하지 않습니다. 이후 모델 제안·파일 선택·승인·worker·결과 확인을 공통 UI에 연결했으며 현재 완료 범위는 문서 상단을 따릅니다.

주 작업 화면은 다음 순서로 구성합니다.

1. 요청·대화: 요청 입력·전송 확인·필요한 질문과 답변.
2. 제안 검토: 모듈·순서·설정·하지 않는 처리를 확인하고 수정 또는 저장. 실행 승인이 아닙니다.
3. 입력 선택: 로컬 입력·프로파일·작업 자원 상한을 선택하고 실행 후보를 준비.
4. 실행 승인: 실제 입력과 결합된 모듈·유효 설정·자원 범위를 확인하고 이번 실행을 명시적으로 승인.
5. 결과 확인: 생성된 표·그래프·로컬 보고서·품질 검토 중단 사유·다음 행동 표시. 생성되지 않은 결과를 만들어진 것처럼 표시하지 않습니다.

모델 연결·동작 모드·작업 기본 자원·LLM 정보 전달 정책은 별도 **설정 화면**에 둡니다. 작업 단계 번호와 설정 화면을 혼동하지 않게 구분합니다. 요청·제안·입력 선택 단계로 돌아가 내용을 변경하면 영향을 받는 후보·전송 확인·실행 승인을 무효화하고, 기존 실행 결과는 덮어쓰지 않습니다.

일반 안내는 한국어로 현재 상태·중단 이유·다음 행동을 먼저 표시하고 JSON·지문·오류 코드는 기술 상세 보기로 분리합니다. 사용자가 승인 ID를 직접 복사하지 않더라도 기존 승인 범위 검증·1회 소비는 유지합니다. 결과 열람과 LLM 전송은 분리하고 [정보 전달 정책 설계](design/LLM_COMMENTARY_REVIEW.md)에 따라 설정 허용과 실제 내용 확인을 모두 거친 요청만 전송합니다. 첫 버전은 단일 사용자·로컬 접속 범위이며 자동 승인·외부 공개·LangSmith 활성화를 포함하지 않습니다. UI 기술은 사용자 선택에 따라 **Streamlit**으로 확정했습니다. 별도 웹 API 서버를 새로 만들지 않고 로컬 Python 프로세스에서 기존 서비스를 호출합니다.

##### Streamlit 화면 갱신·중복 실행 방지 기준

2026-10-18 사용자 합의: 화면 렌더링과 상태 조회는 외부 효과가 있는 명령과 분리합니다. 화면 갱신·탭 이동·새로고침·재접속만으로 모델 호출·승인 발급·worker 실행을 시작하지 않습니다. 아래는 서비스 연결의 구현 기준이며 추가 요청 관리 서비스는 아직 구현하지 않았습니다. 첫 UI 뼈대는 실행 기능을 연결하지 않은 범위입니다.

| 계층 | 책임 | 단독으로 보장하지 못하는 것 |
| --- | --- | --- |
| Streamlit 화면 | 입력을 `st.form`으로 묶고 제출 이벤트만 명령으로 전달 | 폼·버튼 비활성화만으로 새 탭·동시 요청을 방어하지 못함 |
| `st.session_state` | 현재 단계·미저장 입력·대화 객체·선택한 로컬 작업 참조 유지 | 브라우저 연결 종료·새로고침·서버 재시작을 넘는 영속 보장 아님 |
| UI 서비스 계층 | 명시적 요청의 ID·내용 지문·처리 상태 확인, 명령/조회 API 분리 | 이미 네트워크로 전송된 모델 요청의 취소·회수를 보장하지 못함 |
| 로컬 요청 기록 | 모델 호출 등 아직 기존 실행기에 없는 명령의 중복 예약·상태 보존 | 대화 원문 자동 저장 또는 승인 권한을 의미하지 않음 |
| 기존 실행기·SQLite | 실행 잠금·승인 범위 확인·승인 1회 소비와 작업 예약·완료 검증 | LLM 호출·UI 저장 작업까지 이미 관리하고 있다고 해석하지 않음 |

서비스 함수는 대화형 CLI를 subprocess로 호출하거나 `input()`·셸 명령을 흉내 내지 않고 기존 코어를 재사용합니다. CLI와 UI가 사용자 확인 방식만 달리하고 승인 범위 검사·작업 잠금은 같은 신뢰된 계층을 사용하도록 연결합니다. UI 코드는 승인 DB에 직접 SQL을 쓰거나 성공 상태를 임의로 기록하지 않습니다.

요청 관리 원칙은 다음과 같습니다.

1. 새로운 사용자 의도를 명시적으로 제출할 때 요청 ID를 생성하고 해당 입력·정책·모델·작업 범위 지문과 결합합니다. 화면 렌더링마다 새 ID를 생성하지 않습니다. 동일 ID에 다른 내용이 오면 차단합니다.
2. 로컬 트랜잭션에서 중복 여부를 검사하고 예약한 뒤 한 처리자만 효과를 발생시킵니다. 새 요청 저장소가 필요한 모델 호출과 기존 승인/작업 예약을 재사용할 worker 실행을 구분합니다. 중복 방지를 이유로 승인 권한을 새 저장소에 복제하지 않습니다.
3. 같은 ID가 처리 중이면 상태만 반환하고, 완료된 요청은 이미 보관한 결과 참조를 조회합니다. 결과가 없거나 복원할 수 없으면 다시 호출하지 않고 상태와 한계를 안내합니다. 사용자가 같은 내용을 새 요청으로 다시 보내려면 별도 전송 확인과 새 ID가 필요합니다.
4. 명령은 버튼·폼 제출의 명시적 이벤트에서만 접수합니다. `pending` 상태라는 이유로 렌더링 코드가 실행을 재호출하지 않습니다. 장시간 작업은 UI 재실행과 분리한 작업 관리 계층에서 처리하고, 화면·상태 갱신은 조회만 수행합니다.
5. 타임아웃·프로세스 중단으로 모델 요청이 전달됐는지 모르면 전송 여부 확인 불가 상태로 남기고 자동 재시도하지 않습니다. 브라우저 연결 끊김을 작업 취소로 간주하지 않으며, 서버 재시작 뒤에도 이전 미확정 요청을 자동 재전송하지 않습니다.
6. 승인 화면에 표시한 입력·설정·계획·자원과 현재 범위를 서비스에서 재대조하고 기존 SQLite 승인 API로 발급·소비합니다. 재전송된 같은 승인 버튼 요청이 새 승인 여러 개를 만들지 않도록 명령 ID도 검사합니다. 유효 승인 확보 자체와 실제 실행 이벤트는 구분합니다.
7. 승인 후 내용이 변경되면 이전 승인과 전송 확인을 사용할 수 없게 합니다. UI 버튼만 초기화하지 않고 서비스 검증으로 이전 범위 사용을 거부합니다. 기존 완료 기록·소비 승인·실패 이력은 보존합니다.
8. 결과 표 열람·그림 펼치기·다운로드·진행 상태 조회·설정 화면 열기는 모델 호출이나 worker 실행을 포함하지 않습니다. `st.cache_data`·`st.cache_resource`를 부수 효과의 단일 실행 보장 수단으로 사용하지 않습니다.

요청 기록에는 필요한 로컬 식별값·상태·결과 참조만 두고 대화 원문·집계·프롬프트·키를 자동 저장하지 않습니다. 지문도 익명성 보증은 아니므로 로컬 접근 통제를 적용합니다. 기존 대화의 메모리 보관 원칙은 별도 저장 동의 전까지 유지합니다. 단일 사용자용 로컬 UI라도 새 탭·두 번 클릭·동시 이벤트가 발생할 수 있음을 고려하며, 이는 원격 다중 사용자 인증 지원을 뜻하지 않습니다.

`src/ui/app.py`는 5개 작업 단계와 별도 설정 화면을 사이드바로 선택하는 진입점입니다. `src/ui/settings.py`는 모델·동작 모드·기본 자원의 폼을 표시하고, `src/ui/state.py`는 기존 `LocalModelConfig`·`WorkerLimits`로 설정을 검증합니다. #### UI 요청·대화와 로컬 제안 연결

`src/ui/dialogue_service.py`가 기존 `ProposalDialogue`를 재사용합니다. LangGraph 확인 질문·답변과 LangChain의 loopback 운송·응답 계약 검증·추적 비활성화 경계는 그대로 유지합니다. `src/ui/dialogue_view.py`는 화면 표현, `src/ui/model_commands.py`는 명령의 중복 소비 방지를 담당합니다. 모델명·포트·생성 설정은 설정 화면에서 선택한 검증된 값을 사용합니다. 데이터 파일·통계·그래프·승인 DB 내용을 자동 첨부하지 않습니다. 사용자가 직접 입력한 문장 자체는 전달되므로 민감정보를 넣지 마세요.

사용 순서:

1. **요청 초안 보관**: 문장을 이번 세션 메모리에만 보관합니다. 모델을 호출하지 않습니다.
2. **전송 내용 미리보기**: 목적지·모델·실제 누적 요청을 확인합니다. 펼침 영역에는 공개 모듈 명세·응답 스키마·생성 설정을 포함한 전체 payload가 있습니다. 아직 모델을 호출하지 않습니다.
3. 전송 동의를 체크하고 **확인한 내용 전송**: 새 명령을 소비한 뒤 로컬 모델을 한 번 호출합니다.
4. 추가 질문이면 답변을 작성하고 1~3을 반복합니다. 최대 호출 횟수·누적 길이 제한은 기존 대화 계약을 유지합니다.
5. 유효한 제안이면 **2 제안 검토** 메뉴가 열립니다. 실제 모듈·순서·설정·선행 조건을 표시하고 별도 검토 확인 후 제안을 저장합니다. 아래 저장·입력 선택 연결 절을 참고하세요. 실행 승인·worker 연결은 다음 단계입니다.

대화와 제안은 브라우저 세션의 서버 메모리에만 보관하며, 자동 파일 저장·재접속 복원은 하지 않습니다. 모델·모드·자원 설정 변경은 이전 미리보기와 제안을 무효화합니다. 새 대화 버튼도 현재 제안·미리보기를 비우지만 소비된 명령 기록은 삭제하지 않습니다. 규칙 기반 모드에서는 모델 호출 버튼을 비활성화하며 수동 파이프라인 편집 UI는 미구현입니다.

중복 실행 방지: `logs/agents/ui/model_commands.sqlite3`에 명령 ID·설정/전송 지문·pending/completed/unknown·생성 시각만 기록합니다. 문장·모델 응답·승인 토큰은 기록하지 않습니다. HTTP 전에 원자적으로 명령을 소비하며 중복 명령·동시 제출은 다시 호출하지 않습니다. 통신 중단·프로세스 종료 후 pending/unknown은 자동 복구·재시도하지 않습니다. 이는 **동일 명령 ID당 최대 한 번 시도**이지 원격 처리 성공의 exactly-once나 다른 새 명령의 의미상 중복 차단을 보장하지 않습니다. 새 대화·새 전송은 사용자가 명시적으로 요청할 수 있습니다. 원문 오류를 화면에 표시하지 않으며 DB 사용 실패 시 호출 전에 중단합니다.

화면 갱신·메뉴 이동·제안 열람은 모델 호출·실행 승인·worker 시작을 하지 않습니다. 제안 검토 잠금은 현재 설정의 제안을 기존 계약으로 재검사한 결과로 판정하며, 세션의 임의 완료 플래그로 해제하지 않습니다. 이 잠금은 향후 실행기의 실제 권한 검사와 별개입니다. LangSmith 추적은 계속 비활성화합니다.

최초 UI 연결 검사 시 `dl312`에는 대화 의존성이 없었으나 후속 저장·입력 연결 검증 시 LangChain·LangGraph·LangSmith가 설치된 것을 확인했습니다. 새 환경은 UI를 실행할 같은 환경에 아래처럼 설치합니다. 설치는 모델 호출·추적 활성화가 아닙니다.


#### 요청 전 데이터 유형·경로 선택 보완

첫 화면의 **입력 데이터**에서 데이터 유형을 먼저 고릅니다. 기본값은 미선택이며 이 상태에서는 모델 전송 미리보기를 열 수 없습니다.

#### UI 입력 확인에서 실행 후보 생성 연결

#### 일반 PowerShell의 출력 폴더 권한 보완

후속 `llm_eda_run02`는 worker 시작 전 `ACL_OUTPUT`에서 실패했고, 사용자가 관리자 PowerShell에서 실행한 새 작업은 `completed`, `worker_started: true`로 완료했습니다. 이는 권한 설정 단계 문제를 뒷받침하지만, 관리자 실행만으로 세부 명령의 원인을 확정하지는 않습니다.

`writable_directory_acl.py`를 추가하고 모듈 파이프라인 운송 계층에 연결했습니다. 새 작업의 `output/result`·`scratch/task`가 링크 없는 빈 폴더인지 확인하고, 소유자 SID와 현재 프로세스의 사용자 SID가 같을 때만 호출자 자신에게 비상속 `WO`를 추가합니다. 기존 명시 권한은 보존하며 폴더 소유자를 바꾸지 않습니다. AppContainer에는 기존처럼 `M`과 Low 레이블만 적용합니다. 프로젝트·원본·입력·승인 DB의 권한은 변경하지 않으며, 일반 사용자에게 실행에 필요한 모든 권한이 항상 확보된다고 보장하지 않습니다.

Low 레이블 변경에는 `WRITE_OWNER`가 필요합니다([Microsoft SECURITY_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-information)). `icacls /grant`는 기존 명시 권한에 추가하고 `WO`는 소유자 쓰기 권한입니다([Microsoft icacls](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls)). 호출자 WO는 해당 빈 폴더에 남으며 하위 파일로 상속하지 않습니다. worker에 WO·FullControl을 추가하거나 자동 관리자 승격·보안 우회·실패 재시도를 하지 않습니다. 다른 전용 운송 경로의 ACL 동작은 이번 변경 대상이 아닙니다.

실패 시 `diagnostic.acl_operation`으로 `TARGET_CHECK`, `OWNER_CHECK`, `OWNER_MISMATCH`, `CALLER_WRITE_OWNER`, `WORKER_GRANT`, `LOW_INTEGRITY`, `WORKER_ACL`을 구분합니다. 경로와 명령 출력은 넣지 않습니다. 실패하면 worker를 실행하지 않고 기존 승인 소비·실패 기록은 유지합니다.

당시 전체 에이전트 테스트는 427개 중 420개 통과·선택 실행 7개 생략이었습니다. 현재 전체 회귀 결과는 문서 상단의 2026-10-19 검사 결과를 따릅니다. 새 충돌 제외 후보의 실제 AppContainer 합성 검사 1개와 기존 가상 제외 알고리즘 검사 3개도 별도로 통과했습니다. WM canonical의 실제 합성 정상·검토 중단 2개, 기존 검증·EDA·분할 증거 회귀 74개, pickle 변환의 합성 표·숫자 배열·WM 맵 실제 격리 3개는 앞선 실행 기록입니다. 기존 실데이터 품질 결과의 연결 가능성은 읽기 전용으로 확인했으며, 실데이터 후보 진단이나 실제 제외를 자동 실행하지 않았습니다.

모델 학습은 전처리 에이전트의 범위가 아닙니다. 현재 구현에서는 데이터·집계·그림·구조 보고서·상세 경로를 LLM에 전달하지 않습니다. [정보 전달 정책 설계](design/LLM_COMMENTARY_REVIEW.md)는 사용자 합의한 설정·자료 선택·개별 전송 확인 흐름이며 아직 구현하지 않았습니다. 실행 승인과 정보 전달 승인은 구분합니다.

WM 캐시 연결은 관련 회귀 17개와 실제 AppContainer 합성 검사 1개가 통과했습니다. 준비 진단 보완 후 관련 8개를 추가 검증했고, 사용자가 실행한 `wm-development-cache02`는 `cache_complete`로 완료했습니다. 실패한 `wm-development-cache01` 기록과 소비 승인은 보존했습니다. [캐시 생성 절차](guides/PICKLE_IMPORT.md#확인한-변환-설정으로-trainvalidation-캐시-생성)를 참고하세요.

WM Dataset·첫 배치 연결은 합성·기존 캐시/Dataset 회귀 17개와 실제 AppContainer의 PyTorch 합성 검사 1개가 통과했습니다. 실제 검사 worker에는 Train·Validation 캐시만 전달하며, 모델 학습·Test 처리는 하지 않습니다. 실데이터의 성공 여부는 별도 승인 실행으로 확인합니다. [Dataset 검사 절차](guides/PICKLE_IMPORT.md#완료-캐시의-dataset첫-배치-검사)를 참고하세요. 전체 에이전트 테스트 전체집합은 이번 변경 후 재실행하지 않았습니다.

사용자 실행 출력 기준 `wm-dataset-check01`은 `dataset_batch_passed`, `development_inputs_ready: true`로 완료했습니다. 위 별도 실행 확인 단계까지 진행한 기록이며, Test 맵 처리나 모델 학습 결과는 아닙니다.

WM 공통 모듈 연결 1단계는 [통합 등록·계획](design/METADATA_REGISTRY.md#wm-작업의-공통-등록계획-연결)을 참고하세요. 새 검사 10개를 포함한 관련 회귀 38개와 WM Dataset·캐시 회귀 25개가 통과했습니다(중복 제외 53개). 현재 CLI는 목록·정적 검증만 제공하며, 기존 작업 연결 API도 자동 실행·승인 소비는 하지 않습니다. 전체 흐름을 하나의 CLI로 실행하는 단계와 구분합니다.

후속 [실제 작업 연결 조회](design/METADATA_REGISTRY.md#실제-wm-작업-배정과-읽기-전용-연결-조회)를 추가했습니다. `wm_run_binding_cli`는 배정된 정상 WM 6단계의 완료·승인 소비·부모 결과 연결을 읽기 전용으로 대조합니다. 현재 실제 완료 작업 6개도 `bindings_verified`로 확인했습니다. 새 작업 생성·승인 발급·worker 실행 기능은 아니며, 충돌 제외 분기의 통합 조회는 아직 지원하지 않습니다.

[다음 작업 안내](design/METADATA_REGISTRY.md#다음-작업-안내)는 `wm_guidance_cli`로 조회합니다. 준비·승인 요청·승인 대기·유효 승인 보유·예약·실패·취소·보안 잠금을 구분하고 행동만 안내합니다. 새 테스트 7개를 포함한 관련 회귀 22개가 통과했습니다. 현재 단계는 안내까지이며 생성·승인·실행 명령을 자동 호출하지 않습니다.

별도 [생성·배정 CLI](design/METADATA_REGISTRY.md#첫-eda-작업-준비-통합)는 첫 EDA부터 분할·변환·캐시·Dataset까지 정상 6단계를 기존 생성 함수로 준비하고 새 배정 파일을 기록합니다. 첫 EDA도 canonical 바이트 복사·선택 고정만 수행하며 생성 명령 자체는 worker를 실행하지 않습니다. [공통 승인·실행 CLI](design/METADATA_REGISTRY.md#공통-승인한-단계-실행)는 배정된 현재 작업을 명시해 기존 사용자 승인 화면 또는 한 단계 실행을 호출합니다. 자동 승인·전체 자동 진행·실패 재시도 기능은 아닙니다. 실제 AppContainer의 단일 합성 EDA 정상·검토 중단 경로와 [새 합성 6단계 전체 연결](design/METADATA_REGISTRY.md#새-합성-6단계-전체-완료-검증)을 확인했습니다. 실데이터 성능·모델 학습·자동 승인 성공으로 확대 해석하지 않습니다.

충돌 제외 적용 후속 검증은 관련 합성 회귀 57개와 실제 AppContainer 합성 적용 1개가 통과했습니다. 새 canonical 전체 재검증까지 포함하며 실데이터 적용은 자동 실행하지 않았습니다. 이 후속 변경 후 전체 테스트 전체집합은 재실행하지 않았으므로 위 427개 기록과 구분합니다.

## 문서 관리 원칙

- 새 기능마다 최상위 문서를 늘리지 않고 기존 역할별 문서를 먼저 갱신합니다.
- 현재 지원 상태와 읽는 순서는 이 안내에서, 실제 명령은 `guides/`에서 관리합니다.
- 상세 보안 기준은 상세 설계·`security/`, 데이터·모듈 계약은 `design/`을 따릅니다.
- 과거 실행·검증 기록은 `history/`로 구분합니다. 오래된 명령이 재개 가능하다고 가정하지 않습니다.
- 문서 이동 시 상대 링크를 함께 갱신합니다. 하위 폴더마다 README를 추가하지 않습니다.
