# 전처리 에이전트 사용 안내

현재 사용법·지원 상태·제한의 진입점이다. 구조와 계약의 유일한 설계 기준은 [DESIGN](DESIGN.md)이다. 과거 변경/실행 이력은 Git과 로컬 테스트·작업 로그에서 확인한다.

## 현재 구현 상태

| 범위 | 상태 |
| --- | --- |
| 통합 작업 | 공통 조정기·표형(CSV) 어댑터 구현. 진단 → 권장안/질문 → 계획 → 분할·전처리 → 적용·전달 → 보고서 연결 |
| 배열 통합 작업 | 단일 `.npz`의 매핑·분할·Train 채널 기준·Train/Validation float32 결과. 실제 합성 격리·화면·제한된 용량 검증 이력은 [배열 실행과 메모리 검증](#배열-실행과-메모리-검증)을 따른다. 옵션이 모두 none이어도 float32 변환 손실 가능 |
| 실패 대응 | 중복 헤더 동의형 정비, 품질 지적 표시, 일부 입력 실패의 계획 수정·새 시도, 완료 저장 실패의 검증 후 복구 |
| 결과 설명 | 전체 옵션 편집·설명, 후보 영향, 출처·제외 사유, 예상/실측 구분. Test 미적용·미처리·미검증 표시 |
| 메뉴 | 기본은 통합 작업의 작업/설정. 기존 LLM 제안·등록 모듈은 고급 도구에 유지. 사용자 화면 확인 완료 |
| 기존 도구 | CSV 5개 작업, WM 정상 개발 6단계, 구조 판별 pickle 변환, 저장 EDA 제안 목록 복원·모델 목록 조회·별도 로컬 결과 해설 |
| 미지원 확장 | pickle·이미지 폴더 배열 입력, 웨이퍼 통합 프로파일, 표형 v2 이외의 통합 time 분할(표형 v2는 시간 결측 복원 → time 분할 → Train/Validation 내보내기 → 전처리·전달까지 합성 검증, 실제 AppContainer·브라우저 미검증), 외부 API, 일반 자동 재개/사용자 코드 실행 |
| 검색 근거(실험적 Graph RAG) | 기본 OFF 선택 기능. 표형 v1·v2만 ON 가능(배열은 거부). 검토된 지식집(항목 38)을 제품 경로에 연결하고 실제 BGE-M3 색인 구축·검색 점검을 했다. 근거 예산은 검증한 Qwen3.5 구성에서 로컬 토큰 계산을 쓴다(하네스 실제 확인 3건). 실제 ON 작업·브라우저는 미검증이다. 권장 정확성 개선은 확인되지 않았다([사용과 제한](#검색-근거-실험적-graph-rag)) |
| 표형 입력 확장 | CSV v2의 입력 해석·자료형 보존·진단·처리·보고서 연결 구현. 사례 A·B 실제 흐름과 기준 커밋 전체 회귀 확인. [표형 v2 검증](#표형-v2-검증)에서 코드 시점·실제 검사와 생략 범위를 구분한다 |

구현·테스트 통과·실제 환경 확인은 다르다. CSV 실제 작업의 완료 이력이 있지만 모든 데이터·설정의 적절성이나 모델 성능을 보장하지 않는다. 기존 SECOM 실험과 통합 작업은 입력·분할·전처리 설정을 맞추지 않으면 동일 실험이 아니다.

현재 로컬 모델은 확인한 사례에서 진단 수치 해석, 라벨·그룹 구분, 전처리 권장 이유에 오류가 있었다. 형식·허용값 검사를 통과해도 내용의 타당성을 보장하지 않으므로 계산 결과와 모델 의견을 구분해 확인한다. 이는 현재 모델의 관찰된 한계이지 에이전트 공통 기능의 제한이 아니다. 다른 로컬·API 모델은 별도 품질 평가가 필요하며, 외부 API 연결은 현재 미지원이다.

### 표형 v2 지원 범위

- 새 CSV 작업은 `tabular_v2`, 기존 CSV·배열 기록은 저장된 유형으로 연다. 지원 입력 형식은 아직 CSV뿐이다.
- UTF-8/BOM·쉼표·첫 행 헤더를 기준으로 해석한다. 중복 이름은 입력 해석 화면에서 동의 후 정비하며, 빈 이름은 자동으로 채우지 않는다.
- 빈 필드는 기본적으로 결측으로 해석하며, 빈 문자열 보존은 명시한 입력 설정을 따른다. `NA`·`NULL` 같은 추가 결측 토큰을 자동으로 적용하지 않는다.
- CSV에는 자료형 선언이 없으므로 **확정한 입력 해석의 자료형·의미를 보존**한다. 선행 0 문자열과 큰 정수의 저장을 지원하지만, 수치 특징 계산의 정밀도·지원 범위는 별개다.
- 숫자 문자열의 수치 변환, 추가 형식·엔진·다중 파일 연결(T2~T4)은 후속 업데이트로 보류한다.
- 역할·분할·전처리·질문 답변을 반영한 최종 계획을 확인한 뒤 동의 C로 진행한다. 후보 확인 후 동의 D로 적용한다.

## 시작하기

프로젝트 루트와 Windows Python 3.12 환경을 사용한다.

```powershell
conda activate wm-gpu312
Set-Location D:\workspace\waferguard
python -m streamlit run src/ui/app.py --server.address 127.0.0.1
```

실제 UI 격리 실행의 권한 안내를 확인한다. 관리자 권한이 필요한 경로는 관리자 PowerShell에서 서버를 시작한다. 모든 조회·합성 회귀에 관리자 권한이 필요한 것은 아니다. 코드 변경 후 서버를 다시 시작한다. 설정 → 연결 확인은 Ollama `/api/tags` 목록 조회이며 추론/모델 품질 검사가 아니다.

### 통합 작업

1. 파일(CSV 또는 `.npz`)과 목표를 입력하고 작업/복사·진단·모델 전달 범위를 확인한다. 목표에 예측 대상을 명확히 적는다. `.npz`는 pickle 없이 숫자·bool·문자열 배열만 읽고, 모델에는 라벨 이름 대신 순번별 개수만 보낸다(클래스 의미 해석 불가).
   - `.npz`는 진단 화면에서 입력 미리보기(앞쪽 최대 12개, 로컬 전용)를 보고 표본 배열·채널 축·라벨·그룹·ID를 매핑한다. 같은 표본이 있으면 '같은 표본을 한 구간에 모으기'로 누수를 막을 수 있다(삭제 없음).
2. 새 CSV v2는 먼저 입력을 검사한다. 중복 헤더로 멈추면 입력 해석 화면에서 동의한 경우에만 번호를 붙인 작업용 표를 만든다. 원본과 데이터 값/순서는 유지하며 빈 이름 등은 자동 수정하지 않는다. 기존 CSV 기록의 헤더 정비 경로와는 구분한다.
3. 격리 진단 후 모델 권장안 출처와 질문을 확인한다. 모델 실패 시 기본 계획으로 표시되며 자동으로 재요청하지 않는다. 모델 권장안이 계획 계약에 맞지 않으면 권장안 전체를 거부하고(변경 미적용, 부분 채택 없음) 기본 계획으로 시작한다. 분할 계약·역할×분할 거부는 확인된 하위 원인(비율 범위·비율 합·계층 분할과 분할 방식, 필요한 역할 없음·group 역할과 분할 방식·target 없는 계층 분할)과 검사한 분할 값만 고정 문구로 보이며, 하위 진단이 없는 이전 기록(`SPLIT_ROLE_MISMATCH` 포함)은 세부 원인 미확인으로 표시한다. 역할 쪽 원인 컬럼 이름은 기록하지 않는다. 이 안내는 전처리 실패나 모델 권장안 성공이 아니다.
4. 역할·분할·전처리 옵션을 수정한다. target·식별자를 확인하고 필수 질문에 답한다. 비예측 목적이면 예측 대상 없음에 명시적으로 답한다. 질문과 양식 충돌은 직접 선택한다.
5. 최종 계획 미리보기의 유효 설정을 확인하고 동의 C로 분할·내보내기·후보까지 진행한다. 내부 실행명·선행 결과는 시스템이 연결한다.
6. 후보의 제거·출력 폭·clipping·상수화 경고를 확인한다. 바꾸려면 적용하지 않고 계획 수정으로 새 시도를 준비한다. 그대로 적용할 때 동의 D로 적용·전달을 진행한다.
7. 결과의 실제 처리·전후 비교·미처리/미검증·파일 활용을 확인한다. 완료는 전처리 완료이지 모델 성능 검증이 아니다.
   - 새 CSV v2 보고서는 '처리 전 데이터와 기본 EDA'(분할 전 전체 입력 기준 표 7종)와 '계획과 결정'(권장안 사용·결정 출처·최종 설정과 실제 변경) 절을 둔다. '그래프' 절에는 요청·확정 분할 비율과 target 클래스 분포(분할 전 전체 입력)를 화면 그래프로 보이고, 저장 Markdown에는 같은 값의 표와 텍스트 막대를 남긴다. 분할 EDA PNG는 화면에서만 표시한다.
   - 긴 표·target 그래프는 상위 20개만 보이고 표시/전체/생략 개수를 적는다. 긴 이름은 줄이고(표 80자·그래프 24자) 순위로 구분한다. 전체 EDA 표는 기술 상세의 분할 EDA 보고서 폴더에 있다.
   - 완료 보고서의 화면과 Markdown은 같은 표 열 순서를 사용하며 일부 행에 없는 값은 빈 칸으로 둔다. 이 확인은 모든 화면 전용 표의 순서를 보장하지 않으며, 적용·계획 확인 화면과 배열 채널 표의 알려진 문제는 [남은 제한과 안정화](#남은-제한과-안정화)를 따른다. 질문 답변은 고른 선택지와 확정 계획 값을 구분하고, 구간별 클래스는 같은 순서로 표시한다. 결측률 PNG는 0에서 시작하는 백분율 축·값 라벨을 사용하며, 표시한 최댓값에 따라 축 범위가 달라진다. 서로 다른 작업의 막대 높이는 축 범위를 함께 보고 비교한다.
   - 산출하지 않는 것: 구간별 처리 전 분포, 같은 구간의 처리 후 분포·전후 분포 직접 비교, Test 집계, 범주형 특징의 실제 범주값. target이 없거나 근거가 없으면 그래프 대신 해당 없음·근거 없음 사유를 표시한다. 이전에 완료한 작업의 보고서에는 이 절·그래프가 없다(자동 재조립하지 않음).

### 검색 근거 (실험적 Graph RAG)

- 요청 화면의 `검색 근거 (실험적 Graph RAG)`에서 고른다. 기본은 OFF이며 OFF는 기존과 같은 요청을 보낸다. ON은 표형(CSV) 작업만 가능하고 `.npz`로 ON을 고르면 작업을 만들지 않고 OFF로 다시 시작하라고 안내한다.
- ON을 고르면 동의 A 안내에 임베딩으로 보내는 정보(목표 문장 + 전송 집계에서 계산한 고정 특성 문구, 컬럼명·값 없음), 생성 요청에 근거를 더한다는 점, 품질 미입증, 실패 시 동작이 나온다. 같은 화면에 지식집·색인 검사 결과(임베딩 없이)가 보인다.
- 지식집은 `configs/agents/rag/tabular/`(추적), 색인은 `models/rag/tabular/`(Git 제외, 이 PC에서 구축)에 있다. 다른 PC나 새 checkout에서는 색인이 없어 ON으로 시작해도 `현재 지식집에 맞는 벡터 색인이 없습니다` 사유를 기록하고 근거 없이 기존 방식으로 요청한다. `python -m src.agents.rag_index_cli verify tabular`로 검사하고, 색인이 없으면 `build tabular`로 만든다(로컬 Ollama의 `bge-m3:567m` 필요, 문서마다 1회 임베딩, 실패 시 재시도 없음, 기존 색인 덮어쓰기 없음). 작업 중 자동 구축은 하지 않는다.
- 계획 확인·완료 화면과 보고서의 `검색 근거` 줄에서 선택 모드와 실제 결과(그래프 관계까지 전달·벡터 근거만·관련 근거 없음·예산 부족·실패)와 사유, 실제 요청에 넣은 지식·관계의 적용 조건·출처·검토 상태를 확인한다. 저장된 기록만 보여 주며 다시 검색하지 않는다.
- ON의 근거 예산: 검증한 Qwen3.5 구성(Ollama `0.40.7-rc0`, `qwen3.5:9b` digest `56671c2a…`, think=false)이면 로컬 토크나이저로 실제 입력 토큰을 세어 입력 + 응답 예약 + 256 ≤ 문맥 길이 안에서 근거를 넣는다. 그래서 기존 바이트 추정보다 근거가 많이 들어간다. 구성·파일·라이브러리가 다르거나 미지원 문자열(NFC로 바뀌는 문자, GGUF 전용 특수 토큰 문자열 등)이 있으면 기존 바이트 예산을 쓰고 `요청 예산: 기존 바이트 추정 · 전환 사유: …`가 보인다. OFF는 계산하지 않는다.
  - 준비(한 번, 앱 밖에서): 검증 환경은 `python -m pip install --no-deps tokenizers==0.23.3`로 설치했다. `requirements.txt`로 설치하면 `tokenizers`의 선언 의존성(`huggingface-hub`, 버전 미고정)이 함께 설치된다. 런타임에는 쓰지 않는다. 공식 파일은 고정 리비전에서 임시 이름으로 받는다. 아래 Python 명령은 sha256이 맞고 같은 이름의 파일이 없을 때만 `tokenizer.json`으로 이름을 바꾸고, 해시가 다르면 임시 파일을 지운다(PowerShell에서는 `curl.exe`로 쓴다).
    ```
    curl.exe -L --fail --create-dirs -o models/tokenizers/qwen3.5-9b/tokenizer.json.download https://huggingface.co/Qwen/Qwen3.5-9B/resolve/c202236235762e1c871ad0ccb60c8ee5ba337b9a/tokenizer.json
    python -c "import hashlib,os;s='models/tokenizers/qwen3.5-9b/tokenizer.json.download';d=s[:-9];ok=hashlib.sha256(open(s,'rb').read()).hexdigest()=='5f9e4d4901a92b997e463c1f46055088b6cca5ca61a6522d1b9f64c4bb81cb42';print('해시 일치' if ok else '해시 불일치: 임시 파일 삭제');(os.rename(s,d) if not os.path.exists(d) else print('기존 파일 유지: 임시 파일 삭제')) if ok else None;os.path.exists(s) and os.remove(s)"
    ```

- ON 동의 A에는 검색 근거 실행 코드의 지문이 함께 고정된다. 동의 뒤 해당 코드가 바뀌면 임베딩과 모델 요청을 모두 보내지 않고 기본 계획에서 시작하며, `검색 근거 동의(실행 코드 지문 포함)가 현재 작업 설정·코드와 맞지 않아…` 사유가 보인다. 다시 권장안을 받으려면 새 작업으로 시작한다.
- 지식집 출처 중 공식 문서(`official_doc`)의 제목에는 `https://` 주소를 그대로 쓸 수 있다(형식은 [설계](DESIGN.md#실험적-검색-근거-graph-rag-기본-off)의 출처 계약). 주소는 표시만 하며 앱이 접속하거나 내려받지 않는다.
- 근거는 참고자료다. 계획 검증·질문·동의 C·D·처리 계산은 OFF와 같다. 근거가 들어가도 모델 권장안의 정확성이 좋아졌다고 판단하지 않는다.

동의 A/C/D의 정확한 범위는 [설계](DESIGN.md#승인과-실행)를 따른다. 기존 동의를 다른 입력·계획·시도에 재사용하지 않는다. 화면 갱신·메뉴 전환은 새 모델 호출·승인·worker 실행의 동의가 아니다.

### 옵션과 품질 지적

- 구간화·스케일링·이상치 처리는 필요에 맞게 끌 수 있다. 모델 질문이 없어도 양식에서 수정 가능하다. 허용되지 않은 조합은 자동 수정하지 않고 충돌을 표시한다.
- 상수나 결측이 많은 컬럼은 진단 근거를 보고 역할을 정한다. 분할 전 품질 기준과 Train 전처리 제거 기준은 별개다. 일괄 제외는 직접 선택할 때만 적용한다.
- 분할의 '모든 구간에 모든 클래스 요구'는 기본으로 켜져 있다. 작은 데이터·group 분할에서 target 클래스가 빠진 구간이 생기면 분할 제안에서 멈추고 빠진 구간·클래스를 보여 준다. 비율·시드·group 기준을 바꾸거나, 그런 구간을 허용할 때만 이 설정을 끄고 다시 확인한다. 끄고 진행하면 보고서 주요 문제에 '확인된 클래스 누락'으로 남는다.
- IQR 후보는 정상 0/1 값일 수도 있다. 후보 수만으로 삭제/clipping을 결정하지 않는다. 적용 전 정보 손실 경고를 확인한다.
- 결정 D의 표형 `예상 처리 영향` 표는 특징별 `변환 후 고유값`·`값 변화`(상수화·일부 병합·원래 상수)·`관련 설정`(그 특징에 실제 적용된 구간화·극단값 자르기)을 보인다. 변환 후 정확한 고유값은 저장하지 않아 상수화는 1, 구간화는 '최대 구간 수', 그 밖은 미집계로 표시한다. '최대 N' 행이 있는 후보는 표 바로 아래에 이것이 저장된 구간 수로 계산한 상한이며 실제 변환 결과에서 센 고유값 수가 아니라는 설명을 표시한다(설명 추가 전에 계산·저장된 후보에는 나타나지 않는다). 일부 병합은 구간화의 의도된 결과일 수 있으며 오류를 뜻하지 않는다. 값 종류가 적은 숫자 범주 코드를 수치형으로 두고 구간화하면 상수화·병합이 생길 수 있으니 역할을 확인한다. 관련 설정이 둘이면 원인을 하나로 정하지 않는다. 실제 UI 확인(`a8eed00e…`, `train_and_test2.csv`를 622843과 같은 확정 계획으로 재현, 동의 D 전 종료): 10열 머리글·7행 셀이 후보·저장 기준과 일치하고, Sex·Embarked 상수화(구간화)·5개 일부 병합 경고와 구간화만 가리키는 조치 안내를 확인했다. 이 확인 당시 화면에는 상한 설명이 없었고, 이후 추가한 설명은 AppTest 화면 경로로만 확인했으며 실제 브라우저에서는 확인하지 않았다. 같은 실행의 실제 모델 응답은 `SPLIT_STRATIFY_TARGET_MISSING`으로 전체 거부돼 새 지시문에 따른 권장 내용·설명은 확인하지 못했다. 이 1개 데이터 사례는 다른 데이터의 권장 품질을 검증하지 않는다.
- 숫자 문자열/공백을 수치형으로 정비하거나 조건부 대치하는 기능은 아직 없다. 현재는 적합한 역할/제외를 선택하거나 별도 입력 정비를 준비해야 한다. 원본 수정 명령을 자동 실행하지 않는다.

### 결과 파일 사용

전처리 기준은 Train에서만 산출하고 Train·Validation에 적용한다. 결과는 학습 특징 파일과 같은 순서의 `rows.json`에 target·식별자·출처를 나눠 보존한다. `feature_mapping.json`은 출력 열과 원본 특징의 대응, `preprocessor.json`은 Train 기준, `application.json`은 적용·검증 기록이다.

Test는 변환하지 않는다. Test/새 데이터에는 저장한 Train 기준을 별도로 적용해야 하며, 통합 작업이 그 실행이나 성능 평가까지 끝냈다고 보지 않는다. Validation에 새 범주가 있으면 `unknown_category=error` 설정은 차단될 수 있다.

v2 전달 묶음은 `src.agents.csv_handoff_contract.load_handoff_partition(bundle, "train")` 또는 `"validation"`으로 특징 표와 같은 순서의 행 메타데이터를 함께 읽는다. 입력 해석에서 정한 라벨·ID 타입과 앞자리 0을 보존하려면 부속 파일을 임의로 CSV 재추론하지 않는다. 기존 v1 CLI의 전달 절차는 [CSV_HANDOFF](guides/CSV_HANDOFF.md)를 따른다.

## 문제 발생과 기존 작업

- 먼저 확인된 worker 분류·세부 코드와 추정 원인을 구분해 읽는다. 자동 재시도하지 않는다.
- 일부 결정 C 입력 실패/적용 전 후보는 계획 수정 후 새 동의·새 시도로 진행할 수 있다. 환경 오류·불명확 실행·D 이후를 같은 방식으로 재시도할 수 있다는 뜻은 아니다.
- 계산은 끝났지만 완료 저장만 실패했다면 검증 후 완료 기록 복구를 사용한다. worker·승인을 다시 실행하지 않고 계보·결과를 검증해 기록만 복구한다.
- 코드가 바뀌면 미실행 승인이 무효가 될 수 있다. 완료 파일은 보존하지만 모든 과거 결과를 현재 검증기로 열 수 있는 것은 아니다. 코드 변경 후 handoff 읽기 전용 검증은 제한적으로 지원한다.
  - 결측률 그래프 생성 코드는 공통 worker 지문에 포함된다. 해당 코드 변경에 묶인 미실행 승인은 새로 준비해야 한다. 변경 전 완료 작업은 분할 결과의 지문 검사로 PNG 표시·보고서 재조립·단계 결합을 통한 v2 전달 검증이 차단될 수 있다. PNG 검증에 실패하면 화면에서 표시하지 않으며, 저장된 facts·결과·보고서 파일은 보존한다. 조회와 재검증·재실행은 별개이고, 기존 파일을 자동 갱신하거나 승인 기록을 고쳐 우회하지 않는다.
- 표형 입력 검사·생성이 아래 코드로 멈추면 입력 문제가 아니라 공유 Python 런타임 문제다. 화면 문구의 다음 행동을 따른다.
  - `RUNTIME_SOURCE_INVALID`: 원본 환경을 확인한다.
  - `RUNTIME_PREPARE_FAILED`: 디스크 공간과 `logs/agents/worker_runtime` 권한을 확인한다.
  - `RUNTIME_VERIFY_FAILED`: 관리자가 불일치한 버전 폴더를 다른 곳으로 옮긴다.
  - `RUNTIME_PERMISSION_INVALID`: 소유자·권한 이상이다. 다른 Windows 계정이 만든 저장소도 이 코드다. 관리자가 해당 폴더를 확인해 옮긴다. 앱은 권한을 자동으로 고치지 않는다.
  - `RUNTIME_CHANGED`: 승인한 런타임이 없고 Python 환경이 바뀐 경우다. 같은 승인으로 다른 런타임을 고르지 않는다.
  - `INPUT_STORE_PERMISSION_INVALID`: 입력 실행 기록 저장소(작업 폴더의 `input_runs`)의 소유자·권한·경로 이상이다. 입력 데이터 문제가 아니다.
    - 검사 대상은 `input_runs` 아래(실행 기록·승인 DB·worker 작업 폴더 `workers/<task>`)다. 원인은 다른 주체의 쓰기·삭제·권한 변경, 상속 권한, 링크다.
    - 상위 작업 폴더(`tasks/<task>`)의 권한은 검사하지 않는다.
    - 이전 버전에서 만든 작업 폴더, 실행 기록 루트·실행 폴더가 없는 경우도 이 코드다.
  - `INPUT_STORE_PREPARE_FAILED`: 입력 실행 기록 저장소를 보호 권한으로 만들지 못한 경우다. 디스크 공간·작업 폴더 권한·상위 경로 링크를 확인한다.
  - 모든 경우 그 뒤 새 작업으로 시작해 실행·승인을 새로 준비한다.
  - 앱은 공개된 버전 폴더를 덮어쓰거나 지우지 않는다. 원본 환경으로 대신 실행하지 않는다.
  - 이전 버전 폴더와 비정상 종료로 남은 `.staging-*`는 자동으로 정리하지 않는다.
- 실험 브랜치의 새 작업 폴더는 보호 권한으로 만들어진다.
  - `RECORD_UNPROTECTED`: 작업 기록이 보호 경계 밖이다. 이전 버전에서 만든 작업이거나 다른 사용자·그룹의 쓰기 권한이 있는 경우다.
    - 진행·승인·완료 복구는 하지 않는다.
    - 저장된 결과 조회는 기존대로 된다.
    - 완료 작업의 보고서 재조립은 시도할 수 있지만, 현재 코드의 결과 검증을 통과해야 한다. 이전 작업은 대개 실패하며 기존 보고서는 그대로 둔다.
    - 새 작업으로 시작한다. 권한을 자동으로 고치지 않는다.
  - `RECORD_PROTECT_FAILED`: 작업 폴더를 보호 권한으로 만들지 못한 경우다. 디스크 공간·`logs/agents/tasks` 권한·상위 경로 링크를 확인한다.
- 기록 크기·파일 없음·소유자·해시/링크 오류를 구분한다. 파일을 임의 수정하거나 승인 소비를 되돌려 해결하지 않는다.
- 화면이 오래 멈추면 `events.jsonl`의 마지막 started/finished와 프로세스를 확인한다. 터미널 텍스트 선택으로 출력/실행이 일시 정지될 수도 있으나 추측으로 단정하지 않는다.

원본 `review_required`·`drop_evidence_verified: false`는 유지했다. 사후 대조는 같은 실행의 `wfp/review.json`에 별도로 남겼고 ETL은 로컬에만 보관한다. 초기 실행 `36b4641e…`의 Low Integrity 설정 접근 거부와 WFP 미시작 결과도 보존한다. 기존 2026-10-23 ETL 재검토 근거를 새 실행에 소급 적용하지 않으며 상세 시각·식별 대조는 [WFP 진단](security/WFP_DIAGNOSTIC.md#etl-대조-근거와-확인-범위)을 따른다.

- 품질 검토 테스트의 간헐 PROCESSING_FAILED는 원인 미확인이다. 마지막 전체 회귀에서 해당 오류가 없다고 해결로 보지 않는다.
- 실험 브랜치의 관련 묶음 실행에서 단계 생성 직후(`step_status=created`) `PermissionError`가 다른 테스트 두 곳에서 한 번씩 났다. 원인은 미확인이고 해결로 보지 않으며, 이번 변경과 무관하다고 단정하지 않는다. 단계·예외·조건은 `_workspace/worker_runtime_reuse/r3/intermittent_failure.md`에 보존했다.
  - `test_ui_task` 분할 단계(r1 보안 반영 후 실행). 같은 묶음의 이전 실행과 단독 재실행에서는 통과했다.
  - `test_task_array_adapter` 적용 단계(r3 실행). 배열 경로는 이번 변경 코드를 참조하지 않는다. 이전 묶음 실행과 단독 재실행에서는 통과했다.
- 적용 전 계획 수정 테스트의 다중 모듈 실행 실패는 후속 재현 검사에서 재현되지 않았다. 원인은 미확인이며, 실패 시 작업 상태·문제·단계 기록이 나오도록 테스트 진단만 보강했다. 위 품질 검토 실패와 같은 원인이라고 단정하지 않는다.

### 남은 제한과 안정화

- 화면 전용 표의 열 순서는 완료 보고서 표와 검증 범위가 다르다. `30376180…`에서 확인된 CSV 적용 확인 `예상 처리 영향` 표의 순서 결함은 보완 후 자동 검증(A01~A06)과 실제 UI(`1eb29cbe…`, B01~B08)를 통과했다. 실제 UI는 `line` 1행의 최소 사례이며 여러 셀 조합의 판별은 자동 검증 범위다. 품질 지적·권장 변경·옵션 설명·`기본 계획과 다른 항목`·`이번에 고친 항목` 표와 배열 결정 D 채널 표는 표를 만드는 쪽이 열 순서를 명시하도록 보완했고(저장 facts 표는 `columns`를 함께 저장), 자동 검증(AppTest)을 통과했다. 실제 UI(CSV `f8b7c906…` 최종 미리보기, 배열 `9a0e68f0…` 적용 확인)에서는 옵션 설명·`기본 계획과 다른 항목`·`이번에 고친 항목`·배열 채널 표의 머리글·셀을 확인했고, 품질 지적·권장 변경 표는 해당 조건(품질 문제·모델 권장 변경)이 없어 실제 UI 미검증이다. `columns`가 없는 이전 facts는 기존 기본 순서로 표시한다. 배열 진단 요약 표(배열 → 형상 → 자료형 → 구분 → 비유한 값 → 값 종류 → 평균 → 최솟값(로컬) → 최댓값(로컬) → 상수 표본 → 동일 표본)와 배열 결정 D `구간별 표본` 표(구간 → 표본 → 클래스 → 그룹)도 어댑터가 순서를 명시하도록 보완해 자동 검증과 실제 UI(`198a0d24…`, 이름순으로 1차원 배열이 표본 배열보다 앞서는 입력, 적용 확인에서 동의 D 전 종료)를 통과했다. 공통 렌더러 호출부 점검에서 그 밖에 의도와 다르게 보이는 표는 확인되지 않았다. 재사용 검증 절차는 [화면 표 최종 검증](guides/UI_DISPLAY_ACCEPTANCE.md)을 따른다.
- 안정화는 현재 지원 흐름과 결과 일치를 우선한다. LLM 요청·실행 계약 불일치는 보완했고 실제 채택 응답 1건을 확인했으나, 안내 질문의 항목 연결·불필요한 처리 권장 등 의미 품질은 미검증/한계로 남는다. 추가 성능 최적화와 사전 준비 worker·런타임 공유·관리자 권한 분리·별도 B안 프레임워크·T2~T4는 보류한다.
- 검색 근거(실험적 Graph RAG): 검토된 지식집(항목 38·관계 65, 사람 검토 pending)을 연결하고 실제 BGE-M3 색인(38개 임베딩)을 만들어 제품 검증기로 열었다. 개발·보정 질의 20개의 검색 점검(지식집 개발 자료이며 독립 평가 아님)에서 기준 0.555·0.05로 근거 없는 질의 6개는 모두 억제됐고(최고 0.524), 조건이 다른 질의 6개 중 4개에서 기대 항목을 찾았으며, 개발 사례 8개의 기대 항목 42개 중 검색 9개·그래프 확장 포함 20개를 회수했다. 유사도만으로 조건 불일치를 가르지 못하고 범용 항목(K02·K31·K33)이 자주 검색된다. 같은 벡터로 비교한 다른 기준은 회수를 늘리지 못하거나 한 사례만 바꿔 기준을 유지했다. 근거 예산: 바이트 추정(문맥 8192 기준 메시지 약 8.8 KB)만 쓰던 때에는 개발 사례 8개 모두 근거가 들어가지 못했다(`예산 부족으로 미사용`). 지금은 검증한 Qwen3.5 구성에서 로컬 토큰 계산을 쓰며, 하네스에서 제품 요청 구성·RAG 연결·권장 요청 함수로 D01·D04·N_WIDE(81열)를 실제 생성(num_predict 2048)해 확인했다. 근거는 항목 5·8·6개, 관계 6·8·8개가 들어갔다. 로컬 입력 토큰(3,519·4,650·4,871)이 서버 값과 같았고, 진단 범위는 근거 없는 요청과 같았으며, 모두 정상 종료(stop)·권장안 계약 채택이었다. 구성이 다르거나 미지원 입력이면 바이트 예산으로 전환되므로 그때는 근거가 거의 들어가지 못할 수 있다. 정확 계산 일치는 시험한 요청(독립 시험 28개·실제 확인 3개)의 결과이며 모든 입력·버전의 보증이 아니다. 근거가 들어간 권장안의 품질·정확성 개선은 평가하지 않았다. 실제 ON 작업 실행·화면·브라우저 확인은 하지 않았다. 실행 코드 지문 결합(동의 후 코드 변경 시 요청 없음)과 공식 문서 `https://` 주소 허용·로컬 경로 거부도 임시 사본·문자열 검사의 자동 검증 범위다.
- 모델의 내용 오류와 실제 문맥 잘림 감지는 별도 문제다. 예산·응답 계약 통과가 의미적 권장안 품질을 보장하지 않는다.
- 네트워크 차단 증거는 별도 합성 시험의 관찰 범위만 인정하며, 위 [네트워크 시험](#네트워크-시험)과 [WFP 진단](security/WFP_DIAGNOSTIC.md)을 따른다. 전체 회귀나 정상 실행이 네트워크 검증을 대신하지 않는다.
- 부모 검증기의 배열 전체 적재는 기본 용량·옵션·dtype 시험에서 측정했지만, 부모에 별도 Job 메모리 제한을 둔 것은 아니다. 256 MiB 이상 입력·2 GiB 근처 입력, 여러 채널·다른 형상·그 밖의 dtype/처리 설정 조합은 이번 실측 범위 밖이다. 대용량 스트리밍은 지원하지 않는다. 용량 확대 시험은 보류하며 실제 필요한 입력 규모에 따라 별도 판단한다.
- API의 일부 미리보기/적용 기대값이 선택 인자인 상태다. 현재 화면 호출은 전달하며 서버 필수화는 후속이다.
- 특징별 영향·clipping 수 등 원본과 독립 대조하지 않은 worker 통계는 검증 범위를 표시한다.
- 큰 재시도 이력/내용의 크기 상한과 참조되지 않는 분리 파일의 수동 정리 정책은 남아 있다. 자동 삭제하지 않는다.
- 일반 재접속·백그라운드 취소/복구, 모든 과거 단계의 읽기 전용 검증은 지원하지 않는다.
- 개인 테스트 선택기는 참고용이며 낮음 지적 4건은 보류다. 프로젝트 완료 판정 근거로 사용하지 않는다.

후속 순서는 [설계의 후속 범위](DESIGN.md#후속-범위)를 따른다. 사용법·계약·지원 범위가 바뀔 때 해당 문서만 갱신하며 날짜별 작업 절·중복 검증 이력을 추가하지 않는다.
