# 모듈 파이프라인 설정·정적 검증

## LLM의 분할·전처리 후보·적용 제안 확장 설계 — 2026-10-19

상태: **설계이며 미구현**. 현재 LLM은 품질·결측·상관 분석만 제안한다. 이 절은 기존 CSV·WM 실행이나 정보 전달 권한을 변경하지 않는다. 첫 확장은 CSV workflow로 한정하고, WM·pickle·이미지의 자연어 제안은 별도 단계로 둔다. 화면은 기존 공통 5단계를 사용하고 전처리 코어를 복제하지 않는다.

### 1. 현재 코드에서 달라지는 경계

| 현재 구성 | 현재 한계 | 확장 방식 |
| --- | --- | --- |
| `llm_proposal.py`의 `ALLOWED`·공개 설명·응답 스키마 | 품질·결측·상관 분석 3개 고정 | 검토된 정적 명세에서 요청별 공개 작업·설정 스키마를 구성 |
| `llm_proposal_contract.py` | `module_pipeline_v1` 계산 계획과 WM 계획을 검사 | CSV 승인 workflow용 별도 검증 분기·제안 버전 추가 |
| `agent_module_registry.py` | 계산 모듈·WM 계약 조회 | 계산 모듈을 CSV 승인 작업인 것처럼 등록하지 않음 |
| `workflow_service_registry.py`·`csv_workflows.json` | CSV 5개·WM 8개 UI 서비스 목록 | 검토된 공개 제안 명세와 정확한 서비스 ID·버전을 결합 |
| `csv_workflow_creation.py`·`CsvWorkflowService` | 명시적 사용자 입력으로 생성·실행 | 로컬에서 바인딩한 설정으로 기존 미리보기·생성·승인·결과 경로 재사용 |
| `preparation_module_plan.py` | 후보 산출·별도 승인 적용의 고정 2단계 | LLM 설정을 기존 계획 검증기에 넘김. 후보 검토·적용 승인 경계는 유지 |

`csv_prepare_candidate`는 UI 승인 작업 ID이고 `tabular_prepare_propose`는 코어 변환 계약 ID다. 둘을 섞거나 `ALLOWED`에 이름만 추가하지 않는다. 서비스 조회는 기존 고정 라우터로 수행하고 모델이 반환한 Python import 경로·함수명·CLI 명령으로 실행하지 않는다.

### 2. LLM과 로컬 실행 계층의 역할

LLM은 사용자가 요청한 작업 종류·설정·논리 순서만 제안한다. 로컬 계획 검증기가 등록 명세·입출력 포트·설정·선행 조건을 확인하고, 입력 바인더가 사용자가 선택한 파일·프로파일·완료 기록과 결합한다. 사용자가 검토한 뒤 기존 실행 관리자가 각 승인 범위만 실행한다.

```text
요청·추가 질문 → LLM의 논리 workflow 제안
                         ↓ 실행·파일 접근 없음
정적 계약 검증 → 로컬 입력·선행 결과 결합 → 공통 UI의 제안 검토·작업 미리보기
                         ↓ 아직 실행 승인 아님
단계별 사용자 승인 → 기존 서비스·AppContainer/Job → 기존 결과 검증
                         ↓ 다음 승인 지점에서 정지
로컬 표·그림·후보 보고서·전처리 결과 표시
```

LLM은 분할 배정·제거 센서 목록·중앙값·스케일 통계를 계산하거나 확정하지 않는다. 이들은 코어가 허용된 입력에서 산출한다. 후보 기준은 Train에서만 산출하고 적용 단계는 저장된 기준만 사용한다. 분류기 학습·하이퍼파라미터 탐색·모델 성능 최적화는 전처리 에이전트의 범위가 아니다.

### 3. 제안 계약과 등록 명세

기존 `llm_proposal_v1` 분석 경로·저장 제안은 유지한다. 새 제안은 **`llm_workflow_proposal_v1`(정적 계약 구현, 모델·실행 미연결)**로 구분해 기존 분석 worker가 해석하지 못하도록 한다. `proposed`에는 workflow와 빈 질문 목록, `needs_clarification`에는 `workflow:null`과 미해결 질문만 허용한다. 지원되지 않는 사용자 요청은 질문·지원 범위 안내로 돌리고, 로컬 검증기가 미지원 모듈을 포함한 제안을 거부한다.

공개 작업 명세에는 ID·정확한 버전·일반 설명·허용 설정 JSON Schema·논리 입출력·필수 선행 작업·승인 종류를 둔다. 실제 데이터·경로·해시·완료 여부를 읽어서 설명이나 허용 목록을 자동 생성하지 않는다. 공개 대상 여부와 버전은 검토한 정적 등록 정보이며, UI에 등록됐다는 이유로 모든 작업을 자동 공개하지 않는다. UI 명세와 별도 설명을 중복 하드코딩하지 않도록 기존 workflow 명세에 공개 설명을 연결하고, 서명 범위·검증기를 함께 정한다.

예정 응답의 정확한 필드는 다음과 같다. 기존 JSON 중복 키·NaN·Infinity 거부, UTF-8 64 KiB 상한을 유지하며 알 수 없는 필드는 거부한다.

| 위치 | 필수 필드·조건 |
| --- | --- |
| 최상위 | `schema_version`, `status`, `workflow`, `questions`만 허용 |
| `workflow` | `workflow_id`, `steps`만 허용. 첫 CSV 버전은 작업 1~5개, 선형 순서, 정확한 서비스 ID·버전 사용 |
| 각 step | `step_id`, `module_id`, `version`, `inputs`, `settings`, `depends_on`을 명시 |
| 질문 | 최대 5개·각 500자. 미해결 질문과 확정 workflow를 함께 반환하지 않음 |

허용한 입력 포트·참조와 설정의 정확한 키는 공개 작업별 스키마가 정의한다. 중복 step·순환·뒤 단계 참조·필수 선행 작업 누락·같은 역할을 중복 수행하는 계획은 거부한다. 정적 계획을 통과해도 실제 출처·상태·자원 적합성은 로컬 바인딩에서 별도로 확인한다.

모델에는 `source.selected_input`, `split.confirmed`, `export.development`, `candidate.saved` 같은 **고정 논리 참조**만 허용한다. 이는 목표 입출력 연결이지 실제 완료 증거가 아니다. 데이터 경로·작업 이름·UUID·원본 해시·DB ID는 로컬 바인더에만 둔다. 모델이 실제 후보 해시나 실행 ID를 만들어 반환하면 거부한다.

UI 생성 스키마에는 실제 경로·기존 작업 이름·로컬 설정 파일 선택 항목이 있으므로 이를 그대로 모델에 전달하지 않는다. 공개 제안용 스키마는 명시적 투영·허용 목록으로 구성하고, 로컬 입력 항목과 모델이 제안 가능한 일반 설정을 분리한다.

설정의 출처는 사용자 명시 값 또는 사용자가 선택한 기본 설정이다. 생략된 값을 모델이 임의 정책으로 결정하지 않는다. 로컬 정규화 단계에서 기본값을 채운 경우 사용자 값과 구분해 제안 검토 화면에 전부 표시하고, 정규화된 유효 설정을 계획 식별값에 포함한다. 설정이 충돌하거나 선택되지 않았다면 가장 앞선 미결정 항목부터 질문한다.

### 4. 허용 작업과 순서

| 논리 작업 | 재사용할 승인 서비스 | 필수 선행 증거·승인 |
| --- | --- | --- |
| 품질·EDA·분할 제안·확정 | `csv_split_review` | 사용자가 선택한 CSV·프로파일. 기존 품질·EDA·검토·제안·확정 승인 유지 |
| 개발 구간 내보내기 | `csv_partition_export` | 검증된 확정 분할. Train·Validation만 내보내기 |
| 전처리 기준 후보 산출 | `csv_prepare_candidate` | 같은 출처의 분할·내보내기. Train만 전달하고 새 승인 |
| 저장 기준 적용 | `csv_prepare_apply` | 커밋된 후보·사용자 후보 검토·새 적용 승인 |
| 로컬 전달 묶음 | `csv_local_handoff` | 검증된 적용 완료. 사용자가 요청한 경우만 별도 승인 복사 |

첫 구현의 전체 흐름은 위 순서를 따르는 선형 계획이다. 내보내기는 후보 산출의 필수 선행 작업이므로 제안에 명시하고 사용자 검토 화면에서도 보인다. 전달은 선택이며 자동으로 추가하지 않는다. 앞 단계만 실행하거나, UI에서 연결한 기존 완료 증거를 이용해 후보 산출·적용부터 시작하는 것도 허용하되 같은 출처·구간·후보 연결을 로컬에서 검증한다. 필요한 선행 단계가 빠졌다고 실행 중 몰래 추가하거나 이름 검색으로 대체하지 않는다.

분할에는 기존 `SplitRules`의 random·group·time과 비율·난수 시드·stratify·클래스 조건·시간 형식을 사용한다. group·time은 로컬 프로파일의 역할 지정이 필요하며 시간·그룹 컬럼을 모델이 추측하지 않는다. time/group와 stratify의 잘못된 조합·비율 합 불일치 등은 기존 검증기로 거부한다. 요청이나 선택된 기본 설정으로 정해지지 않은 분할 방식·비율은 확인 질문 대상이다.

후보 설정은 기존 `PreparationRules`·모듈 설정 스키마에서 허용하는 특징 제거·대치·스케일링·이상치·범주화·인코딩만 노출한다. 첫 구현은 이미 검증된 기능만 공개하고 임의 함수·표현식·Python 코드를 허용하지 않는다. 적용 작업에서는 같은 통계를 다시 산출하거나 새 설정으로 후보를 바꿀 수 없다. 바꾸려면 새 후보와 검토·승인이 필요하다.

### 5. 예시와 실행 시 사용자 확인

예시 요청: “시간순으로 70·15·15로 나누고, Train에서 결측률 50% 초과 특징과 상수 특징을 제거할 기준을 만든 뒤 중앙값 대치해 주세요. 스케일링은 하지 않고 Train·Validation에 적용해 주세요.”

로컬 검증을 통과한 제안의 사용자 표시 형태는 다음과 같다. 실제 행·컬럼·통계는 모델이 보거나 정한 값이 아니다.

1. 품질·EDA·시간순 분할: 70·15·15. 시간 역할과 형식은 로컬 프로파일에서 결합.
2. 확정 분할에서 Train·Validation 내보내기. 원본·기존 ML 분할 보존.
3. Train 기준 후보: 결측률 `> 0.5`·상수 특징 제거, 중앙값 대치, 스케일링 없음.
4. 후보 보고서 로컬 검토 후 저장 기준 적용. 기준 재산출·Test 적용 없음.

전체 제안 검토나 작업 생성은 실행 승인으로 간주하지 않는다. 분할 작업 내부의 기존 승인, 구간 내보내기 승인, 후보 산출 승인, 후보 보고서 검토, 적용 승인을 그대로 유지한다. 기본 화면 갱신·완료 조회·다음 단계 표시만으로 승인·모델 호출·worker 실행이 반복되지 않아야 한다.

기본 품질 정책에서 높은 결측률이 검토 필요로 판정되면 위 예시도 그대로 중단할 수 있다. “제거해 달라”는 자연어 요청을 품질 검토 해제·ignore 설정의 승인으로 바꾸지 않는다. 기존 UI의 특징 결측·상수 통지 처리 설정처럼 허용된 선택이 필요하면 사용자에게 별도 로컬 확인을 요청한다. 차단을 풀기 위해 Test 사용·그룹 경계 해제·자동 재라벨링을 제안/실행하지 않는다.

### 6. 정보 전달·상태 관리·무효화

현재 정보 전달 정책은 유지한다. 모델에는 사용자가 전송을 확인한 문장과 검토된 정적 공개 명세·설정 스키마만 전달한다. 원본·샘플 행·실제 컬럼명·분포·결측률·통계·그림·로컬 경로·실행 ID·출처 해시·오류 원문은 자동 첨부하지 않는다. 사용자가 자유 문장에 직접 적은 민감 정보가 자동으로 익명화된다고 보증하지 않으며 전송 미리보기를 유지한다.

로컬 보고서의 수치를 보고 사용자가 설정을 결정할 수는 있다. 그러나 품질 검사 결과나 오류를 모델에 자동 재전송해서 다음 계획을 생성하지 않는다. 미지정 시간 역할·그룹 역할·출처 불일치는 로컬 고정 안내로 설명하고, 사용자가 직접 새 문장을 보내는 경우도 별도 전송 확인을 받는다. 상태가 바뀔 때마다 LLM이 다음 단계를 고르는 방식 대신 검증된 로컬 계획으로 진행한다.

제안 식별값은 공개 설정·정확한 작업 버전·순서·기본값을 포함한다. 실행 바인딩은 여기에 로컬 snapshot·프로파일·분할·후보·코드·자원·행 연결 증거를 추가한다. 둘은 별개이며 모델이 만든 문자열을 실제 승인 범위 ID로 사용하지 않는다. 입력·계획·설정·모델·후보·선행 결과·자원 변경 시 해당 미리보기와 미사용 승인 연결을 무효화한다. 소비 승인·완료 결과는 보존하고 덮어쓰거나 재사용하지 않는다.

### 7. 기존 공통 UI와 구현 순서

기존 화면의 1 요청 대화 → 2 제안 검토 → 3 로컬 입력·생성 설정 → 4 단계별 승인·실행 → 5 로컬 결과를 유지한다. workflow 전체의 현재 작업과 다음 승인 지점을 표시하고, 각 단계는 명세로 선택한 기존 `CsvWorkflowService`에 연결한다. 모듈마다 새 화면·새 계산 코드·LLM 호출기를 추가하지 않는다. 기존 EDA 제안 v1과 등록 모듈 수동 실행 경로도 유지한다.

#### B 구현 기록 — 2026-10-20

`llm_workflow_proposal.py`가 자연어 문장·허용 공개 작업·선택 규칙을 새 응답 스키마와 함께 기존 loopback HTTP/LangChain 운송에 전달한다. 전송 전 선택 계약을 검사하고 응답은 A 검증기로 재검사한다. 실제 경로·프로파일·원본·통계·완료 증거를 자동 첨부하지 않는다. 사용자가 자유 문장에 직접 넣은 민감 정보까지 자동 익명화하는 기능은 아니다. 전체 payload는 64 KiB 이하이며 누적 요청은 기존 4000자·UTF-8 8 KiB 제한을 공유한다.

`llm_workflow_dialogue.WorkflowProposalDialogue`는 기존 `ProposalDialogue`의 메모리 전용 LangGraph·중단/재개·호출 제한·추적 차단을 재사용한다. 공개 payload 생성·제안·재검증만 새 계약으로 교체한다. 최초 호출 포함 최대 4회이며 사용자 답변을 확인할 때만 추가 호출한다. 실패 시 세션을 종료하고 자동 재시도하지 않는다. 규칙은 독립 JSON 복사본으로 고정하므로 호출자의 dict 변경이나 모델 답변으로 변경되지 않는다. 선택하지 않은 필수 규칙은 추측하지 않고 질문 대상으로 남긴다. 질문에 답해도 고정 규칙이 바뀌지는 않으며 규칙 변경은 새 선택값으로 새 세션을 시작한다.

#### C 구현 기록 — 2026-10-20

`llm_workflow_binding.bind_workflow_step()`은 B의 `ValidatedWorkflowProposal`과 신뢰된 호출자의 허용 목록·선택 규칙, 현재 단계 ID, 로컬 생성 폼 값, `WorkerLimits`를 받는다. 제안을 다시 정적 검증하고 계획 식별값·공개 계약까지 비교한다. 확인 질문 응답은 작업에 연결하지 않는다. 원본·프로파일 경로·사용자·자원·코드 식별값과 현재 `CsvCreationPreview`를 불변 JSON에 결합한다. 생성·승인·worker 실행은 하지 않는다.

이번 제안의 앞 단계는 `completed_runs={step_id: run_name}`, 중간 시작에 명시한 기존 입력은 `existing_runs={logical_reference: run_name}`으로 전달한다. 필요한 키만 정확히 허용한다. `csv_workflow_binding_evidence.completed_workflow()`는 기존 서비스의 완료 결과·파일 해시·승인 소비·커밋·도메인 검사를 재사용하며 취소·차단·미완료를 거부한다. 같은 원본이라는 이유만으로 연결하지 않고 확정 분할·내보내기 marker·Train 계약·후보·적용 상태의 정확한 식별값을 비교한다. 과거 제안 단계의 규칙도 실제 완료 작업과 같아야 한다.

분할 프로파일의 전체 유효 `SplitRules`와 후보 모듈 계획의 전체 유효 `PreparationRules`는 제안 설정과 같아야 한다. 파일을 자동 수정하거나 모델 기본값으로 덮어쓰지 않는다. 현재 생성 입력의 부모 작업 이름과 native 미리보기의 부모 증거도 검증한 논리 참조와 대조한다. 후보가 아직 없으면 적용 작업을 준비하지 않는다. 후보 완료 후 새 바인딩에서 실제 후보 식별값·보고서 경로를 결합하며 적용 작업 준비 확인은 기존 후보 검토 경계를 사용한다. 적용 실행 승인은 여전히 별도다.

`create_bound_step(binding, confirmed=True)`는 사용자 확인 뒤 전체 바인딩을 다시 만들고 비교한 다음 기존 `CsvWorkflowService.create()`만 호출한다. 파일·설정·선행 결과·후보·자원·코드가 변경되거나 동일 작업이 이미 생성됐으면 중단한다. 기존 서비스 자체의 생성 전 재검사·잠금도 유지한다. 반환값에는 계획·바인딩 식별값과 `execution_approval_issued:false`, `worker_started:false`를 포함한다. 승인 발급·승인 소비·`next()` 호출·자동 후속 단계 준비는 하지 않는다.

로컬 API 사용 순서는 다음과 같다. `values`는 현재 모듈의 기존 `creation_schema()`와 같은 폼 값이고 `selected_settings`는 B에서 사용자가 고정한 규칙이다.

```python
binding = bind_workflow_step(
    validated_proposal,
    allowed_modules=allowed_modules,
    selected_settings=selected_settings,
    step_id=selected_step_id,
    values=local_form_values,
    limits=worker_limits,
    completed_runs=completed_step_names,
)
# 화면에서 binding.packet을 로컬로 검토한 뒤 별도 생성 확인을 받는다.
created = create_bound_step(binding, confirmed=True)
# 생성된 작업의 실행은 기존 서비스의 단계별 승인 절차를 따른다.
```

범위: 바인더는 원본을 분석하거나 LLM에 호출·전송하지 않는다. 기존 생성 서비스가 사용자 확인 후 snapshot 바이트를 복사하고 로컬 작업 메타데이터를 저장할 수 있다. C 시점에는 바인딩 JSON 저장·재개 UI·workflow 전체 진행 제어를 추가하지 않았으며 이후 D의 구현은 아래를 따른다. 기존 제안 CLI는 작업 생성에 자동 연결하지 않는다. `binding_id`는 보안 서명이 아니라 로컬 범위 식별값이다. 원본·경로·행 연결 정보가 있는 `binding.packet`을 제안용 LLM payload나 외부 추적으로 보내지 않는다. 사용자 실데이터·기존 승인·기존 작업은 이번 검사에서 재실행하지 않는다.

검증: 신규 바인더 13개, 기존 제안·정적 계약·LangGraph·LangChain 88개, UI 대화·저장·handoff·CSV UI 32개로 총 133개 통과. 신규 검사는 합성 CSV의 분할 → 내보내기 → 후보 → 적용 → 전달을 기존 승인 실행기로 연결하고 OS 운송만 모의했다. 입력 보존, 단계별 별도 승인, 후보 보고서·실제 해시 결합, 중간 적용 시작, 미완료 부모·설정 불일치·변조 산출물·충돌 계보·native 부모 불일치·자원 변경·기존 생성 재사용 차단을 확인했다. 실제 AppContainer·Qwen·GPU 실행이나 사용자 원본 처리는 수행하지 않았다. 전체 에이전트 회귀를 다시 수행한 결과는 아니며 D·E가 남아 있다.

#### D 구현 기록 — 2026-10-20

사이드바의 `LLM 제안` 안에서 `품질·EDA`와 `CSV 분할·전처리`를 선택한다. 별도 화면 수를 늘리지 않고 기존 1 요청 → 2 검토 → 3 입력 → 4 승인 → 5 결과 화면을 사용한다. `csv_plan_view.py`는 제안·검토·단계 선택만 담당하고 입력 폼·생성 잠금·승인·결과 표시·로컬 해설은 기존 공통 UI를 재사용한다. `csv_plan_service.py`의 `CsvPlanDialogue`는 기존 모델 명령의 SQLite 단일 소비·설정 지문 검사에 새 workflow 응답 검증만 연결한다. 화면 갱신은 모델 전송이나 worker 실행이 아니다.

사용 순서:

1. `1 요청·대화`에서 공개 예제 규칙 JSON의 전체 유효값을 검토·편집하고 `이 규칙으로 새 대화 준비`를 누른다. 예제는 입력 적합성 보증이 아니며 규칙 변경은 새 대화가 필요하다.
2. 요청 문장 → `CSV 전송 내용 미리보기` → 실제 공개 규칙·문장을 확인하고 전송에 동의한다. 확인 질문도 별도 전송 확인을 받는다. 원본·경로·통계를 자동 첨부하지 않는다.
3. `2 제안 검토`에서 순서·규칙을 검토하고 새 이름으로 저장한다. 요청·답변 원문이나 미해결 질문은 저장하지 않는다.
4. `3 입력 선택`에서 현재 작업의 원본·프로파일·계획·자원을 선택하고 생성 범위 검사 후 작업만 준비한다. 분할 프로파일·후보 계획의 유효 규칙은 제안과 정확히 같아야 하며 파일을 자동 수정하지 않는다. 검증된 선행 작업 이름은 다음 폼의 기본값으로 연결한다.
5. `4 실행 승인`에서 기존 승인 중심 진행기를 사용한다. 각 승인 지점에서 확인하며 중단·실패는 자동 재시도하지 않는다. 적용 전에는 검증한 후보 보고서의 제한된 로컬 표시 복사본과 별도 검토 확인을 제공한다.
6. 완료 후 `완료 증거 확인·다음 작업 준비`는 선행 결과를 다시 검증하고 다음 빈 폼만 선택한다. 새 작업을 생성하거나 실행하지 않는다. `5 결과 확인`은 기존 파일·해시·표시 계약을 통과한 결과를 보여준다.

`llm_workflow_store.py`는 `logs/agents/llm_workflows/<사용자 이름>/`에 고정 `plan.json`, 단계별 `*.intent.json`, `*.created.json`을 배타 생성한다. 제안·선택 규칙·계획 지문·연결 코드와 로컬 바인딩·작업 식별값을 보존한다. 파일당 64 KiB, 엄격한 JSON, 링크·덮어쓰기 거부를 적용한다. 해시는 변경 감지용이지 악의적인 로컬 관리자에 대한 진본 인증이 아니다. 경로·계정·증거를 포함하는 로컬 바인딩은 LLM·외부 추적으로 전송하지 않는다.

실제 생성 전에 intent를 기록한다. 생성 이후 receipt가 없거나 기록이 끊기면 결과 불명확으로 중단한다. 화면 갱신·재접속으로 같은 생성을 다시 수행하지 않는다. 이 경우 원래 native 작업 기록을 확인해야 하며 자동 복구·재승인 기능은 제공하지 않는다. 동시 생성은 배타 intent·기존 생성 잠금으로, UI 단계 전환은 별도 세션 잠금으로 막는다. 기존 승인 ID·모델 전송 pending·실행 pending은 보관/복원하지 않는다.

재접속 시 `1 요청·대화`의 `저장된 CSV 실행안 이름`과 `CSV 실행안 불러오기`를 명시적으로 사용한다. 저장 계획·코드·각 생성 영수증·native 작업 ID/선택/계획과 완료 산출물을 확인한다. 완료 작업은 재실행하지 않고 다음 미생성 작업 또는 현재 미완료 작업에 연결한다. 차단·실패·취소는 그 상태로 남긴다. status만 완료로 바꾼 기록은 커밋·도메인 검사에서 거부한다. 복원 자체는 모델 호출·승인 소비·worker 시작이 아니다.

초기 UI 지원 범위는 **새 분할부터 시작하는 연속 CSV 실행안**이다. 기존 분할·후보를 임의로 골라 중간 시작하는 기능은 C API에는 있지만 이번 UI에는 넣지 않았다. WM 수동 모듈 경로와 기존 EDA 제안 경로는 유지한다. 실제 Qwen·AppContainer 실행과 사용자 수동 확인, 전체 에이전트 회귀 E는 별도이며 이번 구현으로 실데이터 작업을 실행하지 않는다.

검증: 신규 9개와 기존 UI·대화 저장·handoff 회귀 85개, 총 94개 통과. AppTest로 같은 5단계 메뉴에서 규칙 선택 → 미리보기 → 확인 전송 → 제안 저장 → 입력 폼을 확인했고 rerun에 따른 모델 추가 호출·자동 작업 생성을 막았다. 합성 CSV의 5단계 기존 승인 실행·완료 후 재연결·후보 보고서 표시 복사본을 검사했다. 실패·취소·품질 차단 상태·보안 잠금·가짜 완료 상태는 다음 단계로 진행하지 않으며 설정 변경·영수증 변조·중단 intent·기존 이름 재사용은 거부했다. 기존 UI 초기 세션 값이 없는 경우의 회귀를 보완했고 CSV 실행안별 입력 위젯 키를 분리했다. 실제 모델과 네이티브 OS 운송은 모의했으며 사용자 작업을 재실행하지 않았다.

#### 고정 규칙 재질문 보완 — 2026-10-20

사용자의 명확한 5단계 요청에도 모델이 시간 컬럼 존재, 층화 분할·클래스 조건 완화, 스케일링·이상치·구간화 필요성을 다시 질문했다. 고정 규칙을 초안처럼 취급하고 일반적인 전처리 조언을 섞은 사례다. 시간순 분할에 `stratify=true`를 권하거나 binning을 범주형 변수 처리로 설명한 것도 잘못이다. 이 모델 응답은 실행 승인이나 실제 데이터 진단이 아니다.

`llm_workflow_proposal.py`의 모호한 “설정 변경이 필요하면 질문” 문구를 제거했다. `SYSTEM_INSTRUCTIONS`로 역할과 질문 조건을 분리하고 공개 문맥에 `settings_status:fixed_user_selection`, `input_validation_owner:local_validator_after_proposal`을 명시했다. 이미 선택한 `none`·`false`·`null`은 재확인 대상이 아니며, 요청 작업과 규칙이 명확하면 `proposed / questions:[]`로 제안하도록 안내한다. 시간 컬럼·형식·클래스 분포·실제 분할 가능성은 로컬 검증에 맡기되 통과했다고 추측하지 않는다. 기본 규칙 변경·조건 완화·미요청 최적화 조언을 하지 않도록 했다.

작업 종류 미정, 요청 작업의 규칙 누락, 사용자의 명시적 변경 요청과 고정 규칙 충돌, 미지원 작업은 여전히 확인 질문 대상이다. 규칙은 UI에서 다시 선택하고 새 대화를 시작해야 하며 모델 답변으로 변경하지 않는다. 기존 정적 검증·승인·Test 금지 정책은 변경하지 않았다.

사용자의 5단계 요청과 전체 허용 목록을 회귀 입력으로 추가했다. 프롬프트의 고정 규칙/로컬 검증 책임 표시, 잘못된 변경 권고 금지, 실제 미정 요청의 질문 유지 및 기존 대화·UI 전송/저장을 확인했다. 범위 검사 **중복 제외 133개 통과**(90개와 62개 실행에서 공통 19개 제외). 실제 모델 운송은 모의했으므로 Qwen이 재질문을 하지 않는다는 보증이나 실제 모델 개선 측정은 아니다. 앞선 940개 전체 회귀는 이 프롬프트 보완 전 기록이며 이번에는 전체 회귀를 재실행하지 않았다.

재확인은 UI 서버 재시작 후 새 CSV 대화에서 같은 요청을 전송한다. 진행 중인 이전 대화는 기존 시스템 문맥을 포함하므로 그대로 이어 쓰지 않는다. 프롬프트 파일도 기존 바인딩 코드 식별값에 포함되어 있어 이전에 저장한 CSV 실행안은 변경된 코드로 자동 복원하지 않는다. 새 제안은 새 저장 이름을 사용하며 기존 native 작업·결과·승인 기록은 변경하거나 재실행하지 않는다.

필수 거부 사례: 분할 전 전체 입력에서 중앙값 산출, Validation/Test에서 기준 산출, Test 적용, 출처가 다른 후보 재사용, 누락 선행 작업·임의 실행 코드·미등록 버전, 품질 blocker 우회, 모델이 승인·완료·통계·해시를 위조한 응답. 대응은 정적 거부 또는 로컬 검토 중단이지 모델의 자체 검증 판정이나 자동 재시도가 아니다.

이번 설계는 [선택형 정보 전달·결과 해설](LLM_COMMENTARY_REVIEW.md)과 별개다. 그 기능을 먼저 구현하지 않아도 데이터 비공개 상태에서 실행안 제안 확장을 진행할 수 있다.

## 초기 계산 파이프라인 구현 기록 — 2026-10-16

구현일: 2026-10-16. 모듈 개발 3~4번의 설정 형식·순서·입출력 연결 검증이다. 이 파일의 정적 검증은 데이터를 실행하지 않는다. 별도 [승인·worker 연결](../guides/MODULE_PIPELINE_EXECUTION.md)은 CSV 분석·검사에 한해 구현·합성 검증했으며 새 진입점의 실제 OS 실행은 확인 전이다.

## 파일 구성

- `src/preprocessing/pipeline.py`: 엄격한 JSON 읽기·등록부 조회·설정 검증·순차 계획 생성.
- `configs/agents/pipelines/tabular_eda_example.json`: 품질 검사 → 결측 분석 → 상관분석 예제. 데이터 경로·컬럼명·원본 값은 포함하지 않는다.
- `tests/agents/test_module_pipeline.py`: 정상 설정·미등록 ID·순환·계약 불일치·파일 제한·계획 식별값 테스트.

## 설정 구조

```json
{
  "schema_version": "module_pipeline_v1",
  "pipeline_id": "missing_only",
  "input": {
    "contract_id": "tabular_data",
    "contract_version": 1,
    "partition": "unsplit"
  },
  "steps": [
    {
      "step_id": "missing",
      "module_id": "eda_missing",
      "version": "1.0.0",
      "inputs": {"data": "source.data"},
      "settings": {},
      "depends_on": []
    }
  ]
}
```

| 항목 | 의미 |
| --- | --- |
| `pipeline_id` | 로컬 계획 이름. 파일 경로·명령이 아님 |
| `input` | 공통 입력의 논리 계약과 선언한 구간. 초기에는 tabular_data v1만 지원 |
| `step_id` | 이 계획 안에서 고유한 단계 이름. 같은 모듈을 여러 번 선택해도 단계 ID는 달라야 함 |
| `module_id`, `version` | 등록된 기능과 정확한 버전. 임의 함수 경로·latest 금지 |
| `inputs` | 입력 포트와 출처 연결. 최초 입력은 `source.data`, 앞 단계 출력은 `<step_id>.<port>` |
| `settings` | 모듈에서 허용한 설정. 생략 시 등록된 기본값 검증 |
| `depends_on` | 앞서 완료되어야 하는 단계 ID. 생략 가능하며 출력 참조도 의존성에 자동 포함 |

단계는 `steps`에 적은 순서 그대로 실행하도록 계획한다. 자동 재정렬하지 않는다. 모든 EDA는 원본을 바꾸지 않으므로 결측 분석 다음의 상관분석도 같은 `source.data`를 읽는다. `missing.result`는 결측 통계 표이지 변환된 원본이 아니므로 다음 EDA의 데이터 입력에 연결하면 계약 불일치로 거부한다.

품질 검사는 필요에 따라 포함할 수 있다. 이를 선택하지 않아도 EDA 코어의 필수 입력 구조 검사는 생략되지 않는다. 배포 예제는 품질 검사를 먼저 배치했다. 품질 결과가 검토 필요·차단이면 이후 실행을 중단해야 한다는 정책을 계획에 고정하며 설정으로 해제할 수 없다. 실제 상태 확인·중단 처리는 후속 실행 관리자 연결에서 강제한다.

## 검증 규칙

- 설정은 64 KiB 이하, 단계는 1~32개. 알 수 없는 필드·중복 JSON 키·NaN·Infinity는 거부한다.
- 단계 ID 중복·예약어 `source`·미등록 모듈·미지원 버전·허용되지 않은 설정을 거부한다.
- 필수 입력 포트 누락·미등록 포트·존재하지 않는 출력·입출력 계약 ID/버전 불일치를 거부한다.
- 자기 참조·뒤 단계 참조·순환·중복 의존성을 거부한다. 임의 DAG 실행이나 병렬 스케줄링은 하지 않는다.
- 모듈 선행 조건은 지원하는 고정 검사 코드만 허용하고 계획의 계약 정보에 보존한다. 설정만 보고 실제 검사가 통과했다고 간주하지 않는다.
- Train 전용 기준 산출 모듈이 연결되는 경우 `partition=train`이 아니면 거부한다. 현재 내장 목록에는 변환 모듈이 없으며, 선언만으로 실제 행의 Train 역할을 증명하지 않는다.

## 결과와 식별값

`PipelinePlan`에는 순서·연결·입력 구간·모듈 계약·사용자 설정·기본값을 적용한 유효 설정을 보존한다. 문자열 JSON과 tuple로 저장해 원래 설정 dict가 바뀌어도 기존 계획은 바뀌지 않는다. `signature`는 이 정보를 SHA-256으로 식별하며 키 순서에는 영향을 받지 않는다.

이 식별값은 **설정 계획 식별값**이다. 데이터 출처·snapshot·코드 해시·OS 격리·승인에 결합된 실행 ID가 아니며 보안 서명도 아니다. 실행 연결 단계에서 기존 실행 관리자의 증거·승인 범위에 함께 결합해야 한다. 입력 파일 경로·원본 데이터·API 키는 설정에 추가하지 않는다.

## 확인 방법

프로젝트 루트에서 실행한다. 아래 명령은 설정만 읽고 데이터나 worker는 실행하지 않는다.

```powershell
python -c "from src.preprocessing.pipeline import load_pipeline; p = load_pipeline('configs/agents/pipelines/tabular_eda_example.json'); print('설정 검증 완료:', p.pipeline_id); print('단계:', [s.step_id for s in p.steps]); print('계획 식별값:', p.signature)"
python -m unittest tests.agents.test_module_pipeline -v
```

검증된 계획의 승인·상태·취소·격리 실행 연결은 [별도 실행 문서](../guides/MODULE_PIPELINE_EXECUTION.md)를 따른다. 새 실행 경로의 실제 OS 검증은 확인 전이다. 과거 보고서·노트북·데이터와 현재 고정 CLI는 변경하지 않는다.
