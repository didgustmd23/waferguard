# CSV 지속 작업 에이전트 재설계

작성일: 2026-10-20 · 상태(2026-10-22 갱신): **표형(CSV) 통합 작업은 7절 구조(G1)로 구현했고, 7.13~7.23 보완까지 구현·합성 검증했습니다.** 실제 환경 확인 범위와 미검증·후속 순서는 [7.24절](#724-현재-상태검증-구분후속-순서--2026-10-22)에 모았습니다. 배열·이미지 통합 연결, 웨이퍼 프로파일 연결, 시간 처리 지원, 일반적인 중단 후 재개(P3)는 미구현입니다. 2026-10-21부터 목표를 **범용 전처리 에이전트**로 정정했고, 공통/유형별 구조는 [7절](#7-범용-전처리-에이전트-구조-재설계--2026-10-21-설계-기준-g1-구현됨)이 기준입니다. 0~5절과 7절이 다르면 7절을 따릅니다. 5.1~5.5절은 구현 당시 기록으로 보존합니다. 이 문서가 재설계의 단일 기준 문서입니다. 결정이 바뀌면 이 문서의 해당 절을 고치고 맨 아래 변경 이력에 한 줄 남깁니다. 버전별 사본은 만들지 않습니다.

## 0. 목표와 범위

**목표:** 사용자가 CSV 파일과 목표 문장만 주면, 에이전트가 필요한 결정만 묻고 다음 순서를 하나의 지속 작업으로 이어 갑니다.

> 입력 선택 → 진단 → 처리안 → 승인 → 전처리 → 최종 보고서

사용자는 작업 이름·경로·선행 작업을 직접 연결하지 않습니다.

- **역할 분담**
  - LLM: 진단 해석, 역할·기준 초안, 처리안, 문제 해결안, 최종 해설
  - 기존 실행기: 계산, 결과 검증, 격리, 승인 기록
- **이번 범위:** 표형 CSV 한 개, 개발 데이터 분할(Train·Validation·Test)부터 전처리 적용·로컬 전달까지(기존 CSV 작업 5종)
- **범위 밖:** WM-811K·pickle·이미지 입력, 모델 학습, 여러 CSV 결합. 이후 같은 구조로 확장합니다.
- **2026-10-21 정정:** CSV는 첫 검증 대상입니다. 작업 조정·상태·승인·공통 UI·질문·문제 처리·보고는 공통 책임이고, 로딩·진단·결정 항목·변환 계산·결과 요약은 입력 유형 어댑터 책임입니다(7절).
- **새 실행 체계를 만들지 않습니다.** 기존 서비스 API를 호출하는 작업 조정기를 중심으로 작업 기록·동의·LLM 보조·공통 UI·보고서를 연결합니다. 별도 worker·운송·계산 엔진을 복제하지 않습니다.

## 1. 사용자가 보는 흐름

화면은 네 영역만 둡니다. 기술 정보(경로, 해시, 승인 범위 원문, 코드 식별값)는 각 영역의 `기술 상세` 접기 안에 둡니다.

| 영역 | 내용 |
| --- | --- |
| 요청 | 파일 선택, 목표 문장, 작업 시작 |
| 진행 상황 | 현재 단계 한 줄, 완료 단계 목록, 진행 중 표시 |
| 필요한 결정 | 지금 사용자가 정할 것 하나와 그 근거·추천안·수정 칸 |
| 최종 결과 | 보고서, 생성 파일 목록, 해설 |

### 1.1 정상 흐름

| # | 사용자가 보는 것 | 에이전트가 자동으로 하는 것 |
| --- | --- | --- |
| 1 | 파일 선택, 목표 입력(예: "생존 예측용으로 분할·전처리해 줘"), `작업 시작` | — |
| 2 | **결정 A — 작업 동의.** 무엇을 읽고 만들지, 모델에 무엇을 보낼지, 자원 상한, 원본을 바꾸지 않는다는 점, 이후 자동 진행 범위를 한 화면에서 확인 | 동의 기록 저장 |
| 3 | "입력 확인·진단 중" | snapshot 복사 → 헤더 점검 → (필요 시 중복 컬럼명 정비) → 격리 진단 → 부모 검증 |
| 4 | **결정 B — 역할·기준 확인.** 진단 해석 요약, 역할 초안 표(근거 한 줄씩), 결측·상수 컬럼 처리 초안. 그 자리에서 고치고 `확정` | 로컬 LLM에 진단 집계 전달 → 해석·역할 초안 생성 → 프로파일 계약 검사 |
| 5 | "처리안 작성 중" | 프로파일 저장(자동 이름) → LLM 처리안(분할·전처리 규칙) → 기존 제안 계약 검증 |
| 6 | **결정 C — 처리안 승인.** 분할 방식·비율, 전처리 규칙, 예상 산출물, 단계 목록을 요약 표로 표시. 수정 후 승인 가능 | 처리안 저장 |
| 7 | "분할·내보내기·전처리 후보 작성 중" | 품질 검사 → EDA → 분할 제안 → 분할 확정 → 개발 구간 내보내기 → Train 기준 전처리 후보 산출. 각 단계는 작업 생성, 사전 검사, 승인 기록, 격리 실행, 검증 순서로 진행 |
| 8 | **결정 D — 전처리 적용 승인.** 후보 보고서 요약(변환 규칙, 제거 컬럼, 출력 크기)과 LLM 요약 | — |
| 9 | "전처리 적용·전달 묶음 작성 중" | 적용 → 로컬 전달 묶음 → 결과 검증 |
| 10 | **최종 결과.** 보고서(입력·진단·결정·처리 이력·산출물), LLM 해설, 산출물 위치 | 보고서 조립 → 해설 생성 |

A~D는 필요한 결정의 종류이며 버튼 네 번을 강제하는 화면 단계가 아닙니다. 역할·기준과 처리안을 함께 검증·표시할 수 있으면 B·C를 한 화면의 한 번의 확인으로 묶습니다. 역할 변경으로 처리안을 다시 계산해야 하면 수정 화면 안에서 갱신하며 별도 작업 준비 버튼은 만들지 않습니다. A는 작업 시작과 합칠 수 있고, D는 실제 후보를 확인한 뒤 받습니다. 확인 사이 진행은 모두 자동입니다.

### 1.2 문제 발생 흐름

어떤 문제든 "필요한 결정" 영역에 **원인 한 줄 + 해결안 + 바로 고칠 수 있는 칸**이 함께 나옵니다. 사용자가 고치면 에이전트가 필요한 새 내부 작업을 만들어 이어서 진행합니다.

| 상황 | 사용자가 보는 것 | 에이전트 동작 |
| --- | --- | --- |
| 중복 컬럼명 | "zero가 19번 사용됨. 번호를 붙인 복사본으로 진행할까요?" `복사본으로 진행` / `파일 다시 선택` | 동의하면 정비 → 파생 입력 → 진단 재개. 결정 A에서 미리 허용했으면 묻지 않고 진행 후 안내만 표시 |
| 빈 컬럼명·깨진 CSV | 고정 사유와 "파일을 고친 뒤 다시 선택"만 표시 | 자동 수정하지 않음 |
| 품질 검토(상수·높은 결측 등) | 해당 컬럼 목록과 LLM 해결안(예: "상수 19개 제외"), 역할 표를 그 자리에서 수정 | 새 프로파일 저장 → 새 분할 작업 자동 생성 → 이어서 진행. 이전 작업은 보존 |
| 분할 조건 불충족(클래스 부족 등) | 원인과 대안(비율·계층 분할 끄기 등)을 처리안 수정 칸으로 표시 | 수정 처리안을 다시 검증하고, 새 작업으로 재개 |
| 격리 실행 실패·시간 초과·권한 | 고정 실패 코드의 쉬운 설명, `같은 조건으로 다시 시도` / `자원 상한 늘려 다시 시도` | 자동 재시도하지 않음. 사용자가 고르면 새 작업·새 승인 기록으로 재실행 |
| 모델 응답 실패·형식 오류 | "처리안을 만들지 못했습니다" `다시 요청` / `직접 입력` | 한 번 실패한 요청은 자동 재전송하지 않음 |
| 원본 파일만 바뀜 | "원본은 변경됐지만 이 작업은 선택 당시 복사본을 사용합니다". 필요하면 `새 내용으로 새 작업` 제공 | 승인한 snapshot·파생 입력이 온전하면 기존 작업을 계속함. 원본을 조용히 다시 읽거나 교체하지 않음 |
| 실행 입력이 바뀜 | "작업에 사용 중인 복사본이 변경되어 중단했습니다" | snapshot·파생 입력 변조 시 후속 실행과 위임 차단. 새 입력은 새 작업·동의로 시작 |
| 코드 업데이트 후 재개 | "프로그램이 바뀌어 남은 단계는 다시 확인이 필요합니다" | 완료 증거 보존. 남은 단계에 해당하는 A·C·D 동의를 다시 확인. 과거 결과를 현재 검증기로 확인할 수 없으면 자동 재실행 대신 조회 한계 표시 |
| 앱 종료·재시작 | 작업 목록에서 이어 할 작업 선택 → `이어서 진행` | 기록과 실제 완료 증거를 다시 대조한 뒤 다음 단계부터 진행 |

## 2. 자동 진행과 사용자 확인의 경계

### 2.1 사용자 확인이 필요한 것 (그 외는 자동)

| 결정 | 확인 내용 | 이유 |
| --- | --- | --- |
| A 작업 동의 | 입력 파일, 모델 전달 범위·공급자, 자원 상한, 자동 진행 범위, 중복 컬럼명 자동 정비 허용 여부 | 데이터 사용과 외부 전송의 근거 |
| B 역할·기준 | 컬럼 역할, target, 결측·상수 처리, 품질 기준 | 분석 의미를 정하는 사용자 판단 |
| C 처리안 | 분할 방식·비율·시드, 전처리 규칙, 단계 목록 | 이후 계산 기준. 승인 위임 범위가 됨 |
| D 적용 | 후보 보고서를 본 뒤 실제 변환 산출물 생성 | 데이터 변경(새 파생 데이터 생성) |
| 수시 | 문제 발생 시 해결안 선택, 동의 범위 밖 요청, 외부 공급자 첫 사용, 실패 후 재실행 | 범위 밖이거나 결과가 불확실한 경우 |

### 2.2 자동으로 하는 것

- snapshot 복사, 헤더 점검, 진단 작업 생성·실행
- 동의 범위 안의 중복 컬럼명 정비
- 프로파일 파일 생성(이름 자동 부여)
- 내부 작업 생성과 작업 이름·경로·선행 결과 연결(`bind_workflow_step`의 `values`를 조정기가 채움)
- 단계별 사전 검사
- 동의한 계획·입력 계보를 검사하고 실제 단계 인자를 확정한 뒤, 그 범위에 정확히 결합한 1회 승인 기록 발급과 실행(2.5절)
- 결과 검증, 다음 단계 진행
- 로컬 LLM 호출(동의 범위 안의 자료), 보고서 조립

### 2.3 이번에 바꾸는 정책

| 기존 정책 | 변경 |
| --- | --- |
| 단계마다 사용자가 직접 승인(자동 승인 금지) | A는 진단·허용한 정비, C는 후속 처리 계획, D는 실제 후보 적용의 동의입니다. 조정기는 그 위임 범위 안에서만 단계별 1회 승인을 발급합니다. 미생성 산출물의 해시를 미리 요구하지 않고 승인한 생성 규칙·입력 계보에 맞는 결과인지 검증한 뒤 실제 해시를 실행 승인에 결합합니다(2.5절, Q1). 범위를 벗어나면 멈추고 묻습니다. |
| 작업 생성·이름·경로·선행 작업을 사용자가 입력 | 조정기가 생성·연결합니다. 사용자는 이름을 보지 않아도 됩니다(기술 상세에 표시). |
| 입력 진단 결과의 LLM 전달 차단 | 결정 A의 동의 범위 안에서 컬럼명·진단 집계·품질 보고서·후보 보고서를 로컬 LLM에 전달합니다. 원본 행 값은 기본 제외합니다(Q3). |
| 역할 추천 금지(초기값 모두 제외) | LLM이 근거와 함께 역할 초안을 제시합니다. 확정은 사용자가 결정 B에서 합니다. |
| 결과 해설은 민감도 분류·정책 저장 후 단건 | 작업 동의가 해설 허용을 포함합니다. 민감 자료 표시는 결정 A에서 한 번 받습니다. |
| 외부 API 미지원 | 공급자·전달 범위·보관/학습 정책 위험을 결정 A(또는 첫 사용 시)에서 확인하면, 그 작업과 범위 안에서는 반복 확인 없이 씁니다(Q2). |
| 품질 검토 결과는 사용자가 다른 화면에서 새 작업으로 처리 | 그 자리에서 수정하고, 조정기가 새 작업을 만들어 이어 갑니다. |

### 2.4 유지하는 실행 안전장치

- CSV 데이터 분석·변환 계산은 기존 AppContainer·Job 격리 worker에서 합니다. 비격리 계산 대체 경로는 없습니다. 부모의 계약 검사·결과 검증·허용된 로컬 전달 복사·보고서 조립과 로컬 모델 호출은 기존 책임 구분을 유지합니다.
- 부모는 worker 결과를 그대로 믿지 않고 기존 결과 검증기로 다시 확인합니다.
- 승인 기록은 지금처럼 단계별 1회용이고 범위에 결합됩니다. 위임 발급도 같은 `ApprovalScope`를 씁니다. 승인 재사용, 범위가 다른 승인, 기록 없는 실행은 없습니다.
- 승인한 실행 입력·코드·계획이 바뀌면 영향받는 남은 단계의 위임이 무효가 됩니다. 승인한 생성 규칙에 따른 검증된 파생 결과 생성은 입력 변조가 아닙니다. 원본만 달라지고 선택 당시 snapshot이 온전한 경우는 1.2절처럼 구분합니다.
- 전처리 기준은 Train에서만 산출하고 Test에 맞추지 않습니다. 저장 기준을 다시 산출하지 않습니다.
- LLM 출력은 기존 계약·허용 목록으로 검증한 값만 씁니다. 셸·경로·코드로 해석하지 않습니다.
- 원본과 기존 snapshot은 바꾸지 않습니다. 생성 파일은 덮어쓰지 않습니다. 실패한 부분 결과는 입력으로 등록하지 않습니다.
- 실패한 worker·모델 요청은 자동 재시도하지 않습니다. 재시도는 사용자가 해결안을 고를 때만 합니다.
- 외부 전송은 동의한 공급자·자료 범위 밖으로 확장하지 않습니다. 무보관·무학습 정책이 있더라도 금지 자료를 보내는 근거로 쓰지 않습니다.
- 대화 원문·승인 토큰·API 키는 작업 기록에 저장하지 않습니다.

### 2.5 위임 발급 규칙 (Q1 추천안)

**계획 동의와 실제 실행 승인을 분리합니다.** 아직 생성하지 않은 결과 해시는 동의 시점에 알 수 없습니다.

- **동의 시 고정:** 작업·사용자, 결정 종류, 계획 revision·지문, 확보한 snapshot 해시, 모듈·버전·유효 설정, 단계·선행 관계, 파생 입력 생성 규칙, 자원 상한, 코드 식별값, 전달 정책, 만료입니다. 미생성 결과는 임의 경로나 자리표시 해시가 아니라 승인한 선행 단계·출력 계약으로 참조합니다.
- **실행 직전 고정:** 검증된 선행 결과의 실제 실행 ID·완료 증거·파일 해시, 실제 내부 작업·단계·도구·인자·자원입니다. 기존 바인더와 `preview_approval`로 정확한 `ApprovalScope`를 계산합니다.

단계 `s`의 승인 발급에는 다음 조건을 **모두** 요구합니다.

1. 동의 시각·만료·OS 사용자가 유효합니다. 진단·허용한 입력 정비는 **A**, 품질 검사부터 Train 기준 후보 산출까지는 **C**, 후보 적용과 결과의 로컬 전달은 **D**를 근거로 합니다. B만으로 실행 권한을 주지 않습니다.
2. 모듈·설정·단계·자원이 동의 범위 안이고 코드 식별값이 일치합니다. 초기 snapshot 준비는 A의 선택 파일·복사 정책에 결합하고, 확보한 snapshot 해시를 이후 기준으로 고정합니다.
3. 선행 결과는 해당 작업의 승인된 선행 단계에서 생성됐고 기존 완료·무결성·도메인 검증을 통과해야 합니다. 다른 작업의 임의 결과나 실패한 부분 결과를 끼워 넣지 않습니다. 실제 해시는 이 시점에 결합하고 실행 전 기존 검사를 다시 수행합니다.
4. 실제 승인 범위가 위 조건에서 확정한 범위와 정확히 일치합니다. 판정은 계약 코드가 수행하며 LLM이 일치 여부를 결정하지 않습니다.
5. 같은 논리 단계·시도에 이미 발급·소비·실행 중인 승인이 없는지 기존 저장소에서 확인합니다. 새 시도는 사용자 재시도 선택 후 생성하고 범위 변경은 해당 동의를 다시 받습니다.
6. D는 사용자가 본 검증된 후보 ID·전처리 기준 해시·적용 구간에 결합합니다. 후보나 기준이 바뀌면 이전 D를 사용하지 않습니다.

**기록 의미:** 기존 승인 저장소·잠금·범위 재검사·일회 소비를 재사용하되 `confirmed=True`만 넣어 사용자 직접 검토를 가장하지 않습니다. 기존 직접 확인 이벤트(CSV 작업 `workflow_approval.record_approval`의 `LOCAL_REVIEW_CONFIRMED`, 진단·EDA `pipeline_approval_cli.record_approval`의 `PIPELINE_APPROVAL_RECORDED`)는 실제 사용자가 표시된 자료를 확인했을 때만 기록합니다. 위임은 별도 고정 이벤트 `DELEGATED_APPROVAL_RECORDED`로 기록하고 동의 ID·계획 revision/지문·실제 승인 범위 지문·논리 단계/시도 ID를 연결합니다. 기존 승인 API에 이 구분과 연결을 위한 작은 확장을 추가합니다.

실행 전에 위임 근거 기록이 완성돼야 합니다. 발급 도중 중단되면 기존 승인과 연결 기록을 조회해 복구하며, 근거 연결을 입증할 수 없는 승인은 사용하지 않습니다. 중복 발급으로 우회하지 않습니다. 조건이 어긋나면 결정 영역에 차이를 보여 줍니다.

## 4. 작업 저장·재시작·재개

- **위치:** `logs/agents/tasks/<task_id>/`
  - `task.json`: 현재 상태
  - `events.jsonl`: 단계 이벤트
  - `consents/<decision>.json`: 결정 기록
  - `report/`: 최종 보고서
- **`task.json`에 저장하는 것:**
  - 입력: 원본 경로·식별자, snapshot·파생 입력 등록 기록 경로
  - 결정 A~D의 내용 해시와 결정 시각
  - 프로파일 파일, 처리안 저장 이름
  - 단계별 고정 논리 단계 ID·시도 ID·내부 작업 이름·상태·완료 증거 참조
  - 위임 연결: 동의 ID·계획 지문·실제 승인 범위 지문
  - 현재 단계, `revision`, 코드 식별값
- **저장하지 않는 것:** 대화 원문, 모델 응답 원문, 승인 ID·토큰, API 키. 승인 기록은 기존 내부 저장소에 유지하고 작업 기록에 중복 저장하지 않습니다. 확정한 역할·계획과 검증된 구조화 해설은 재개·보고서에 필요한 범위에서 저장합니다.
- **저장 방식:** 기존 `LocalStateStore`처럼 `expected_revision`으로 충돌을 막고 작업별 잠금과 기존 실행 잠금을 함께 사용합니다. 내부 작업 생성 전에 논리 단계·시도 ID와 예약한 작업 이름을 저장하고, 재진입 시 같은 이름의 실제 기록을 조회합니다. 재렌더링·중복 클릭·재시작으로 새 이름·승인을 만들지 않습니다.
- **재개 방식**
  1. 작업 목록에서 작업을 고르면 `task.json`을 읽고, 저장 상태를 믿지 않고 **실제 증거로 다시 계산**합니다.
     - 완료 단계: `completed_workflow`, 진단 결과 검증기, snapshot 해시
     - 미완료 단계: 기존 `RunState`
  2. 화면을 여는 것만으로는 실행하지 않습니다. `이어서 진행`을 누르면 다음 결정 지점까지 자동으로 진행합니다.
  3. `worker_started: None`은 관측 정보 부족이지 중단 판정이 아닙니다. 기존 RunState·잠금·승인 소비·실행 예약·완료 표식·결과 검증을 대조합니다. 실행 중이면 관찰만 하고 완료 증거가 유효하면 결과를 연결합니다. 어느 쪽도 입증하지 못하면 "결과 확인 필요"로 멈춥니다.
  4. 실행 의도 저장 후 발급 전, 발급 후 실행 전, 실행 후 작업 상태 저장 전 중단을 각각 복구 테스트합니다. 동일 범위의 기존 미사용 승인은 새로 발급하지 않고 소비할 수 있습니다(`approval_store` 범위 조회, 만료된 승인은 사용하지 않음). 소비된 승인이나 실행 불명확 단계는 자동 재실행하지 않습니다. 새 시도는 이전 실행이 더 이상 활성 상태가 아님을 확인하고 사용자 재시도 선택 후 만듭니다.
  5. 승인한 snapshot·파생 입력 변조는 후속 위임을 차단합니다. 원본만 바뀌고 snapshot은 온전하면 계속합니다. 코드·계획 변경은 영향받는 남은 단계의 동의를 다시 받습니다. 완료 결과를 현재 검증기로 확인할 수 없으면 한계를 표시하고 자동 재실행·임의 통과하지 않습니다.
- **보존:** 작업은 사용자가 지우기 전까지 유지합니다. 이전 내부 작업과 소비된 승인은 보존하고 재사용하지 않습니다.

### 7.1 목표와 현재 구조 판정

**목표:** 데이터와 목적을 주면 AI가 진단·권장안·필요한 질문을 제시하고, 사용자 승인 범위에서 전처리부터 내용 있는 최종 결과까지 연결합니다. 입력 유형이 바뀌어도 공통 조정기와 화면은 그대로 둡니다. CSV는 첫 검증 대상입니다.

**판정:** 현재 구조(5.1~5.5절)는 이 목표에 맞지 않습니다. 보안 기반은 적합하지만 다음 다섯 가지가 목표를 막습니다.

| 목표 요소 | 현재 | 문제 |
| --- | --- | --- |
| AI 진단 | 격리 진단 집계를 모델에 보내 해석 요약을 받음 | 진단 실행·전송 범위가 조정기 안에 CSV 전용으로 고정됨 |
| 권장안 | 모델이 역할과 분할·전처리 설정 21개 전체를 다시 작성함 | 실제 일반 CSV에서 계약 위반으로 거부됨(5.3절). 합성 4사례 중 역할까지 맞은 것은 1건 |
| 필요한 질문 | 자유 문장 notes와 코드 경고뿐 | 질문·답변 계약이 없음. 식별자 의심을 안내하지 않아 실제 적용이 실패함(아래 7.7) |
| 승인 범위 전처리 | 위임 발급·격리·결과 검증은 동작함 | 단계 목록(`STEPS`)과 결정별 허용 단계 표가 csv 모듈로 고정됨 |
| 내용 있는 결과 | 보고서 틀(절 구성·미집계·기술 상세 분리)은 적합함 | CSV 결과 파일 이름을 직접 읽음. 실패에 원인·다음 행동이 없음. 후보 표가 원문 그대로 보임 |

**이전 판단(같은 날 대화)에서 정정한 네 가지**
1. 입력 유형 선택 화면은 두지 않습니다. 유형이 하나뿐인 지금 선택지는 가상의 요구입니다. 입력을 보고 어댑터를 정하는 경계만 둡니다.
2. 구조 분리만으로는 부족합니다. 실제로 실패한 권장안·질문 계약을 다시 정의합니다(7.4·7.5).
3. 흐름 결함 3건(식별자 미안내, 후보 표, 실패 원인 없음)은 별도 보완이 아니라 재편 완료 조건에 포함합니다(7.7·7.10).
4. 승인된 목표 안의 구조 보완은 다시 묻지 않습니다. 웨이퍼 프로파일 모듈의 위임 발급 위치만 연결할 때 결정합니다(7.11).
5. **(2026-10-21 추가 정정)** WM은 데이터 유형도 상위 분류도 아닙니다. 공통 계층은 **표형**과 **배열·이미지** 두 데이터 형태를 기준으로 둡니다. 웨이퍼 처리는 배열 형태 위의 **도메인 프로파일과 전용 모듈**이고, WM-811K는 그 프로파일로 들어오는 **입력 매핑**입니다(7.3.1). 이 절에서 "WM 연결"이라고 썼던 곳은 "웨이퍼 프로파일 연결"로 읽습니다.

### 7.3 책임 구분

| 계층 | 책임 | 비고 |
| --- | --- | --- |
| 계층 | 책임 | 비고 |
| --- | --- | --- |
| **공통 핵심** | 작업 기록·상태, 동의 A·C·D, 계획 확정과 전체 검증 실행, 결정 지점·위임 범위 계산, 위임 발급 호출, 단계 진행·이름 예약·재계산 대조, 질문 표시와 답변 반영, 문제 처리(고정 코드·확인/추정 구분·다음 행동), 보고서 조립, 4영역 화면 | 데이터 형태·도메인·입력 형식 모듈을 import하지 않음. `wm`·`wafer`·`csv` 이름, WM 필드명, 웨이퍼 단계명을 쓰지 않음(7.9에서 검사) |
| **데이터 형태 어댑터** (표형 / 배열·이미지) | 형태별 canonical 계약, 진단 실행·검증 결과 읽기, 모델 전송 집계와 전송 범위 문구, 결정 항목 스키마와 기본값, 결정적 검사(실행 검증)와 질문 생성, 결과 요약 추출 | 표형: 컬럼 역할·분할·전처리. 배열·이미지: 표본·라벨·그룹·형상·값 집합(7.3.1) |
| **도메인 프로파일** (선택) | 한 데이터 형태 위에서 분야 의미를 더함. 라벨 체계, 값 의미, 전용 진단·검사, 전용 모듈 카탈로그와 계획 템플릿, 모듈별 계보 결합 규칙 | 첫 사례는 배열 형태 위의 웨이퍼 프로파일. 표형은 지금 도메인 프로파일 없이 범용 템플릿 사용 |
| **입력 형식 로더·입력 매핑** | 파일 형식 판별과 복사, 형태별 canonical 데이터로의 변환과 필드 매핑 | CSV 로더(헤더 정비, 인코딩, time 분할 미지원), pickle 구조 변환기(`tabular_v1`·`numeric_array_v1`), WM-811K 매핑(`wm811k_v1`) |
| **계산 모듈** | 기존 분할·변환·EDA·품질, `src/wafer_dl`과 `wm_*` worker | 바꾸지 않음 |

등록은 `pipeline_binding_registry`처럼 `adapter_id`(또는 프로파일 ID)를 키로 하는 고정 dict입니다. 플러그인 탐색이나 동적 import, 새 프레임워크는 만들지 않습니다. 등록 목록은 코드 지문에 포함합니다.

**선택 순서:** 입력 형식 로더가 형태를 판별합니다(CSV → 표형, pickle → 구조 서명으로 표형·배열·WM-811K 매핑). 형태 어댑터가 정해지고, 매핑이 도메인 프로파일을 지정하면 그 프로파일을 씁니다. 사용자에게 유형 선택 화면을 보여 주지 않습니다. 판별이 모호하면 결정 영역의 질문으로 묻습니다.

### 7.3.1 배열·이미지 형태와 웨이퍼 분리

**배열·이미지 형태의 canonical 계약(공통 이름)**
- 표본 모음: 표본마다 `sample_id`, 배열(정수·실수, 2차원 이상), 선택 필드 `label`·`group`·`source_position`
- 공통 진단 집계: 표본 수, 형상 분포, 값 집합·범위 요약, 라벨 분포, 라벨·그룹 결측, 그룹 수, 중복 표본 수
- 결정 항목: 라벨 필드 사용 여부, 그룹 기준(분할 누수 방지), 분할 비율·시드, 형상 정규화 방식 등. 실제 선택지는 도메인 프로파일의 모듈이 지원하는 범위로 제한합니다.
- `canonical_data.export_array`·`numeric_array_v1`이 이 계약의 기존 기반입니다.

**웨이퍼 도메인 프로파일**
- 내용: 값 의미(배경·정상·불량 다이), 클래스 체계(`validate_canonical.CLASS_NAMES`), lot 기준 그룹, 충돌 표본 검사, 웨이퍼 변환·캐시
- 모듈: `wm_module_catalogue.wm_modules`의 8개 모듈과 `src/wafer_dl`을 그대로 프로파일의 카탈로그·템플릿으로 씁니다. 모듈 ID·포트 이름(`wm_canonical` 등)은 **프로파일 내부 식별자**입니다.
- 공통 핵심에는 다음 형태로만 전달합니다: 계획의 모듈 참조, 계산된 결정·위임 범위, 결과 요약 사실, 질문.

**WM-811K 입력 매핑**
- 내용: pickle의 `waferMap` → 표본 배열, `failureType` → `label`, `lotName` → `group`. 출처·변환 기록은 기존 `export_bundle`이 남깁니다.
- 매핑 결과는 웨이퍼 프로파일을 지정한 배열 형태 데이터입니다.
- WM 열 이름은 이 매핑 안에만 둡니다. 공통 핵심·형태 어댑터·화면은 `sample_id`·`label`·`group`만 압니다.
- 다른 웨이퍼 데이터셋은 같은 프로파일에 새 매핑만 추가하면 됩니다. 이번 범위에서는 만들지 않습니다.

**기존 코드 보존:** 웨이퍼 계산(`src/wafer_dl`, `wm_*` worker·results·transport)과 기존 5단계 화면의 WM 분기는 바꾸지 않습니다. 새 공통 작업 화면과 조정기만 위 경계를 지킵니다. 웨이퍼 결과 요약 추출은 웨이퍼 프로파일에 새로 둡니다. 기존 `wm_*_results`가 검증한 결과만 읽습니다.

### 7.4 계획: 템플릿 → 권장 변경 → 질문 답변 → 전체 검증

계획은 한 가지 형식으로 표현합니다: **유형 템플릿의 모듈 순서 + 각 모듈의 유효 설정 + 결정 항목 값**(표형이면 역할). 확정과 실행은 모두 이 계획 하나를 기준으로 합니다.

1. **기본 계획:** 어댑터가 템플릿과 결정 항목 기본값으로 만듭니다(현재의 기본 초안에 해당). 이 시점에 이미 전체 검증을 통과해야 합니다.
2. **권장 변경(모델):** 모델은 설정 전체를 다시 쓰지 않습니다. 결정 항목 스키마 안에서 **기본 계획과 다른 항목만** 다음 형식으로 냅니다.
   - 형식: `{path, value, reason}`. `path`는 스키마에 있는 항목, `value`는 그 항목에 허용된 값, `reason`은 300자 이하 문장입니다.
   - 진단 해석 요약과 질문(7.5)도 함께 냅니다.
   - 모듈 순서는 바꿀 수 없습니다(템플릿 고정). 선택 모듈 추가는 이번 범위에 넣지 않습니다.
3. **합친 계획:** 기본 계획에 권장 변경을 모두 적용한 계획을 만듭니다.
4. **전체 검증:** 합친 계획 전체를 한 번에 검사합니다. 검사 범위는 다음과 같습니다.
   - 어댑터의 스키마·계약 검사. 표형이면 `build_profile`·`SplitRules`·`PreparationRules`·역할×분할 교차 검사입니다.
   - 카탈로그 계획 검증(`validate_workflow_proposal` 일반화판)
   - 유효 설정 계산
   - 이 중 하나라도 실패하면 **권장 변경 전체를 채택하지 않고** 기본 계획을 보여 줍니다. 거부 사유는 고정 코드로 남깁니다(5.3절 방식 유지). 항목별 부분 채택은 하지 않습니다.
5. **표시:** 화면은 합친 계획(또는 기본 계획)을 보여 줍니다.
   - 모델 권장으로 바뀐 항목은 "기본값 → 권장값 · 이유"로 따로 표시합니다.
   - 실행에 영향을 주는 전체 유효 설정 표를 함께 보여 줍니다.
6. **사용자 수정·답변:** 사용자가 고친 값과 질문 답변(7.5)을 반영한 **최종 계획**을 다시 같은 전체 검증에 넣습니다.
   - 실패하면 고정 메시지와 해당 항목을 표시하고 작업을 만들지 않습니다.
   - 화면 검사와 서버 확인은 같은 어댑터 함수를 씁니다. 화면 검사는 안내용이고, 서버 확인이 실행 검증입니다.
7. **동의 C:** 최종 계획 서명, 질문별 답변, 유효 설정, 입력 해시, 코드 지문에 결합합니다. 이후 단계는 이 계획만 실행합니다.

### 7.5 질문·답변 계약과 계획 반영

질문은 사용자가 정해야 하거나 확인해야 할 항목입니다. 공통 화면이 출처와 상관없이 같은 방식으로 보여 줍니다.

| 필드 | 의미 |
| --- | --- |
| `id` | 작업 안에서 고정된 질문 ID |
| `source` | `adapter`(결정적 검사) 또는 `model` |
| `level` | `required`(답해야 확정 가능) 또는 `advisory`(안내만, 진행 가능) |
| `path` | 답이 반영될 결정 항목 경로. 없으면 확인형 질문 |
| `options` | 선택지. `path`가 있으면 그 항목의 스키마 허용값 중 일부만 가능 |
| `recommended` | 권장 선택지(없을 수 있음) |
| `text` | 고정 문구 또는 모델 문장. 화면에서는 항상 일반 텍스트로 표시 |
| `subjects` | 관련 컬럼·항목 이름. 일반 텍스트로만 표시 |

**규칙**
- **필수 질문은 어댑터만 만듭니다.** 모델 질문은 항상 `advisory`이고, `path`가 스키마 밖이면 버립니다. 이것은 응답 전체를 거부하는 사유가 아니라 질문 하나를 제외하는 것입니다. 어떤 질문을 버렸는지 기술 상세에 고정 코드로 남깁니다.
- **답변 하나는 해당 `path` 하나만 바꿉니다.** 다른 항목을 연쇄로 바꾸지 않습니다. 바뀐 값은 "답변으로 변경"으로 표시합니다.
- **답변은 계획을 다시 검증합니다.** 답변을 반영한 최종 계획이 전체 검증(7.4의 6)을 통과해야 확정할 수 있습니다. 필수 질문에 답이 없으면 확정 버튼을 비활성으로 두고, 서버도 거부합니다.
- **기록:** 답변은 작업 기록과 동의 C 내용에 포함합니다. 같은 질문 ID에 다른 답을 주면 새 동의 C가 필요합니다.
- **자동 변경은 없습니다.** 질문에 권장 선택지가 있어도 사용자가 고르기 전에는 계획에 반영하지 않습니다. 권장안 자체는 7.4의 권장 변경으로만 반영됩니다.

**표형 어댑터의 질문(첫 범위)**

| 질문 | 생성 조건 | level | path·선택지 |
| --- | --- | --- | --- |
| target 지정 | target이 없거나 목표 문장에 target 컬럼 이름이 없음 | advisory | `roles.<컬럼>` 중 target 후보 선택 또는 "target 없음" |
| 식별자 의심 | 범주형·문자열 특징의 관측 고유값 수가 결측을 뺀 행 수와 같음 | advisory | `roles.<컬럼>`: 식별자 / 범주형 유지 / 제외. 범주형을 유지하고 `unknown_category=error`이면 "Validation에 Train에 없던 값이 생겨 적용이 실패할 수 있음"을 함께 표시 |
| 분할 방식 | time 제안이 거부되어 분할 방식이 비어 있음(5.4절) | required | `split.strategy`: random / group. random으로 자동 대체하지 않음 |
| 역할×분할 불일치 | 교차 검사 실패 | required | 관련 `split.strategy` 또는 `roles.<컬럼>` |

수치형 특징은 연속 측정값이면 고유값이 대부분 다르므로 식별자 의심 대상에서 뺍니다. 이것은 현재 범위의 한계로 기록합니다.

### 7.6 결정 지점·위임 범위 계산

- 카탈로그 명세의 `approval_boundaries`(모듈별 승인 단계)와 어댑터가 정한 결정 종류(사람 검토, 실제 적용)를 근거로, **확정한 계획에서** 다음을 계산합니다.
  - 동의 C·D의 허용 (모듈, 단계) 집합
  - 결정 D 지점
- `task_consent`의 손으로 적은 표(`csv_*` 고정)를 대체합니다.
- 계산 결과는 동의 내용에 그대로 넣고 해시합니다. 위임할 때마다 같은 계산을 다시 해서 대조합니다. 판정 규칙(2.5절 1~6)은 바꾸지 않습니다.
- 표형 템플릿에서 계산한 결과는 현재 표와 같아야 합니다. 테스트로 대조합니다.

### 7.7 결과 요약 계약, 문제 처리, 보고서

- **결과 요약:** 어댑터가 각 단계의 `results()` 검증을 통과한 결과에서 공통 형식의 사실을 추출합니다.
  - 형식: 문제점 / 처리 내용 / 전후 비교 / 그래프 / 결과 파일 / 주의사항
  - 값이 없으면 `미집계`로 둡니다. 공통 보고서는 이 사실만 조립하고 파일 이름을 직접 읽지 않습니다.
  - 표형 어댑터는 현재 `task_report.build_facts`의 내용을 옮깁니다.
- **결정 D의 후보 표시:** 같은 결과 요약에서 구조화된 표를 그립니다.
  - 표: Train 행 수, 제거 후보, 유지 특징, 예상 출력 특징, 특징별 처리, 적용 규칙
  - 원문 보고서는 일반 텍스트로 접어 둡니다. 마크다운으로 해석하지 않습니다.
- **문제 처리**(공통)
  - 서비스가 실패한 단계의 worker 진단 분류(`scratch/task/diagnostic.json`의 고정 stage·code)를 허용 목록으로 검증해 돌려줍니다.
  - 조정기는 문제 기록을 다음 세 부분으로 나눠 남깁니다.
    - **확인된 분류:** worker 진단
    - **추정 원인:** 어댑터가 확정 계획에서 계산
    - **다음 행동**
  - 메시지는 고정 문구입니다. 컬럼 이름은 별도 필드에 두고 일반 텍스트로 표시합니다.
- **2026-10-21 실제 실패 사례로 확인한 사실**
  - 작업 `bea225e0…`의 적용 실패는 worker 진단 `INPUT_VALIDATION / INPUT_INVALID`였습니다.
  - 저장 결과를 대조하니 후보의 `id` 범주는 Train 값 84개였습니다. Validation 18행의 `id`는 모두 Train에 없는 값이었습니다.
  - 확정 역할에서 `id`가 범주형이었고 `unknown_category=error`였습니다.
  - worker는 예외 원문을 남기지 않으므로 오류 문장 자체는 확인하지 못했습니다. 분류와 데이터 대조가 같은 원인을 가리킵니다.
  - 이 경우 안내는 "확인된 분류: 입력 검증 실패 / 추정 원인: 범주형 특징 id에 Train에 없던 값 / 다음 행동: 새 작업에서 id를 식별자로 지정"이 됩니다.
  - 같은 설정으로 다시 진행하면 같은 실패가 나므로 "같은 조건으로 재시도"는 제공하지 않습니다.

### 7.8 공통 화면

- 요청·진행·결정·결과 4영역은 그대로 둡니다. 메뉴 이름은 `통합 작업`입니다.
- 입력란은 어댑터가 허용하는 형식을 안내합니다. 지금은 CSV만 허용합니다.
- 결정 영역에는 다음을 순서대로 둡니다.
  1. 진단 요약
  2. 권장 변경(기본값 → 권장값 · 이유)
  3. 질문(필수 → 안내 순)
  4. 결정 항목 양식(어댑터 스키마)
  5. 전체 유효 설정 표
  6. 동의
- 표형 역할 편집 표는 어댑터가 제공하는 입력 부품입니다. 공통 화면은 스키마의 enum·number·boolean 항목만 일반 양식으로 그리고, 어댑터 전용 부품은 이름으로 등록합니다.
- 모델 문장·질문·컬럼 이름은 모두 일반 텍스트나 표로만 표시합니다. 마크다운으로 해석하는 위치에는 고정 문구만 둡니다.

### 7.9 공통성 검증: 작은 비표형 합성 어댑터

공통 핵심이 표형·CSV·웨이퍼에 기대지 않는지를 **테스트 전용 합성 배열 어댑터**로 검증합니다. 제품 메뉴에는 노출하지 않고 계산 모듈도 새로 만들지 않습니다. 배열·이미지 형태 계약(7.3.1)을 쓰되 도메인 프로파일은 없습니다.

- **입력:** 작은 합성 표본 모음(예: 24개, 4×4 정수 배열, `label` 3종, `group` 6개, 라벨 결측 2개, 중복 표본 1개). 웨이퍼 값 의미나 WM 필드명을 쓰지 않습니다.
- **진단:** 7.3.1의 공통 진단 집계. 테스트 내부 계산이며 격리 실행 대상이 아닙니다.
- **결정 항목:** `use_label`(boolean), `group_split`(boolean), `drop_duplicates`(boolean)
- **질문:** 라벨 결측이 있으면 `use_label` 필수 질문, 중복 표본이 있으면 `drop_duplicates` 안내 질문
- **계획:** 모듈 2개짜리 템플릿. 서비스는 공통 서비스 API를 흉내 낸 테스트 대역으로 두고, 승인 단계 1개씩과 결과 요약을 제공합니다.
- **검증 항목**
  1. 공통 핵심 모듈(조정기·동의·작업 기록·질문·문제 처리·보고서·화면 틀)이 표형·CSV·웨이퍼(`wm_*`, `wafer_dl`) 모듈을 import하지 않고, 이 이름들과 WM 필드명을 코드에 쓰지 않습니다. import 그래프와 식별자 검색으로 검사합니다.
  2. 같은 공통 조정기와 화면으로 요청 → 진단 → 권장 변경(모의 모델) → 질문 답변 → 전체 검증 → 동의 C → 단계 진행 → 결정 D → 결과 보고서까지 진행합니다.
  3. 위임 범위를 계획에서 계산하고, 범위 밖 단계에는 위임을 거부합니다.
  4. 필수 질문에 답하지 않으면 서버가 확정을 거부합니다.
  5. 권장 변경 중 하나라도 계획 검증을 통과하지 못하면 전체를 버리고 기본 계획을 씁니다.
  6. 결과 요약에 없는 값은 `미집계`로 표시합니다.
- 이 어댑터는 승인·격리 경계를 검증하지 않습니다. 실제 위임 발급·격리 실행은 표형 어댑터의 기존 테스트가 계속 담당합니다.

### 7.10 보존·호환·코드 지문

- **보존:** 격리 실행, 승인 저장소, 1회 승인, 위임 판정 규칙(2.5절), 입력 복사본·해시, 계산 모듈, `results()` 검증, LLM 전송 제한(Q3), 응답 계약 검증, 거부 코드, 역할×분할 교차 검사. 기존 테스트의 안전 기대값은 낮추지 않습니다.
- **기존 기록:** 작업 기록에 `kind`가 없으면 `tabular_csv`로 읽습니다. 완료된 작업의 보고서 조회와 재조립을 계속 지원합니다. 완료 작업은 재실행하지 않습니다.
- **코드 지문:** 공통 핵심, 표형 어댑터, 어댑터 등록 목록을 CSV `code_id`와 모듈 파이프라인 지문에 넣습니다. 구현을 한 번에 마치면 지문은 한 번 바뀝니다. 아직 실행하지 않은 CSV·모듈 파이프라인 승인과 진행 중인 통합 작업은 다시 준비해야 합니다. `workflow_approval.py`를 고치지 않으면 WM 지문은 바뀌지 않습니다.
