# 모듈형 전처리 — 변환 연결 계획

작성일: 2026-10-16. 분석·품질 검사 모듈의 실제 합성 정상/중단 경로를 확인한 뒤 준비하는 후속 설계다. 아래 모듈 ID·입출력·승인 흐름은 제안이며 아직 등록·격리 실행하지 않는다.

2026-10-17 갱신: [Train 후보 기준 산출](../guides/PREPARATION_CANDIDATE.md)을 별도 승인·격리 worker·부모 검증·후보 커밋에 연결했다. 기존 복합 코어의 기준 산출 설정을 재사용하며 실제 transform은 호출하지 않는다. 아래 제안 ID의 모듈 등록부 연결과 저장 기준 적용 승인은 아직 구현하지 않았다. 실제 Windows 후보 실행은 별도 확인이 필요하다.

추가 갱신: [저장 기준 적용](../guides/PREPARATION_APPLY.md)의 별도 승인·격리 transform·부모 검증·커밋을 연결했다. 완료 후보와 같은 분할의 Train·Validation만 사용하고 재산출·Test 적용·모델 학습은 하지 않는다. 별도 CLI 경로이며 제안 ID의 모듈 등록부 연결과 실제 Windows 적용 확인은 남아 있다.

## 1. 기존 코드에서 재사용할 부분

| 기존 코드 | 재사용 범위 | 새 격리 경로에서 필요한 보완 |
| --- | --- | --- |
| `src/preprocessing/transform.py`의 PreparationRules·TabularPreprocessor | 특징 제거·대치·변환 기준 산출과 적용 알고리즘 | 원본 보존·Train 증거·후보/적용 단계 구분 |
| 같은 파일의 build_preparation·save_preparation·load_preparation | 복합 전처리 Pipeline·JSON 상태 저장/복원 | 복사된 상태의 크기·해시·버전·역할 계약 검증 |
| 같은 파일의 prepare_splits | 확정 분할 검증·Train 기준 산출 방식 | 전체 입력 접근 대신 승인된 구간만 전달하는 격리 계약 |
| `src/agents/adapters/prepare.py` | commit_split 의존성·승인·행 연결·산출물 설계 | 부모의 원본 재파싱·재변환 검증을 그대로 격리 부모에 이식하지 않음 |

모델 학습은 추가하지 않는다. 중앙값·제거 목록 등의 전처리 기준 산출만 수행한다. 제거·대치·스케일링을 각각 독립 상태 모듈로 다시 구현하지 않고 기존 복합 변환기를 재사용한다.

## 2. 선행 조건: 분할과 입력 증거

현재 모듈 CLI는 하나의 CSV snapshot을 읽는 비파괴 분석만 지원한다. JSON의 `partition: train` 선언만으로 그 데이터가 실제 Train이라는 증거가 되지는 않는다.

변환 연결 전에 승인·확정된 분할 산출물의 출처·행 위치 또는 안정된 행 ID·분할 역할·완료 해시를 입력 계약에 결합한다. 기존 분할 계약을 재사용하되 격리 전달·부모 검증 범위는 별도로 구현해야 한다. 새 worker에 전체 원본 폴더·Test 입력을 무조건 전달하지 않는다.

첫 적용 대상은 Train·Validation이며 Test 변환은 명시적인 별도 범위다. Train-only 산출 작업에는 Train 입력만, Validation 적용 작업에는 Validation과 저장 기준만 전달한다. 중복 행·그룹 연결과 시간 경계는 분할 계약 단계에서 확인한다.

## 3. 제안 흐름: 후보 산출과 적용을 구분

```text
승인된 확정 분할·입력 계약
    ↓
기준 산출 작업 승인
    ↓
격리 worker: Train에서 후보 기준 산출
    ↓
로컬 제안: 제거 목록·사유·개수·유지 특징·처리 규칙·입출력 영향
    ↓
사용자: 정확한 후보 상태·변경 범위에 대해 적용 승인
    ↓
격리 worker: 저장 후보 기준만 Train·Validation에 적용
    ↓
부모 파일·행 연결·계약 검증 → 새 전처리 산출물 완료 기록
```

첫 승인은 데이터 읽기와 전처리 기준 후보 산출을 허용한다. 두 번째 승인은 검증한 후보를 파생 데이터에 적용하는 변경 승인이며 서로 재사용하지 않는다. 후보 산출만 끝난 결과를 전처리 완료로 표시하지 않는다.

기존 하나의 승인 작업 안에서 EDA·검사를 실행하는 경로와 달리 중간 사용자 검토 경계가 필요하다. 따라서 현재 module CLI의 한 worker 안에 제안·적용을 몰아넣지 않고 기존 승인·작업 예약 기능을 재사용하는 별도 작업으로 연결한다. 정확한 stage·실행 계획 매핑은 구현 시 정하고 현재 고정 정책을 우회하지 않는다.

## 4. 제안 모듈 계약

| 제안 ID | 기준 처리 방식 | 필수 입력 | 출력 |
| --- | --- | --- | --- |
| `tabular_prepare_propose` | derive_on_train | 검증된 Train·확정 분할 증거·PreparationRules | 후보 preparation_state·변경 제안 |
| `tabular_prepare_apply` | apply_saved | 검증된 입력 구간·승인된 후보 상태·분할 증거 | 새 prepared_data·행 연결·처리 기록 |

후보 상태에는 설정·알고리즘 버전·산출 Train의 출처/분할 식별값·입력 역할·유지 특징 순서·처리 통계를 결합한다. 적용 승인은 이 상태의 정확한 해시와 적용 대상 구간에 묶는다. 승인 후 후보·입력·규칙·자원 한도가 바뀌면 새 승인을 요구한다.

초기 범위는 결측률 기준 특징 제거·상수 특징 제거·수치 대치(median/mean/none)다. 지원하지 않는 설정을 자동으로 끄지 않고 명시적으로 거부한다. 기존 스케일링·이상치 clip·범주화·원핫 알고리즘은 보존하며 후속 연결 대상으로 둔다.

## 5. 검토 필요를 다루는 방식

현재 `review_required` 실행은 그대로 중단·보존한다. 새 변환 설정을 넣었다고 과거 품질 보고서를 passed로 바꾸거나 소비한 승인을 되살리지 않는다.

향후 변경 제안은 HIGH_MISSING_RATIO·CONSTANT_FEATURE·ALL_MISSING_FEATURE 등 명시적으로 처리 가능한 finding과 변환 규칙을 연결한다. 제거 대상은 전체 데이터 EDA가 아니라 해당 Train에서 다시 산출한다. 라벨 오류·필수 ID 누락·분할 증거 불일치 등은 특징 제거로 해결한 것으로 취급하지 않는다.

사용자 적용 승인은 특정 검토 항목의 처리만 허용한다. 파생 결과는 다시 검사하고 남은 검토/차단 항목이 있으면 중단한다. 모든 검사를 ignore로 바꿔 진행하는 경로를 만들지 않는다.

## 6. 결과 검증과 제한

- 원본은 덮어쓰지 않는다. 라벨·ID·group·timestamp는 특징과 분리하고 행 연결을 보존한다.
- Validation·Test에서 제거 목록·중앙값·범주·스케일링 기준을 재산출하지 않는다. 검증을 이유로 부모가 다시 산출하는 것도 하지 않는다.
- 부모는 허용 파일·크기·해시·JSON 필드·특징 순서·행/구간 연결·설정과 상태 일관성을 검사한다. pickle/joblib·임의 코드는 읽지 않는다.
- 기존 load_preparation은 변환 상태 구조를 검증하지만, 격리 부모에서 이를 직접 호출할지 또는 제한된 JSON 검증기로 분리할지는 구현 전에 검토한다. 원본을 읽는 기존 어댑터 validate를 그대로 사용하지 않는다.
- 실제 중앙값·제거 정확성은 정답을 아는 합성 데이터 테스트로 확인한다. 파일 계약 검사만으로 일반 데이터의 통계 정답을 보증하지 않는다.
- 출력 열·셀·파일 크기·worker 메모리·프로세스 수·시간을 제한한다. 한도 초과 시 부분 완료로 처리하거나 데이터를 조용히 자르지 않는다.
- LLM은 입력·통계·제거 목록·후보 상태를 받거나 검증하지 않는다. 원본 폴더·승인 DB·네트워크 권한은 확대하지 않는다.

## 7. 구현 순서와 완료 조건

후속 갱신: [내보내기 요청·worker·부모 파일 검증·승인 CLI·AppContainer 운송·커밋 연결](../guides/PARTITION_EXPORT.md)을 구현했다. 합성 연결 테스트는 통과했으며 실제 Windows 격리 실행 완료로 취급하지 않는다.

진행 갱신: [확정 분할·구간 입력 계약](PARTITION_INPUT_CONTRACT.md)의 타입·읽기 전용 검증과 내보내기 커밋 결과 수용을 합성 검증했다. 다음은 합성 네이티브 운송 확인과 Train 전용 전처리 후보 기준 산출이다.

1. 확정 분할 증거와 구간별 입력 snapshot의 연결 계약부터 준비한다.
2. 기존 복합 변환기를 감싸는 후보 산출·기준 적용 계약과 등록 타입을 만든다.
3. 제안 결과의 부모 검증기·적용 승인 범위를 준비한다.
4. 격리 산출·적용 worker와 기존 실행 관리자를 연결한다.
5. 합성 정상·검토 중단·누수 방지·상태 변조·승인 불일치·저장 복원 테스트를 수행한다.
6. 사용자 합성 실제 OS 실행을 확인한 뒤 실데이터 사용 범위를 검토한다.

정확히 50%인 특징은 제거하지 않고 초과만 제거하는지, 상수/전체 결측의 정책과 제거 개수가 맞는지, Validation의 극단값이 Train 기준을 바꾸지 않는지, 적용 시 fit을 다시 호출하지 않는지 확인한다. 삭제·열 순서·NaN·필수 컬럼 누락·라벨/ID 보존도 검사한다.

이 문서는 변환 작업 승인이 아니다. 각 실행의 후보 산출과 적용은 여전히 별도 사용자 승인이 필요하다.

### 2026-10-17 현재 상태

사용자 Windows 실행에서 분할·구간 내보내기·Train 후보 산출·별도 승인 후 Train/Validation 적용을 확인했다. `secom-prep-apply01`은 `applied / transformed: true / refit: false / test_used: false`이며 저장 결과의 기존 계약 검증도 통과했다. 자세한 실행 기록은 [저장 기준 적용](../guides/PREPARATION_APPLY.md#실제-실행-확인-2026-10-17)을 따른다. 위 진행 갱신은 구현 당시 이력이며 현재 미구현 목록이 아니다.

남은 연결 범위는 전달용 결과 계약과 모듈 등록부·파이프라인 계획 통합이다. 후보 산출·적용 자체는 별도 승인 CLI로 구현됐지만, 제안 ID를 등록해 모듈형 파이프라인에서 실행하는 기능까지 완료된 것은 아니다. 사용자 모듈 등록·LLM 제안도 별도 후속 범위로 유지한다.

후속으로 [변환 모듈 등록과 승인 계획](PREPARATION_MODULE_PLAN.md)을 구현했다. 두 모듈의 고정 등록·설정·정적 순서·단계별 새 승인 경계·기존 CLI 매핑까지 지원한다. 아직 새 계획에서 작업을 자동 생성·실행하지 않으며, 증거 결합과 실행 관리자 연결은 다음 단계다.

추가 구현: [통합 실행 관리자](../guides/PREPARATION_PIPELINE_EXECUTION.md)가 계획·입력 증거를 기존 하위 실행기에 연결한다. 후보 산출 완료 후 사용자 review로 적용 작업을 생성하고 별도 APPLY 승인을 요구한다. 기존 완료 실행을 가져와 승인 없이 실행하지 않으며, 합성 연결 검증과 실제 Windows 통합 실행 확인은 구분한다.
