# WaferGuard 전처리 에이전트 기초 설계

현재 구현 상태와 읽는 순서는 [문서 안내](GUIDE.md)를 기준으로 합니다. 아래의 날짜별 설계·검증 기록은 해당 시점의 범위와 구분해서 읽습니다.

## 현재 기준 — 2026-10-20

- **실행:** CSV 5개 작업(품질·EDA·분할, 구간 내보내기, Train 기준 후보, 저장 기준 적용, 로컬 전달)과 WM 정상 개발 6단계를 공통 UI·기존 CLI에 연결했다. CSV `csv_plan01`은 사용자 승인·완료 결과 검증·사용자 열람까지 확인했다.
- **LLM:** 로컬 Qwen/Ollama와 LangChain·LangGraph로 EDA 및 CSV workflow의 제안·확인 질문을 처리한다. LangGraph는 메모리 전용 제안 대화이며 전처리 worker·승인을 실행하는 그래프가 아니다. 실제 실행 순서·중단·승인·증거 검사는 기존 로컬 실행 관리자가 강제한다.
- **복원·연결:** 저장 EDA 제안은 목록 선택 후 명시적으로 불러오고, CSV 실행안은 이름으로 복원한다. 설정의 연결 확인은 loopback `/api/tags` 조회이며 추론·GPU 동작 검사가 아니다. B 항목의 실제 사용자 화면 확인까지 완료했다.
- **정보 전달:** 제안에는 확인한 요청·누적 질문/답변·등록 공개 명세·선택 규칙만 제공한다. 결과 해설은 별도 정책으로 허용한 집계·그래프만 제공한다. 원본 행·배열·맵·인증정보·승인 토큰·로컬 바인딩·전체 로그는 자동 첨부하지 않는다. 집계도 정보 추측 위험이 남으며 해설은 결과 검증을 대신하지 않는다.
- **검증:** 2026-10-20 마감 시점의 전체 합성 회귀는 958개 실행·945개 통과·13개 생략·실패/오류 0이다. 실제 OS 격리 재검증과 모델 품질 평가는 아니다. 근거와 생략 사유는 [GUIDE](GUIDE.md#현재-구현-상태)를 따른다. 2026-10-22 최신 전체 회귀 `ea687d47…`는 1126개 실행·1112개 통과·오류 1개·생략 13개로 PASS가 아니다. 오류 테스트는 수정 후 해당 모듈만 재실행해 통과했다. 통합 작업(표형) 구현 상태와 후속 순서는 [GUIDE](GUIDE.md) 상단을 따른다.
- **보류:** 결과 해설의 추가 편집/영구 저장/자동 민감 정보 탐지, WM 충돌 분기 생성 UI·일반 pickle canonical 후속 EDA·사용자 모듈 일반화, 외부 API·RAG·외부 추적·전체 자동 진행.

아래 날짜별 메모와 최소 상태 DTO 기반 런타임 선택기(`minimal_state_v1`, `bounded_llm`)는 초기 설계·확장안이다. 현재 구현 완료를 뜻하지 않는다. 현재 제공하는 제안 대화·선택형 해설과 혼동하지 않으며, 초기 완료 체크 전체를 현행 마감의 필수 미완료 목록으로 사용하지 않는다.

## 1. 목적과 에이전트의 의미

전처리 에이전트는 프로파일에 따라 구조·품질 검사, EDA, 필요한 학습 입력 준비를 관리하는 **사용자 승인형 실행 시스템**이다. 입력 형식은 등록 어댑터가 해석하고 분석은 독립적인 공통 코어가 수행한다. LLM은 등록 기능·사용자 규칙에 맞는 실행안과 확인 질문을 제안하고, 별도 정책으로 결과를 해설한다. 실제 계산·필수 차단·승인은 로컬 실행기가 강제한다. EDA 전용 요청에 분할·이미지 캐시 생성을 강제하지 않는다.

이번 프로젝트에서 보여줄 가치는 전처리 자동 실행, 품질 실패 시 차단, 사람의 승인, 중단 후 안전한 재개, 데이터·산출물 추적이다. 처음부터 여러 에이전트의 자유로운 토론이나 자율 코드 생성을 도입하지 않는다.

현재 버전은 **LLM의 제안과 규칙 기반 실행을 분리하는 방식**이다. 모델이 전처리 방법·품질 기준·라벨·분할 정책을 임의로 변경하지 않는다. 결정적 보고서는 로컬 코어에서 생성하고 LLM 해설은 보조 설명으로 구분한다. LLM 없이도 등록 모듈을 직접 선택해 실행할 수 있으며, 이를 자율적인 AI 판단으로 포장하지 않는다.

### 할 일과 하지 않을 일

| 할 일 | 하지 않을 일 |
| --- | --- |
| 설정·입력 경로·실행 환경 검사 | 임의 웹 다운로드·패키지 설치·코드 생성/실행 |
| 승인된 원본 읽기·품질 검사 도구 호출 | 출처 불명 pickle 자동 역직렬화 |
| 공개 명세·사용자 선택 규칙으로 등록 작업의 실행안 제안 | 불리한 결과를 삭제하거나 품질 기준 완화 |
| 분할안·예상 용량을 보여주고 승인 요청 | 자동 라벨 변경·재분할·seed 무제한 탐색 |
| 결정적 캐시·Dataset 계약 검사 실행 | Test 성능에 맞춘 전처리 최적화 |
| 중단 상태와 완료 산출물 보존 | 원본·완료 산출물 덮어쓰기·자동 삭제 |
| 실제 결과를 로컬 보고서로 표시하고, 별도 허용된 집계·그래프만 LLM 보조 해설 | 원본·오류 원문·전체 실행 문맥을 자동 전송하거나 해설을 검증 판정으로 사용 |
| 해결 불가 시 사용자 확인 요청 | 공정 원인·출하 승인·통합 검출률 확정 |

## 2. 구성 요소와 의존성

```text
사용자 요청 / 검증된 설정
          │
          ▼
로컬 실행 진입점 · 승인 처리
          │
          ▼
등록 계획 · 로컬 실행 관리자 ─── SQLite 승인 · 실행 기록
          │
          ▼
도구 실행기 · 권한/입출력 검사
          │
          ▼
전처리 코어 (원본 읽기·검사·분할·변환·캐시·계약 검증)
          │
          └──► 결정적 결과 보고서 (로컬에서 생성·열람)

확인한 요청·공개 규칙 → LangChain·로컬 모델 → LangGraph 제안·확인 질문
                                            ↓
                         제안 계약 검증 → 사용자 검토 → 로컬 입력 결합

검증된 결과 → 별도 전달 정책·민감도 확인 → 허용 집계·그래프의 보조 해설
모델에는 직접 파일·도구·승인·worker 실행 권한 없음

LangSmith: 실제 데이터 처리 경로에서는 외부 추적 금지
```

공통 코어는 `src/preprocessing/`이며 에이전트 없이 입력 검사·EDA를 호출할 수 있다. `src/agents/adapters/`가 CSV 또는 WM metadata를 공통 계약으로 변환한다. WM 맵 특화 기능은 `src/wafer_dl/`에 유지한다. 공통 코어가 agents·wafer_dl·sensor_ml을 import하지 않으며 Dataset과 학습 코드가 LangGraph·LangChain·API 키에 의존해서는 안 된다.

| 도구 | 이번 설계의 역할 | 필수 여부와 제한 |
| --- | --- | --- |
| LangGraph | 제안 대화·확인 질문 중단/재개·메모리 체크포인트 | `llm_dialogue.py`·`llm_workflow_dialogue.py`에서 사용. worker·승인 실행은 로컬 관리자 담당 |
| LangChain | 로컬 모델 호출·구조화 제안 adapter | 공개 제안 계약에 사용, 코어에는 불필요. 결과 해설 운송은 별도 정책 경로 |
| LangSmith | 합성 데모의 추적·설명 품질 평가 후보 | 실제 데이터 실행 추적 금지, 로컬 기록을 대체하지 않음 |
| 공통 전처리 코어 | 컬럼 역할 검사·분포·결측·상관·로컬 보고서 | 데이터셋 독립 계산 경로 |
| 데이터 어댑터·도메인 확장 | 파일 읽기·공통 입력 변환, 필요시 맵/그룹 등 특화 처리 | 코드에 등록한 기능만 사용 |
| 로컬 저장소 | 실행 상태·승인·산출물 연결 | 초기 필수. 외부 서비스 없이 재개 가능 |

라이브러리 버전은 구현 때 환경과 기능을 확인해 별도 의존성 파일에 기록한다. 문서의 API 이름만 보고 최신 버전을 무조건 설치하거나 기존 ML 환경을 변경하지 않는다. 다중 사용자 서버·클라우드 배포·자동 학습 실행은 초기 범위 밖이다.

## 3. 프로파일별 작업 그래프

프로파일은 코드에 등록한 `eda_review_v1` 또는 `training_preparation_v1`을 선택한다. 전자는 `preflight → audit → run_eda → review_eda → validate_contract → render_report`이며 분할·캐시를 생성하지 않는다. 후자는 학습 입력 준비 템플릿으로 `prepare_data`를 사용한다. 템플릿 정의는 모든 처리 도구의 구현 완료를 뜻하지 않는다. 상세 단계와 실행 계약은 [범용 설계 5절](design/GENERIC_PREPROCESSING_DESIGN.md#5-프로파일-설정과-실행-계획)을 따른다.

아래 그래프와 노드 표는 WM 맵 전처리 적용 예시다. Lot·해상도·채널·캐시는 도메인 조건이며 모든 데이터에 강제하지 않는다. 승인 UI 노드는 공통 실행기의 민감 작업 승인 게이트로도 표현할 수 있다.

```text
preflight
   ↓
approve_source ── 거부 → cancelled
   ↓ 승인
ingest → audit
           ├── 필수 검사 실패 → blocked_input
           └── 통과
                 ↓
             run_eda
                 ↓
             review_eda ── 미확인/문제 → awaiting_approval
                 ↓ 사용자 확인
             propose_split
                 ↓
             approve_split ── 거부/수정 → awaiting_approval / cancelled
                 ↓ 승인
             commit_split
                 ↓
             approve_prepare
                 ↓ 승인
             prepare_cache → validate_contract
                                  ├── 실패 → blocked_input / failed_runtime
                                  └── 통과 → publish
                                               ↓
                                         render_report
                                               ↓
                                           completed
```

`publish`는 인터넷 공개가 아니라 로컬 완료 산출물 등록이다. Git 커밋·push·외부 업로드는 하지 않는다. 사용자가 설정 수정으로 승인안을 바꾸면 해당 승인과 이후 결과는 무효화하고 새 계획을 제시한다.

### 노드별 입력·출력

| 노드 | 입력 | 출력·통과 조건 |
| --- | --- | --- |
| preflight | adapter·설정·원본 위치·출력 루트 | 유효 설정, 접근 가능 경로, 디스크/RAM 사전 점검 |
| approve_source | 원본 출처·파일 식별·읽기 위험 | 해당 파일과 작업에 연결된 명시적 승인 |
| ingest | 승인된 원본 | canonical 맵·전체 행 manifest, 원본 보존 |
| audit | canonical 산출물 | 품질·미라벨·중복·Lot 집계, 제외 기록, blocker 목록 |
| propose_split | 검사 완료 데이터·분할 정책 | 미확정 분할안, 클래스 지원·중복 그룹·비율 검사 |
| approve_split | 정확한 분할안과 경고 | 사용자 결정 또는 승인 대기 |
| commit_split | 승인된 분할안 | 변경 불가 계약으로 등록한 split manifest |
| approve_prepare | 해상도·채널·증강·캐시 예상 용량 | 변환 계획과 자원 사용 승인 |
| prepare_cache | 확정 split·변환 설정 | 결정적 캐시. Train 증강 결과는 캐시하지 않음 |
| validate_contract | manifest·캐시·클래스 매핑 | 무결성·배치·split 비중첩·마스크 검사 결과 |
| publish | 필수 검사 통과 산출물 | 완료 레지스트리와 전달 묶음 |
| render_report | 검증된 지표·근거 경로 | 수치가 결정적으로 삽입된 Markdown 보고서 |

### 3.1 제한적 자율 선택 분기

이 절은 초기 확장 설계이며 현재 worker 실행에 연결된 LLM 선택기가 아니다. 현재 모델은 품질 결과를 받아 런타임의 다음 도구를 자동 선택하지 않는다.

기본 그래프의 승인·필수 검사는 고정한다. `audit`·분할안 검사·캐시 계약 검사 뒤에 선택 지점을 두되, 안전 실행기가 먼저 필수 blocker를 판정한다. 기본 그림의 실패 화살표는 후속 전처리를 차단한다는 뜻이다. 선택 모드에서는 `blocked_input` 또는 `failed_runtime`으로 최종 대기하기 전에 제한된 진단·사용자 확인 분기를 거칠 수 있지만, 이를 통해 실패한 필수 검사를 통과한 것으로 바꾸지 않는다.

```text
로컬 도구 결과
   ↓
안전 실행기: blocker·선행 조건·승인·호출 한도 판정
   ↓
정보 축소 게이트: 승인된 최소 상태·가능한 동작 ID 생성
   ↓
LLM 선택 → 응답 스키마·현재 허용 동작 검증 → 도구 실행 / 사용자 확인
   └── 실패·한도 초과 → 결정적 규칙 경로 / 안전 중단
```

| 동작 ID | 로컬 작업 | 제한 |
| --- | --- | --- |
| inspect_structure | 기존 canonical 데이터의 구조 진단 | 읽기 전용. 원본 재역직렬화·LLM으로 상세 결과 반환 금지 |
| inspect_split_constraints | 기존 분할안의 비중첩·지원 조건 진단 | 재분할·seed 변경 금지 |
| verify_cached_contract | 기존 캐시의 계약 재검증 | 캐시 재생성·덮어쓰기 금지 |
| request_user_review | 로컬 근거와 선택지를 사용자에게 표시 | 승인 자체를 생성하지 않음 |
| continue_workflow | 고정 그래프의 다음 단계로 복귀 | 선행 조건·승인·blocker를 실행기가 다시 검사 |

한 선택 지점에서 LLM 선택은 최대 3회, 동일 상태·동작 반복은 거부한다. 이 한도는 도구 I/O 재시도 한도와 별개다. 진단으로 같은 blocker가 남으면 사용자 확인으로 종료하고 무제한 자기 수정 루프를 만들지 않는다. 한도가 부족하면 사용자가 근거를 확인한 뒤 새 계획으로 명시적으로 재개한다.

LLM은 위 노드를 자유롭게 추가하거나 순서를 바꾸지 않는다. 미라벨 분리·품질 격리 등은 사용자가 사전에 승인한 설정 범위에서 코어가 수행한다. 일반 경고를 승인할 수는 있어도 필수 불변식 위반을 단순 승인으로 우회하지 않는다.

## 4. 상태와 추적 계약

### 4.1 그래프 상태

| 필드 | 의미 |
| --- | --- |
| run_id, thread_id | 로컬 실행·체크포인트 식별자. 가명 ID로 바꿔도 외부 전송 금지 |
| adapter_id, profile_id, workflow_id | 등록된 입력 로더·검증 프로파일·검토된 실행 템플릿 |
| status, current_stage | 실행 상태와 현재 단계 |
| config_ref, config_id | 검증한 설정 사본과 식별자 |
| source_id, dataset_version | 승인된 원본 식별과 정규화 버전 |
| split_protocol_id, preprocess_version | 분할·변환 계약 |
| artifact_refs | 단계별 파일 위치·검증 기록·완료 상태 |
| quality_summary_ref | 상세 검사 보고서 위치. 배열 전체를 상태에 넣지 않음 |
| blockers, warnings | 구조화된 오류 코드·한국어 메시지·근거 |
| approval_requests, approval_records | 승인 대상·계획 식별자·결정·시점 |
| attempts | 단계별 시도 횟수·실패 코드 |

원본 맵 배열·전체 라벨 목록·DataFrame·API 키·살아 있는 파일 핸들은 그래프 상태에 넣지 않는다. 체크포인트와 상세 결과는 접근 통제된 로컬 저장소에만 보존한다. 전체 상태를 LLM 메시지로 직렬화하지 않고 8절의 최소 DTO만 별도로 생성한다. LLM 선택기 프로세스에서 실제 파일·상태 저장소에 접근할 수 없게 한다. 요청·선택·거부 사유의 연결 기록은 로컬에만 남긴다.

### 4.2 상태 전이

- `created → running → awaiting_approval → running → completed`가 기본 흐름이다.
- `blocked_input`: 데이터 구조·품질·분할 불가. 사용자 판단이나 입력 변경 전 자동 재시도하지 않는다.
- `failed_runtime`: I/O·환경·자원 오류. 원인별로 재시도 가능 여부를 판단한다.
- `cancelled`: 사용자가 취소. 부분 산출물을 자동 삭제하지 않는다.
- `completed`는 필수 계약 검사와 로컬 등록을 통과했다는 뜻이며 모델 성능·학습 완료·배포 승인과 다르다.
- LLM 선택 실패는 필수 검사를 생략하는 이유가 아니다. 검증된 규칙 경로로 복귀하거나 안전 중단한다. 완료한 산출물은 유지한다.

최초에는 실행 1개를 직렬 처리한다. 대용량 원본 로드·캐시 생성 두 작업을 동시에 시작하지 않는다. 도구 내부 병렬 수는 검증된 설정에서만 받는다.

## 5. 사람의 승인과 실행 권한

### 5.1 승인 지점

| 승인 | 사용자에게 보여줄 내용 | 승인 범위 |
| --- | --- | --- |
| 원본 신뢰 | 출처·파일명·크기·식별값·pickle 위험 | 해당 원본의 역직렬화·지정된 로컬 처리 |
| 분할 확정 | Lot·중복 정책·클래스 지원·제외량·목표 비율 차이 | 해당 분할안 등록 |
| 변환/캐시 | 해상도·채널·품질 규칙·예상 디스크·출력 위치 | 해당 변환 버전 생성 |
| 제한적 LLM 선택 모드 | provider·endpoint·전송 상태 항목·추측 위험·호출/비용 한도 | 승인된 최소 상태 계약에만 적용. 원본·집계·식별자 전송으로 확대 불가 |

초기에는 각 지점을 보여주고 승인받는 방식을 기본으로 한다. 익숙해진 뒤 하나의 입력 계획에 대한 묶음 승인을 추가할 수 있지만, 미래 설정 변경까지 포괄하는 승인을 만들지 않는다.

전처리 승인은 `(run_id, stage, source_id, config_id, plan_id)`에 연결한다. 원본·설정·계획이 바뀌면 이전 승인으로 진행하지 않는다. LLM 모드 승인도 로컬에서 해당 계획에 연결하지만 이 식별자들은 LLM에 보내지 않는다. LLM의 텍스트나 데이터에 들어 있는 `approved=true`는 승인 기록이 아니다.

LangGraph `interrupt()`는 승인 대기에 활용할 수 있다. 재개 시 해당 노드가 처음부터 다시 실행될 수 있으므로, 승인 노드 앞부분에서 원본 읽기·파일 쓰기 같은 부작용을 수행하지 않고 승인과 실행 노드를 분리한다. 체크포인트·thread_id가 필요하다는 점과 재개 동작은 [공식 문서](https://docs.langchain.com/oss/python/langgraph/interrupts)를 따른다.

### 5.2 도구 권한

- Python 함수와 구조화된 인자만 허용한다. LLM이 생성한 셸 문자열·Python 코드·파일 경로를 그대로 실행하지 않는다.
- 읽기는 등록된 원본·해당 실행 산출물로, 쓰기는 승인된 data/processed·logs·reports의 실행 하위 경로로 제한한다.
- 경로를 정규화하고 절대 경로 이탈·`..`·심볼릭 링크/Windows junction을 통한 외부 접근을 검사한다. 허용 루트를 벗어나면 거부한다.
- 원본 수정·완료 산출물 덮어쓰기·모델 학습·Test 성능 평가·네트워크 다운로드·파일 삭제 도구는 초기 allowlist에 넣지 않는다.
- Test 캐시의 구조 검사 권한은 모델 성능 평가 권한과 다르다. 전처리 승인으로 Test 학습·예측까지 허용하지 않는다.

승인 UI와 Python 경로 검사는 실수 방지·애플리케이션 통제다. 임의 코드를 실행할 수 있는 공격자를 격리하는 OS 보안 경계로 주장하지 않는다. 다중 사용자·외부 파일 서비스로 확장하면 별도 계정·샌드박스·인증 설계가 필요하다.

## 6. 저장·중단·재개와 실행 범위 관리

### 6.1 저장 원칙

초기는 로컬 영속 체크포인트 저장소를 사용한다. 재시작 재개가 필요한 실행에서 메모리 전용 저장소를 완료 구현으로 간주하지 않는다. 사용 DB·checkpointer 패키지·버전은 구현 때 확인한다. [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)는 상태 보존 계층으로 사용하되 데이터 캐시의 무결성을 대신하지 않는다.

산출물은 단계별 임시 경로에 쓰고, 파일 검사와 완료 표식이 모두 준비된 뒤 등록한다. 동일 실행·단계에는 배타적 실행 잠금을 사용한다. 취소·오류 후 부분 산출물을 완료 데이터로 노출하지 않는다. 잠금의 오래된 여부를 확인하지 않고 자동 해제하지 않는다.

체크포인트와 데이터 파일 쓰기는 하나의 원자적 트랜잭션이라고 가정하지 않는다. 중간 장애 때는 다음을 확인한다.

1. 해당 원본·설정·버전과 연결된 산출물인가?
2. 필수 파일·행 수·범위·계약 검사·완료 표식이 일치하는가?
3. 완료 산출물이면 재계산 대신 재사용 사실을 기록한다.
4. 부분 결과면 승인된 실패 단계부터 새 시도 경로에서 실행한다. 이전 결과는 보존한다.

따라서 체크포인트가 있다고 도구 실행이 항상 정확히 한 번만 일어나는 것은 아니다. 중복 호출에도 완료 결과를 재사용하거나 명확히 거부하는 멱등성 검사를 도구 쪽에 구현한다.

### 6.2 재실행 범위

| 변경 | 에이전트가 제안할 범위 |
| --- | --- |
| 원본·adapter·라벨/품질 기준 | ingest 이후, 기존 승인 재검토 |
| 분할 정책 | 분할안 생성 이후, 승인 재요청 |
| 해상도·보간·채널 | 캐시 생성 이후, 변환 승인 재요청 |
| Train 증강 | Train 변환 계약 갱신, 학습 담당에게 재학습 필요 안내 |
| 모델/loss 설정 | 전처리 결과 재사용 가능 여부만 안내. 학습 실행은 담당 영역 |
| 실제 결과 보고서 | 로컬 보고서 단계만. 원본 읽기·분할·캐시 생성 반복 금지 |
| LLM provider·최소 상태 계약 | 전송 범위 재검토·승인. 전처리 데이터 재생성은 금지. 상태 계약 확대는 보안 설계 변경으로 별도 검토 |

범위 판단은 명시한 의존 관계와 설정 식별자를 사용한다. 각 소스 파일에 수작업으로 해시를 적는 관리 작업은 만들지 않는다. 원본·설정 식별값은 자동 계산하고 처리 코드의 의미 변경은 preprocess_version 갱신으로 관리한다. 과거 Test 사용 이력은 재분할·복사·새 run_id로 초기화하지 않는다.

## 7. 실패와 재시도 정책

| 상황 | 처리 |
| --- | --- |
| 필수 컬럼 없음·미지 라벨·분할 불가능 | blocked_input. 근거와 사용자 선택지를 표시, 자동 재시도 없음 |
| RAM/디스크 부족·권한 없음·패키지 불일치 | failed_runtime. 자원·환경 수정 후 명시적 재개 |
| 명확한 일시 I/O 오류 | 멱등성 확인 후 최대 2회 재시도 제안. 최초 실행 포함 최대 3회 |
| 작업 제한 시간 초과 | 프로세스 종료 상태 확인 후 정지 기록. 이전 작업이 살아 있으면 중복 실행 금지 |
| LLM timeout·rate limit·스키마 오류 | 동일 최소 payload로 최대 1회 재시도 후 규칙 경로 또는 안전 중단. 원문 오류·응답을 재질문에 추가하지 않음 |
| 사용자가 취소 | 신규 도구 호출 중단, 실행 중 도구의 안전한 종료 확인, 부분 결과 보존 |

모든 단계에 짧은 동일 timeout을 적용하지 않는다. 원본 로드·캐시 생성은 대용량 작업이므로 소규모 측정 후 단계별 제한과 heartbeat를 설정한다. LLM 호출 예산·timeout은 데이터 처리와 분리한다.

도구 출력은 `status`, `artifact_refs`, `metrics`, `warnings`, `errors`의 고정 스키마를 사용한다. 오류에는 코드·한국어 설명·단계·근거 경로를 포함하되 로컬 기록으로만 보존한다. 이 전체 출력이나 실제 오류 코드를 보내지 않고, 고정 매핑으로 축소한 승인 상태만 LLM에 전달한다. 매핑되지 않은 오류는 로컬 사용자 확인으로 처리한다.

## 8. LLM의 사용 범위와 provider 독립성

### 8.1 초기 정책

8.1~8.4의 최소 상태 선택기 계약은 미활성 초기 설계다. 현행 provider는 로컬 Ollama의 설정 가능한 Qwen이며 제안 대화와 선택형 결과 해설의 계약·전달 정책을 분리한다. 이 절의 예제 모드를 현재 UI 설정이나 실행 가능한 운영 모드로 안내하지 않는다.

권장 운영 모드는 `bounded_llm`이다. 최초 실행은 provider와 전송 계약 검토·명시적 모드 승인 전까지 `rules_only`로 유지한다. API 키·provider 패키지가 없어도 코어 전처리·승인·재개·수치 보고서가 모두 동작해야 한다. LLM 모드 실패 시 규칙 경로로 복귀하거나 안전 중단하며 모드 전환을 로컬에 기록한다.

LLM은 **최소 상태를 받는 선택기 경계에서만** 호출한다. LangGraph에는 게이트를 통한 선택 노드를 두고, 전처리 코어에는 provider SDK·LLM 호출을 넣지 않는다. 외부 API·로컬 모델에 같은 입력 계약을 적용한다. 실제 provider·모델·배포 방식은 미정이며 임의 API URL은 허용하지 않는다. 외부 API는 endpoint·데이터 보관·학습 이용·요청 로그 정책 검토 후 사용한다. 무학습·무보관 정책은 금지 데이터를 보내도 된다는 근거가 아니다.

### 8.2 허용되는 입력과 출력

허용 입력은 사전 검토한 정적 도구 설명·안전 규칙과 **최소 정형 상태 DTO**다. 원본에서 추출한 자유문이나 전체 도구 결과를 넣지 않는다. 허용 상태는 `structure_check_passed`, `structure_review_required`, `split_constraints_unmet`, `cache_check_passed`, `cache_review_required`로 시작한다. 실제 오류의 세부 유형·컬럼명·클래스명·수치·건수는 숨기고 다수의 내부 결과를 하나의 일반 상태로 매핑한다. 매핑표는 구현 전 별도 검토한다.

요청 예시(문서용):

```json
{
  "contract_version": "minimal_state_v1",
  "check_state": "split_constraints_unmet",
  "allowed_actions": ["inspect_split_constraints", "request_user_review"]
}
```

`contract_version`은 공개된 메시지 계약 버전이며 데이터·원본·실행 버전이 아니다. 허용 동작 목록은 실행기가 현재 안전 정책으로 생성하고 임의 문자열은 받지 않는다. 이 상태와 동작 목록 자체가 제한적으로 허용한 운영 정보다.

| 정보 종류 | LLM 입력 정책 |
| --- | --- |
| 원본 맵·센서·배열·라벨·샘플 | 금지 |
| crop·resize·마스크·썸네일·대표 그림·모델 입력 tensor | 금지 |
| 클래스 빈도·불량률·평균/분산·분위수·히스토그램·중복률 | 정확값·반올림·구간화 모두 금지 |
| Lot·시간·장비·공장·해상도 분포·처리 순서 | 금지 |
| 샘플 수·파일 크기·경로·원본/맵 해시·버전·run_id | 금지 |
| 실제 설정·threshold·선택 센서·품질 기준·가중치·클래스 매핑 | 금지 |
| 실제 오류 코드·누락 컬럼명·세부 상태·처리 시간·메모리·진행률 | 금지 |
| 승인된 일반 검사 상태·현재 허용 동작 ID | 최소 계약의 열거값만 허용. 운영 상황의 일부 추측 위험은 남음 |
| 예측·성능·임베딩·파생 특징·학습된 파라미터 | 금지 |
| 마스킹·가명화·암호화한 원본 유래 payload | 금지. 익명성·추측 불가능성의 근거로 삼지 않음 |
| 실제 데이터로 생성한 가상·합성·임의 요약 정보 | 최소 상태 계약 외에는 금지 |
| 사전 승인된 정적 도구 설명·안전 규칙 | 허용. 실제 설정값을 동적으로 삽입하지 않음 |

공개 WM-811K도 처리 경로의 실제 데이터로서 같은 제한을 적용한다. 공개 데이터라는 이유로 추가 전송 예외를 만들지 않는다. 사용자가 실제 수치를 입력한 자유문도 받지 않는다. 여러 요청의 상태·빈도·순서·시점으로 운영 상황을 추측할 수 있으므로 상태 축소·호출 한도·이력 미전송으로 노출을 줄이되, 역추론 불가능성을 보장하지 않는다. 이 잔여 위험이 허용되지 않는 환경에서는 `rules_only`를 사용한다.

### 8.3 정보 경계와 전송 게이트

1. **데이터 처리 프로세스**는 원본·캐시·체크포인트에 접근하지만 LLM SDK·키·외부 네트워크 권한을 갖지 않는 구성으로 만든다.
2. **LLM 선택기 프로세스**는 정적 정책과 최소 DTO만 읽는 별도 권한으로 실행하며 data·logs·models·reports·전체 그래프 상태를 마운트하거나 읽지 않는다. 승인된 provider 또는 격리된 로컬 모델에만 연결한다. 단순한 Python 함수 분리는 격리가 아니다.
3. **로컬 정보 축소 게이트**가 내부 결과를 고정 상태에 매핑한다. provider가 원본 결과를 받아 요약하게 하지 않는다. 자유문·파일 첨부·클립보드·run_id·실제 error_code·원문 stack trace를 전달할 입구를 만들지 않는다.
4. 게이트는 열거값만으로 새 DTO를 만든다. 전체 상태를 복사한 뒤 일부 필드를 지우는 방식은 쓰지 않는다. 알 수 없는 키·임의 metadata·문자열 추가가 있으면 전송 전에 거부한다.
5. 계약 버전·상태 열거값·동작 목록·정적 프롬프트·전송 대상·크기를 검사한다. 헤더·요청명에도 실행 식별자를 넣지 않는다. 비밀 문자열 정규식 검출은 보조 수단이며 검출되지 않았다고 허용하지 않는다.
6. LLM에 파일·검색·코드 실행·DB·셸·RAG·직접 도구 callback을 주지 않는다. LLM은 동작 ID를 제안할 뿐이며 로컬 실행기가 검증 후 실행한다. 재시도·오류 보고·telemetry에도 같은 전송 제한을 적용한다.
7. 판단 불가·검사 실패·설정 모순은 **전송 없이 종료**한다. 허용을 위해 사용자에게 원본 데이터를 붙여 넣으라고 요청하지 않는다.

OS·컨테이너·네트워크의 실제 권한 분리를 구현·검증하기 전에는 위 경계를 실현했다고 주장하지 않는다. 앱 설정만으로 절대 유출되지 않는다고 보장하지 않는다.

### 8.4 선택 응답과 실행 검증

출력의 초기 스키마:

```json
{
  "action_id": "inspect_split_constraints",
  "reason_code": "CHECK_CONSTRAINTS"
}
```

응답은 **권한 없는 선택 제안**이다. 동작·사유는 고정 열거값만 받고 자유문·경로·코드·설정값·추가 인자는 거부한다. 사유 코드는 `CHECK_STRUCTURE`·`CHECK_CONSTRAINTS`·`VERIFY_CONTRACT`·`NEEDS_USER_REVIEW`·`READY_TO_CONTINUE`로 시작하며, 각각 3.1절의 동작 순서에 대응한다. 실행기는 응답 수신 후 현재 상태·선행 조건·승인·잠금·도구 허용목록·호출 한도를 다시 검사한다. 오래된 응답은 거부하며 요청과 로컬 계획 연결은 외부로 보내지 않는 실행기 기록으로 관리한다. LLM이 `continue_workflow`를 골라도 blocker나 승인 대기를 우회할 수 없다.

각 요청은 이전 대화·추론 내용·전체 도구 이력을 포함하지 않는 독립 요청으로 만든다. provider의 대화 메모리·벡터 DB·자동 도구 루프는 사용하지 않는다. 실제 보고서와 선택 사유 설명은 로컬 템플릿·사유 코드로 생성하고 상세 수치·오류·설정은 로컬에서만 표시한다. LLM 선택을 데이터 분석·공정 원인 진단·성능 개선 근거로 주장하지 않는다.

## 9. 보안과 외부 추적

### 9.1 데이터와 명령 분리

CSV 값·라벨·metadata·오류 문자열·보고서에 들어 있는 지시는 신뢰할 수 없는 데이터다. `이전 규칙을 무시하라`, `파일을 업로드하라` 같은 내용이 있어도 명령·승인으로 실행하지 않는다. 프롬프트 경고문에만 의존하지 않고 도구 allowlist·인자 스키마·경로 검사·승인 기록을 애플리케이션에서 강제한다.

LLM 선택기 전용 API 키는 해당 프로세스의 환경 변수나 승인된 비밀 저장소에서만 읽는다. 데이터 처리 프로세스에 키를 전달하지 않으며 설정 JSON·그래프 상태·보고서·체크포인트·Git에도 저장하지 않는다. 오류 로그에서도 마스킹한다. 호출 수·토큰·예산을 제한하고 한도를 넘으면 규칙 경로 또는 안전 중단으로 전환한다.

### 9.2 LangSmith와 기타 외부 추적 정책

실제 데이터 처리의 LangSmith 등 **외부 추적은 계속 금지**하고 로컬 실행 기록만 유지한다. 최소 상태를 승인된 LLM endpoint로 보내는 예외가 외부 관측 서비스에도 적용되는 것은 아니다. 환경·SDK·callback·IDE의 추적 설정이 이미 활성화돼 있을 수 있으므로 실제 설정을 검사한다. 강제로 안전 상태를 만들 수 없으면 데이터 처리를 시작하지 않는다. provider 자체 요청 기록은 8.1의 별도 검토 대상이며 LangSmith 비활성화만으로 요청 보관이 없다고 주장하지 않는다.

LangSmith 사용 시연은 실제 데이터·환경·실행 이력에서 생성하지 않은 **독립된 수작업 합성 fixture**로 별도 환경에서만 허용한다. 실제 기록을 익명화하거나 합성처럼 바꿔 보내지 않는다. 실제 실행과 공유하는 thread_id·상태 저장소·키·로그 업로드 경로를 만들지 않는다.

LangSmith의 [조건부 추적](https://docs.langchain.com/langsmith/conditional-tracing)·[마스킹](https://docs.langchain.com/langsmith/mask-inputs-outputs)은 이 제약을 완화하는 근거가 아니다. SDK 오류 보고·일반 telemetry·자동 crash upload·프록시 로그도 점검한다. 데이터 처리 프로세스의 outbound 네트워크 차단을 검증하고, 필수 네트워크 작업이 필요하면 데이터 로드 전 별도 승인·분리 단계로 처리한다.

개인 로컬 데모의 승인 기록은 강한 인증·부인 방지 서명이 아니다. 외부 사용자에게 서비스하면 사용자 인증·권한 분리·보존 기간·파일 암호화·로그 접근 통제가 추가로 필요하다.

## 10. 설정·파일 구성 제안

현재 공통 코어는 `src/preprocessing/`, 프로파일은 `configs/agents/profiles/`, 프로파일 계획 생성은 `src/agents/workflow.py`에 구현했다. 파일별 현황은 [범용 설계 6절](design/GENERIC_PREPROCESSING_DESIGN.md#6-파일-구성과-호환)을 따른다. 데이터 규칙과 에이전트 실행 정책을 분리하고 split seed나 해상도를 중복 정의하지 않는다.

```text
configs/agents/profiles/  # 컬럼 역할·등록 adapter·workflow·EDA 옵션
src/preprocessing/       # 공통 계약·프로파일·EDA·workflow 정의
src/agents/
  state.py               # 로컬 상태·revision
  policy.py              # 작업 허용·차단
  approvals.py           # 승인 계약
  approval_store.py      # 승인·작업 이력 SQLite
  artifacts.py           # 완료·재사용 검사
  workflow.py            # 프로파일별 실행 계획
  executor.py            # 등록 도구 실행·재개
  adapters/              # CSV·WM metadata → 공통 입력
  cli.py                 # 합성 데모·프로파일 계획 조회
  minimal_state.py       # 예정: 최소 DTO 변환
  selector/              # 예정: 격리 IPC·provider
logs/agents/<run_id>/
  execution_plan.json
  state.json
  events.jsonl
  approvals.sqlite3
  attempts/
```

프로파일 JSON의 실제 설정 방법과 예시는 [범용 설계 5절](design/GENERIC_PREPROCESSING_DESIGN.md#5-프로파일-설정과-실행-계획)에 유지한다. 실행 정책과 LLM 선택기 설정은 데이터 프로파일과 분리한다.

LLM 선택기 설정 예시(별도 프로세스에서만 읽음):

```json
{
  "enabled": false,
  "provider": null,
  "model": null,
  "input_contract": "minimal_state_v1",
  "request_retry_limit": 1
}
```

모드 승인·provider 검토·계약 검증이 끝난 뒤 `mode=bounded_llm`과 선택기 `enabled=true`를 함께 사용한다. 모순된 설정은 거부한다. 호출당 토큰·실행당 총 요청 수·비용·timeout의 유한한 상한은 provider 선정 시 확정하며 미설정 상태에서 활성화하지 않는다.

원본·상세 파생 정보의 LLM 입력 금지·외부 실행 추적 금지·자유문 금지는 실행기의 필수 정책이다. 최소 계약 밖의 필드를 일반 설정으로 추가하지 못하게 한다. 계약 확대는 별도 보안 설계 변경이며 원본 금지의 예외가 아니다. 필수 승인도 false로 바꿔 우회할 수 없게 한다. 입력 설정의 알 수 없는 키는 거부한다. 프로세스별 파일·네트워크 접근 권한은 별도 실행 환경에서 강제하며 JSON만으로 격리를 보장하지 않는다.

`plan`은 설정·파일 metadata만 읽어 실행 계획을 제시하고 pickle 역직렬화·다운로드·캐시 쓰기를 하지 않는다. `run`은 승인 지점에서 멈추고, `approve`는 지정된 계획에만 결정을 기록한다. `resume`은 원본·설정·완료 결과를 확인한 뒤 재개한다. 실제 명령 문법은 구현 때 확정하며 현재 실행 가능한 명령으로 안내하지 않는다.

## 11. 최소 구현과 검증 기준

### 단계별 구현

1. 전처리 코어의 ingest·audit부터 완성하고 합성 입력으로 계약을 검사한다.
2. 로컬 `plan/run/status`와 상태 스키마·도구 adapter를 만든다. LLM·외부 tracing은 사용하지 않는다.
3. LangGraph에 원본 승인→검사→분할 승인→캐시 승인→계약 검증 흐름을 연결한다.
4. 프로세스를 중단했다 재개해 완료 결과 재사용·부분 결과 차단을 확인한다.
5. 구조·split·변환 실패 사례와 승인 변경을 시연한다.
6. 최소 상태 매핑·선택기 프로세스·응답 검증을 구현하고 합성 fixture로 차단 사례를 검증한다. provider 정책·잔여 위험·호출/비용 한도를 승인한 뒤 실제 실행의 제한적 LLM 선택 모드를 활성화한다.
7. LangSmith 시연이 필요하면 실제 데이터·환경·실행 이력과 무관하게 수작업으로 만든 합성 fixture를 별도 환경에서만 사용한다.

### 완료 체크

아래는 초기 런타임 LLM 선택기 설계의 목표 검사다. 현재 구현된 제안·실행·해설의 완료 여부는 상단 현재 기준과 GUIDE를 따른다. 미활성 선택기 목표를 근거 없이 완료 체크하지 않는다.

- [ ] 같은 설정에서 코어 단독·규칙 모드·LLM 선택 모드의 필수 데이터 계약·결정적 산출물이 일치한다. 추가 진단 순서만 달라질 수 있다.
- [ ] API 키·인터넷·LLM 없이 전처리와 보고서 생성이 완료된다.
- [ ] 품질 blocker가 있으면 분할·학습용 산출물 등록으로 진행하지 않는다.
- [ ] 승인 후 설정을 바꾸면 이전 승인으로 실행되지 않는다.
- [ ] 중단·재개·중복 호출 때 결과 덮어쓰기·이중 실행이 발생하지 않는다.
- [ ] 보고서만 재생성하면 원본 로드·분할·캐시 단계는 다시 실행되지 않는다.
- [ ] 미라벨·metadata의 악성 문자열이 도구 실행·승인으로 해석되지 않는다.
- [ ] 경로 이탈·원본 삭제·자동 Test 평가 요청을 거부한다.
- [ ] 원본·집계·설정·실제 오류·식별자가 LLM 요청·재시도에 포함되지 않고 최소 DTO와 정적 정책만 전달된다. 실제 실행의 외부 trace·telemetry는 차단된다.
- [ ] 데이터 처리 프로세스의 외부 네트워크와 선택기 프로세스의 실제 파일·체크포인트 접근이 권한 수준에서 차단된다.
- [ ] 서로 다른 합성 원본이 같은 최소 상태·허용 동작으로 매핑되면 전송 본문이 동일하다. 동적 헤더·metadata에도 원본 차이가 반영되지 않는다.
- [ ] 합성 입력에 심은 추적용 표식이 요청·헤더·metadata·오류 전송에 나타나지 않는다. 이 검사는 보조 검증이며 권한 차단을 대체하지 않는다.
- [ ] 알 수 없는 상태·필드·원문 삽입을 전송 전에 거부한다. 입력 게이트 차단 사례의 외부 요청 수는 0이다.
- [ ] LLM의 미허용 동작·추가 인자·오래된 응답·승인 우회·동일 상태 반복을 거부하고 금지 도구 실행 수는 0이다.
- [ ] blocker가 있는 동안 LLM 선택과 무관하게 후속 처리·등록이 잠기며, 선택/재시도/총 요청 한도 초과 시 규칙 경로 또는 안전 중단으로 전환한다.
- [ ] 체크포인트에 비밀 키를 저장하지 않으며 로컬 데이터 접근 권한을 적용한다.
- [ ] LLM 실패에도 로컬 수치 보고서와 완료 산출물은 유지된다. 실패·모드 전환은 로컬에 기록된다.

핵심 시연은 **정상 완료, 상태별 진단 도구 선택, 위험한 선택 차단, 승인 후 재개, 중단 후 재사용, LLM 없이 완료**다. 선택기의 유효 동작 선택률·불필요 진단 횟수·사용자 확인까지의 호출 수를 규칙 모드와 비교한다. 규칙보다 이득이 없으면 LLM을 필수 요소로 만들지 않는다. 성과는 분류 정확도 향상으로 주장하지 않고 수작업 감소·실패 탐지·재현성·데이터 계약 준수로 평가한다.

## 12. 초기 결정과 현재 유보 사항

초기에는 LangGraph 기반 런타임 선택기를 계획했지만 현재는 제안 대화에만 사용한다. 전처리 코어 독립·로컬 기록·명시적 승인 원칙은 유지한다. LLM은 실행안을 제안하고 규칙 실행기가 권한·승인·차단을 강제한다. 수치 해설은 별도 허용 자료의 보조 설명이며 자율 정책 변경·품질 판정으로 쓰지 않는다. LangSmith·외부 추적은 활성화하지 않았다.

로컬 provider·모델 설정, 메모리 전용 대화 checkpoint, 작업별 시간·자원 상한은 구현했다. 외부 provider, 대화 영구 보존, 승인 DB 변조 방어, 조회·캐시 성능 개선과 추가 형식의 일반화는 별도 유보 사항이다. 이를 현재 마감의 필수 개발로 확대하지 않는다.

현재 공통 입력·EDA·품질·분할·Train 기준 산출/적용·전달을 구현하고, CSV 실제 사용자 실행과 WM 정상 개발 흐름을 구분해 검증했다. 품질 검토 필요는 자동 해제하지 않는다. 최소 상태 기반 런타임 선택기는 활성화하지 않았으며, 자연어 제안과 별도 결과 해설은 구현되어 있다. 추가 개발보다 현재 마감 범위·보류 항목을 기준으로 관리한다.
