# 저장 facts 기반 화면 표의 자동·실제 UI 최종 검증

저장 facts를 읽어 표시하는 화면 표의 열 순서·값 대응·빈 셀·저장 전후 표시를 자동 UI 테스트와 실제 브라우저에서 확인하는 재사용 절차다. 아래의 구체적인 기준 사례는 CSV v2 적용 확인 화면의 **예상 처리 영향** 표다. 구현 완료·자동 테스트 통과·실제 화면 통과를 각각 판정한다. 이 문서는 테스트 구현·실행이 모두 완료됐다는 뜻도, 새 실행 승인도 아니며, 현재 지원·검증 상태는 [GUIDE](../GUIDE.md), 승인·격리 계약은 [DESIGN](../DESIGN.md)을 따른다.

다른 표에 재사용할 때는 3절의 대상 경로·고정 머리글·셀 근거와 5~6절의 도달 조건을 먼저 그 표에 맞춰 정한다. 이 CSV 사례를 배열·계획 확인 화면 전체의 합격 기준으로 적용하지 않는다. 기능별 실행 안내와 함께 사용하는 검증 절차이므로 이 경로를 유지하고, 코드 위치가 바뀌면 절차를 갱신한다.

## 1. 수행자와 실행 범위

| 단계 | 수행 환경 | 범위 |
| --- | --- | --- |
| 자동 검증 | 일반 Claude Code 또는 Codex | `unittest`·Streamlit AppTest, 합성 집계·임시 디렉터리·mock |
| 실제 최종 확인 | Chrome 연결 Claude Code 또는 브라우저 제어가 연결된 실행자 | 최종 코드의 서버에서 새 합성 작업 1건, 적용 확인 화면까지 |
| 완료 보고서까지의 확장 확인 | 별도 실행 범위를 확인한 브라우저 실행자 | 동의 D 이후 적용·전달·보고서까지. CSV 적용 확인 표를 검증하는 필수 경로는 아님 |

실제 실행 전 새 작업 생성·합성 입력·로컬 모델 요청·동의 A/C의 허용 범위를 확인한다. 해당 범위가 이미 승인됐으면 반복해서 묻지 않는다. 모델 요청은 최대 1회이며 거부·연결 실패에도 재요청하지 않는다. 기본 계획으로 후보까지 진행할 수 있으면 표시 검증을 계속하고 모델 경로는 별도 판정한다.

필수 최종 확인은 `awaiting_apply`에서 종료한다. **동의 D를 체크하거나 적용·전달을 실행하지 않는다.** 실행환경 개편, 승인 검사 축소, 기존 작업 재조립, 전체 회귀, 커밋·푸시는 포함하지 않는다.

## 2. 시작 조건과 고정할 근거

1. HEAD·Git 상태·수정 대상 소스/테스트 해시를 기록한다. 기존 사용자 변경을 보존한다.
2. 테스트 실행 중 대상 소스·테스트·설정을 바꾸지 않는다. 변경이 생기면 해당 실행을 최종 코드 근거로 사용하지 않는다.
3. 서버 PID·시작 시점·실행 코드 경로와 관련 소스의 변경 시점을 확인한다. 최종 코드를 읽은 서버인지 불명확하면 재시작을 조율한다. 사용자 서버를 임의 종료하지 않는다.
4. 승인·자원·모델의 실제 유효 설정을 화면에서 확인한다. 관리자 권한이 필요한 서버는 사용자가 승인한 방식으로 시작한다.
5. 기존 완료 작업·facts·보고서·승인 기록은 수정하거나 재사용하지 않는다. 파일과 폴더에는 충돌하지 않는 새 이름을 사용하고 기존 파일을 덮어쓰지 않는다.
6. 시험 중 코드가 바뀌면 실제 UI 결과를 변경 후 코드의 검증으로 승계하지 않는다. 실패 시 자동 재시도하거나 새 작업을 추가하지 않는다.
7. 다른 작업자가 테스트를 실행 중이면 대상 소스·테스트를 고치지 않는다. 실행 완료와 결과 보고를 확인한 뒤 보완하며, 이 문서의 케이스 수를 현재 구현된 테스트 수나 통과 수로 인용하지 않는다.

## 3. 테스트 대상과 정답 기준

대상 표 제목은 `예상 처리 영향 (Train 후보 계산, 영향이 있는 특징만)`이다. 현재 생성 경로는 `tabular_task.review_facts` → 저장된 후보 facts → `task_view._render_apply` → 공통 표 렌더링이다. 함수 이름이 바뀌어도 같은 제품 경로를 추적한다.

열의 정답은 다음 **고정 목록**이다.

| 위치 | 머리글 |
| --- | --- |
| 1 | 특징 |
| 2 | 변환 전 고유값 |
| 3 | clipping 변경 값 |
| 4 | 구간 수 |
| 5 | 출력 열 |
| 6 | 변환 후 상수 |
| 7 | 정보 손실 |

정답은 사용자가 확인할 흐름인 **특징 → 변환 전 상태 → 변환 영향 → 출력·정보 손실**에 따른다. `COLUMN_ORDER`나 테스트 대상 함수가 반환한 순서를 그대로 기대값으로 삼지 않는다. 제품 계약이 바뀔 때만 이 목록과 테스트 기대값을 함께 검토한다.

이 표는 영향이 있는 특징만 표시한다. 행이 없는 상태를 열 순서 통과로 판정하지 않는다. 화면의 표시는 문자열이 될 수 있으므로 값 대조에서는 표시 형식을 구분하되 값·행 대응을 유지한다.

### 셀별 대조 근거

후보 facts는 화면과의 대응 근거이고, 값의 출처는 후보·전처리 근거에서 별도로 확인한다. 현재 `tabular_task._expected_impact`의 표기 규칙은 다음과 같다. 구현이 바뀌면 해당 규칙이 제품 계약과 맞는지 확인하고 이 절을 갱신한다.

| 표시 열 | 후보·전처리 근거와 표기 |
| --- | --- |
| 특징 | 후보 impact의 `column` |
| 변환 전 고유값 | 후보 impact의 `distinct_before` |
| clipping 변경 값 | `clipped`와 Train 행 수·해당 특징의 결측 수를 이용한 비율. 분모는 `max(train_rows - missing, 1)`. `clipped=None`은 기존 미산출 표기 |
| 구간 수 | 해당 전처리 record의 `edges`가 있으면 `len(edges) + 1`, 없으면 `-` |
| 출력 열 | 후보 impact의 `width` |
| 변환 후 상수 | 후보 impact의 `constant_after`가 참이면 `예`, 아니면 `아니오` |
| 정보 손실 | `constant_after`가 참이고 `distinct_before > 1`이면 `예`, 아니면 `-` |

`정보 손실`은 candidate.json의 같은 이름 필드를 읽는 값이 아니라 위 조건에서 조립한 표시다. 이 표기는 상수화에 대한 제한된 판정이며 모든 변환의 정보 보존 여부를 증명하지 않는다. 특징별 영향 수치의 worker 집계·부모 검증 수준을 구분하고 표시 확인을 독립 계산 검증으로 과장하지 않는다.

### 다른 표의 순서와 검증 범위

계획 확인 화면의 `기본 계획과 다른 항목`·`이번에 고친 항목` 등 화면 전용 표와 배열 결정 D의 채널 표는 표를 만드는 쪽이 열 순서를 명시하도록 보완됐다. 각 표의 자동 검증·실제 UI 확인 여부는 [GUIDE의 남은 제한과 안정화](../GUIDE.md#남은-제한과-안정화)를 따른다. 보완된 표와 실제 UI 미검증인 표를 구분하고, 이 문서를 과거 결함이 계속 미해결이라는 근거로 사용하지 않는다.

공통 렌더러나 같은 열 이름을 사용해도 표별 정답 순서는 다를 수 있다. 다른 표에서 문제가 관찰되면 현재 GUIDE와 대조해 새 결함인지 확인하고 CSV 영향 표의 판정과 분리한다. 다른 표의 수정·검증을 자동으로 이번 실행 범위에 포함하지 않는다. 새 값 불일치·승인 범위 문제로 안전하게 진행할 수 없다면 별도 차단 사유다. 이 절에 표별 검증 상태나 실행 이력을 복제하지 않는다.

## 4. 자동 테스트 케이스

기본 위치는 `tests/agents/test_report_display_fix.py`다. 이미 같은 검사가 있으면 재사용·보완하고 중복 테스트 파일을 만들지 않는다. 아래 ID는 검증 항목이며 실제 테스트 함수 수와 같을 필요는 없다.

| ID | 준비·조작 | 기대 결과 |
| --- | --- | --- |
| A01 실제 적용 화면 경로 | 실제 `review_facts`로 서로 다른 영향 행을 2개 이상 조립한다. clipping·원핫 등의 합성 집계를 사용하고 JSON 저장/재조회처럼 키를 정렬한 뒤 AppTest에서 `_render_apply`를 호출한다. | 예외 없이 대상 표가 나타나고 머리글이 3절의 고정 목록과 정확히 같다. 공통 함수만 따로 호출하는 검사로 대체하지 않는다. |
| A02 값·행 보존 | 특징명·고유값·출력 폭뿐 아니라 구간 수·상수·정보 손실도 판별할 수 있는 서로 다른 행 조합을 둔다. 예: 구간 수가 있는 행과 없는 행, 원래 상수인 행과 변환 후 상수가 된 행. 후보·전처리 근거는 3절의 규칙과 일치시킨다. | 렌더링된 모든 셀이 별도로 정한 기대값과 대응하고, 행 순서·건수가 같다. 검사할 열들의 값 벡터가 전부 같아 열 교환을 못 잡는 fixture를 피한다. 기존 조립 facts와의 값 대조도 유지한다. |
| A03 누락 셀 | 서로 다른 행에서 `구간 수`, `정보 손실` 등 일부 키를 뺀다. 각 열은 다른 행에 하나 이상 남긴다. | 열 순서는 고정되고 누락 위치만 빈 칸이다. `None`·`nan`이 새 값처럼 표시되거나 행이 밀리지 않는다. |
| A04 영향 없음 | 영향 집계가 존재하는 정상 후보에서, 표시 조건에 해당하는 영향 행만 0개인 facts를 실제 `review_facts`로 만든다. 후보·impact 자체가 누락된 경우와 구분한다. | 대상 표 제목과 `(없음)`이 표시되며 영향 행을 만들어 내지 않는다. 이전 후보 등으로 영향 집계가 없어 표 자체가 생략되는 경우는 이 케이스의 입력·정답이 아니다. |
| A05 기존 표 호환 | 기존 완료 보고서뿐 아니라 실제 `_render_apply`가 특징별 처리·제거 후보·출력 폭·실제 실행 설정 표를 그리도록 기존 fixture를 준비한다. | 완료 표와 적용 화면의 각 인접 표를 제목·고유한 열 구성으로 식별해 머리글·셀·행 순서를 대조한다. 빈 표가 있으면 표 인덱스가 제목 순번과 같다고 가정하지 않는다. 기존 Markdown 문자열 불변 계약이 있으면 유지한다. |
| A06 저장 순서와 독립 | 조립 직후와 JSON 키 정렬 후 같은 표를 렌더링한다. | 두 화면의 열·행·값이 같다. 저장 과정의 가나다순 키 정렬을 사용자 표시 순서로 쓰지 않는다. |

합성 집계는 표시 검증을 위한 것이며 실제 clipping 계산을 검증했다고 표현하지 않는다. 후보·행·표 생성 전체를 mock해 정답 DataFrame을 직접 반환하는 테스트로 A01을 대신하지 않는다. 실제 실행·모델 요청·승인 발급은 mock으로 분리한다.

필수 단언은 다음처럼 나눈다. A01은 3절의 머리글 7개를 테스트에 고정해 비교하며 `list(built[0])`를 정답으로 쓰지 않는다. A02는 고정된 셀 기대값과 사실 보존을 함께 확인한다. A03은 빈 셀뿐 아니라 A01의 고정 머리글도 검사한다. A04는 '영향 집계 있음·표시 행 0개'의 대상 제목과 빈 표 안내를 식별한다. 영향 집계가 없어 표를 생략하는 이전 후보의 호환 검사는 별도로 구분하며 A04를 대신하지 않는다. A06은 동일 facts의 조립 직후/키 정렬 후 두 입력을 실제 화면 경로에 각각 넣어 비교한다. 저장된 입력만 한 번 렌더링한 테스트로 A06을 충족했다고 하지 않는다.

수정 전 실패와 수정 후 통과를 구분한다. 이미 수정된 코드에 테스트를 추가한다면 실패 재현 방법과 한계를 기록하고, 실행하지 않은 RED를 실행했다고 쓰지 않는다. 공통 렌더러의 직접·전이 영향을 보고 관련 기존 테스트를 선별하며 전체 회귀는 별도 승인 범위다.

## 5. 실제 브라우저용 합성 입력

작업 폴더에 UTF-8·쉼표·첫 행 헤더의 CSV 1개를 새로 만든다. 최소 기본 사례는 120행이며 행 인덱스 `i`는 0~119다. 생성 규칙과 입력 SHA256을 기록한다.

| 컬럼 | 생성 규칙 | 최종 역할 |
| --- | --- | --- |
| `sample_id` | `i + 1`을 6자리 앞자리 0 문자열로 기록 | 식별자 |
| `temperature` | `20 + (i % 17)` | 수치형 |
| `pressure` | `100 + (i % 11)` | 수치형 |
| `line` | `i % 3`에 따라 `A`, `B`, `C`. 단, i=8·88은 빈 필드 | 범주형 |
| `outcome` | `i % 4 == 0`이면 1, 나머지는 0 | target |

실제 개인정보·실데이터를 넣지 않는다. `line`은 Train에 여러 범주가 남아 원핫 출력 폭이 1보다 커지도록 선택한 입력이다. 분할 결과를 확인하고 추측한 Train 범주 수를 정답으로 쓰지 않는다.

이 기본 입력은 영향 표에 `line` 1행을 표시해 대상 화면 도달·머리글·실제 값 대응을 확인하는 최소 사례다. 이상치 처리·구간화가 none이므로 clipping·구간 수·상수화·정보 손실의 다양한 값 조합은 검증하지 않는다. 특히 같은 `-` 값을 갖는 열의 교환을 B05만으로 판별할 수 없다. 서로 다른 값 조합의 셀 교환 판별은 A02 자동 검사가 맡으며, B05 통과를 A02 대체 근거로 쓰지 않는다.

목표 문장 예시:

> outcome 예측을 위한 전처리입니다. sample_id는 식별자로 보존하고, temperature와 pressure는 수치 특징, line은 범주 특징으로 사용하세요.

최종 계획은 위 역할, random 0.70/0.15/0.15, 시드 42, 계층 분할 켬, 모든 구간 클래스 요구 켬으로 맞춘다. 수치 결측 중앙값, standard 스케일링, 범주 결측 Train 최빈값, 이상치 처리·구간화 none을 사용한다. 그 밖의 실제 유효 설정과 자원 상한을 기록한다. 모델 권장값을 확인 없이 그대로 확정하지 않는다.

## 6. 실제 UI 최종 테스트 케이스

순서대로 수행한다. 브라우저 DOM·접근성 트리의 머리글 검사와 실제 화면의 시각 확인을 함께 사용한다.

| ID | 절차 | 합격 기준·증거 |
| --- | --- | --- |
| B01 시작·동의 A | 새 입력과 목표를 넣고 복사·진단·모델 전달 범위를 확인해 제출한다. | 새 작업 ID 1개. 로컬 공급자와 허용 전달 범위가 승인 범위와 같다. 원본 해시가 유지된다. |
| B02 계획 확정 | 역할·질문·전처리 옵션을 맞추고 최종 미리보기를 확인한 뒤 동의 C로 진행한다. | 역할·분할·전처리의 유효 설정이 5절과 같다. 질문이 나오면 응답과 확정 계획을 구분해 기록한다. 계획 화면의 다른 표는 3절에 따라 현재 검증 상태를 확인하고 대상 표의 판정과 분리한다. |
| B03 대상 표 존재 | 후보 완료 후 적용 확인 화면에서 대상 표를 찾는다. | `awaiting_apply`이며 표에 영향 행이 1개 이상 있다. `line` 행이 없다면 후보 사실·분할 범주 수를 확인하고 미검증/차단 사유를 기록한다. 다른 설정으로 임의 재실행하지 않는다. |
| B04 머리글 | 표의 실제 머리글을 왼쪽부터 추출하고 화면 캡처와 대조한다. | 3절의 7개 머리글과 정확히 같다. 제목이나 다른 표의 머리글을 잘못 읽은 결과가 아니다. |
| B05 모든 셀·행 대조 | 현재 작업의 후보 facts와 검증된 후보·전처리 근거를 읽기 전용으로 확인하고 3절의 셀별 규칙으로 대조한다. | 표시된 모든 영향 행의 특징·고유값·clipping·구간 수·출력 열·상수·정보 손실이 대응한다. 특히 정보 손실은 `constant_after and distinct_before > 1`에서 확인한다. 행 수·순서가 같다. worker 집계와 부모 검증 수준을 구분한다. |
| B06 배치·스크롤 | 브라우저 크기와 확대율을 기록하고 첫 화면 및 가로 스크롤 끝을 확인한다. | `특징`이 첫 열이며 모든 열과 값을 정상 스크롤로 확인할 수 있다. 가로 스크롤 자체는 결함이 아니다. 셀이 잘려도 제품의 기존 상세 보기로 확인 가능한지 구분한다. 범위 밖 오버레이·겹침·접근 불가를 기록한다. |
| B07 인접 표 회귀 | 같은 적용 화면의 특징별 처리·출력 폭·실제 실행 설정 등 표시된 표를 확인한다. | 기존 정해진 머리글 순서·값이 유지된다. 대상 표만 통과했다고 모든 표 통과로 일반화하지 않는다. |
| B08 종료·보존 | 동의 D 이전에 종료하고 작업·서버·파일 상태를 확인한다. | 작업은 `awaiting_apply`. 동의 D·적용·전달·보고서 생성이 없다. 대상 소스·입력 해시가 전후 같고 기존 결과가 보존된다. 사용자 서버·기존 탭을 유지하고 시험자가 연 탭만 닫는다. |

이 필수 경로에서는 Markdown 최종 보고서를 새로 생성하지 않는다. 대상 표는 적용 화면 전용이므로 후보 facts와 대조한다. 완료 보고서 호환은 A05의 자동 검사와 별도 실제 완료 검증 이력을 구분한다.

## 7. 선택: 완료 보고서 표시 전체 확인

질문 답변·작은 결측률 PNG·클래스 순서·완료 화면과 Markdown까지 다시 검증할 필요가 있을 때만 선택한다. 시작 전에 새 작업 수와 동의 D 이후 실행까지 승인된 범위를 확인한다. 기본적으로 별도 작업을 추가하지 않고 계획한 같은 작업의 완료 범위를 확장한다.

- 작은 결측률 확인이 목적이면 시작 전에 입력을 1,309행으로 정하고 `line` 빈 필드를 2개만 둔다. 나머지 생성 규칙은 5절을 따른다. 결측률 정답은 `2/1309 × 100 ≈ 0.153%`다. target 분포는 생성 결과에서 확인하며 다른 사례의 967/342를 가져오지 않는다.
- 적용 화면 B03~B07을 먼저 확인한 뒤 유효 설정·후보 영향을 대조하고 동의 D로 적용·전달·보고서까지 진행한다.
- 질문이 실제로 나왔다면 선택 컬럼과 확정 역할의 표시를 확인한다. 질문이 없으면 해당 항목은 실제 UI 미검증으로 남긴다. 기록을 변조하거나 모델을 재호출하지 않는다.
- 완료 화면과 새 Markdown의 해당 표 머리글·값을 대조한다. 분할 클래스 순서는 구간별로 같아야 한다. target 전체 분포 표의 정렬 기준과 다를 수 있으므로 기준을 함께 본다.
- 새 분할 EDA의 검증된 PNG에서 약 0.15% 막대·값 라벨·0 시작 백분율 축을 확인한다. 파일 해시 일치만으로 가시성을 판정하지 않고 화면을 직접 본다.
- 확대 검증에서 적용·전달·보고서가 생성되는 것은 정상이다. 이 경우 B08의 필수 종료 조건을 그대로 적용하지 말고 완료 상태·실행 범위·산출물 보존으로 판정한다.

## 8. 판정·증거·재사용 기록

각 케이스를 `통과 / 실패 / 미검증 / 차단`으로 기록한다. 미검증·차단은 통과 수에 넣지 않는다. 모델 연결 실패와 표시 결함을 구분한다. 값이 맞아도 열 순서가 틀리면 B04는 실패다. 자동 테스트 통과만으로 B04~B07의 실제 브라우저 통과를 선언하지 않는다.

필수 완료 조건은 A01~A06과 B01~B08의 확인이다. 미검증·차단이 남으면 확인한 범위만 보고하고 최종 UI 검증 완료로 쓰지 않는다. 선택 확장을 하지 않았다는 이유만으로 필수 열 순서 검증을 미완료로 판정하지 않는다.

실행 근거는 `_workspace/display_fix/` 아래 충돌 없는 폴더에 최소한만 보관한다. 모델 원문·승인 토큰·전체 작업 기록은 복제하지 않는다. 화면 캡처에서 주소창·토큰·모델 자유 문장을 제외한다. 승인 ID를 알아야 할 때도 전체 토큰을 기록하지 않는다.
